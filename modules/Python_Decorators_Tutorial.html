00What is a decorator?

A decorator is a function that modifies or extends another function (or class) without changing that function's source code. You "wrap" the original in extra behavior and get an enhanced version back.

Imagine you have a plain sandwich. You want to add lettuce, tomato, and mayo. You could take the sandwich apart, insert the ingredients, and put it back together. Or... you could just wrap the whole thing in a bigger sandwich that already has those ingredients.

Decorators are that bigger sandwich. They take your original function (the inner sandwich), add stuff around it (the lettuce and tomato), and give you back the whole package. Your original function never changes — it just gets wrapped.

Say you have a plain function and you want to time how long it runs, log every call, cache its results, or check permissions first. You could edit the function and paste that logic inside. But you'd repeat yourself for every function that needs it, and you'd tangle the core logic with side concerns.

Decorators let you write that extra behavior once and apply it anywhere with a single line:

the whole idea, in four lines
@timer                       # ← apply the decorator
def crunch_numbers():
    return sum(range(10_000_000))

crunch_numbers()             # runs your code AND prints the timing
🎁The Gift Wrap Analogy

Think of a decorator like gift wrap. You have a toy (your function). You put it in a box (the wrapper). The box might have a ribbon, a card, and bubble wrap — but the toy inside is still the same toy. When someone "opens the gift" (calls the function), they see the box first, then the toy, then the box again. The toy never knows it was wrapped.

★The one sentence to remember

A decorator takes a function as input, defines a new function that adds behavior around it, and returns that new function. The @ symbol is just a shortcut for that hand-off.

Before we can build one, we need two Python features that make decorators possible. If you already know that functions are objects and what a closure is, skip to section 03.

01Functions are first-class objects

In Python, functions are values like any other. You can store them in variables, pass them into other functions, and return them from functions. This is the foundation decorators are built on.

🎫Think of functions as tickets

A function is like a ticket to a movie. You can hold it in your hand (store in a variable), give it to a friend (pass as an argument), or get a new ticket back from the box office (return from a function). The ticket represents the movie — it doesn't start playing until you walk into the theater (add parentheses).

Assign a function to a variable

Referencing a function without parentheses gives you the function object itself, not its result:

first_class.py
def shout(text):
    return text.upper() + "!"

yell = shout          # no parentheses → grab the function object
print(yell("hello"))  # call it through the new name
OutputHELLO!
Step 1
We defined shout. It lives in memory as a function object.
Step 2
We wrote yell = shout — no parentheses! This means "make yell point to the same function object as shout."
Step 3
Now yell and shout are two names for the exact same function. Calling either one does the same thing.

Pass a function as an argument

Because a function is just a value, it can be handed to another function. The receiver decides when (and whether) to call it:

higher_order.py
def do_twice(func, value):
    func(value)
    func(value)

def announce(name):
    print(f"Welcome, {name}!")

do_twice(announce, "Ada")   # pass the function, don't call it here

02Nested functions & closures

A function can be defined inside another function and returned from it. When the inner function remembers variables from the enclosing function, that's a closure — and it's exactly how a decorator "carries" the original function around.

🎒The Backpack Analogy

Imagine a teacher gives a student a backpack containing a calculator. The student walks out of the classroom. Even though class is over, the student still has the calculator in their backpack. A closure is like that backpack — the inner function carries variables from the outer function even after the outer function has finished running.

closures.py
def make_multiplier(factor):
    def multiply(number):        # inner function
        return number * factor   # "remembers" factor from outside
    return multiply              # return the function, uncalled

triple = make_multiplier(3)      # triple is a closure over factor=3
double = make_multiplier(2)

print(triple(10))   # 30
print(double(10))   # 20
Output30
20
Step 1
We call make_multiplier(3). Inside, factor becomes 3.
Step 2
We define multiply inside. It "sees" factor = 3 because it's inside the same scope.
Step 3
We return multiply — but we don't call it yet! We just hand back the function object.
Step 4
make_multiplier finishes. Normally, factor would be thrown away. But multiply still remembers it!
Step 5
Later, we call triple(10). The closure opens its backpack, finds factor = 3, and calculates 10 × 3 = 30.

Notice how triple still knows that factor is 3, long after make_multiplier finished running. The inner function closed over that variable and keeps it alive.

★Why this matters for decorators

A decorator receives your function as an argument, defines an inner "wrapper" that closes over it, and returns the wrapper. Closures are the mechanism that lets the wrapper reach back and call your original function.

03Build a decorator by hand

Now combine both ideas. A decorator is a function that (1) accepts a function, (2) defines a wrapper that adds behavior and calls the original, and (3) returns that wrapper.

🥪The Sandwich Shop Analogy

Imagine a sandwich shop. You hand them your plain sandwich (the function). They put it on a plate, add fries on the side, pour a drink, and hand the whole tray back to you. Your original sandwich is still there — but now it comes with extras. You didn't change the sandwich; you just got a better meal.

1
Accept a function

The outer function takes the function you want to enhance as its parameter, conventionally named func.

2
Define a wrapper inside

An inner function adds behavior before and/or after, and calls func() in the middle.

3
Return the wrapper

Return the wrapper function itself — not its result. The caller now uses the wrapped version.

my_first_decorator.py
def announce(func):              # 1. accept a function
    def wrapper():               # 2. define the wrapper
        print("→ before the function runs")
        func()                   #    call the original
        print("← after the function runs")
    return wrapper               # 3. return the wrapper (no parentheses!)

def say_hello():
    print("Hello, world!")

# manually wrap it:
say_hello = announce(say_hello)  # reassign the name to the wrapped version
say_hello()

04The @ syntax is just sugar

Putting @decorator on the line above a function is identical to defining the function and then writing func = decorator(func). Nothing magic — just a tidy shorthand.

📝The Sticky Note Analogy

Writing @announce above a function is like putting a sticky note on a package that says "Please gift-wrap this." You could also hand the package to the gift-wrap counter and say "wrap this, please" — both do the same thing. The sticky note is just faster and more visible.

These two blocks do the exact same thing

The @ form is preferred because the decoration is visible right where the function is defined.

the_at_syntax.py
# ── verbose form ─────────────────────────
def say_hi():
    print("Hi!")
say_hi = announce(say_hi)

# ── @ form (identical result) ────────────
@announce
def say_hi():
    print("Hi!")

say_hi()   # already wrapped, just call it
Output→ before the function runs
Hi!
← after the function runs
→Read @announce as…

"Take the function defined below me, pass it through announce, and bind the result to the same name." The line runs once, at definition time.

Does the @ symbol do anything special?
No! It's just shorthand. Python sees @announce and immediately rewrites it as say_hi = announce(say_hi) in its head. The @ symbol exists only to make your code prettier and easier to read.

05Arguments & return values

Our first wrapper only worked for functions that take no arguments and return nothing. To decorate any function, the wrapper must accept arbitrary arguments with *args / **kwargs and pass along the return value.

📦The Mail Forwarding Analogy

Imagine you're a receptionist. People hand you packages with all sorts of labels — some have one address, some have many, some have special instructions. Instead of writing a rule for every possible package, you just say "I'll accept ANY package and forward it to the right person." *args and **kwargs are that "any package" rule.

The universal wrapper pattern

universal_wrapper.py
def announce(func):
    def wrapper(*args, **kwargs):        # accept ANY arguments
        print(f"→ calling {func.__name__}")
        result = func(*args, **kwargs)   # forward them; capture the result
        print(f"← {func.__name__} returned {result!r}")
        return result                    # hand the result back to the caller
    return wrapper

@announce
def add(a, b):
    return a + b

total = add(3, 4)      # arguments flow through the wrapper
print("total =", total)
Output→ calling add
← add returned 7
total = 7

!Two things people forget

1. The wrapper must return result, or every decorated function silently returns None.  2. Always forward *args, **kwargs so keyword and positional arguments both survive the trip.

What are *args and **kwargs exactly?
*args catches all positional arguments (like 3, 4) into a tuple. **kwargs catches all keyword arguments (like name="Ada") into a dictionary. Using both means "I'll accept whatever you give me."

06Preserve metadata with @wraps

When you wrap a function, the wrapper's identity replaces the original's. The function's name, docstring, and signature now report as the wrapper's — which breaks debugging and documentation tools. functools.wraps copies that metadata back.

🎭The Mask Analogy

When you wrap a function, it's like putting a mask on someone. From the outside, everyone sees the mask (the wrapper's name and docs) instead of the real person (your original function). @wraps is like writing the real person's name on the mask so everyone still knows who they are.

The problem

metadata_lost.py
def announce(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@announce
def greet(name):
    """Return a friendly greeting."""
    return f"Hi {name}"

print(greet.__name__)   # 'wrapper'  ← identity lost!
print(greet.__doc__)    # None       ← docstring gone!
Outputwrapper
None
What went wrong?
Python looks at greet and sees... wrapper. Because wrapper is the function object that got returned and assigned to the name greet. The original greet is hidden inside, but Python doesn't know that.

The fix

Decorate your wrapper with @functools.wraps(func). It's a decorator for decorators — it copies __name__, __doc__, and more from the original onto the wrapper.

metadata_kept.py
import functools

def announce(func):
    @functools.wraps(func)           # ← copy identity from func onto wrapper
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@announce
def greet(name):
    """Return a friendly greeting."""
    return f"Hi {name}"

print(greet.__name__)   # 'greet'  ✓
print(greet.__doc__)    # 'Return a friendly greeting.'  ✓
Outputgreet
Return a friendly greeting.
★Make it a habit

Use @functools.wraps(func) on every wrapper you write. It costs one line and prevents a whole category of confusing bugs in logging, introspection, and frameworks that read function names.

Why is it called "wraps"?
Because it "wraps" your wrapper with the original function's identity. It's a decorator that fixes the side effects of using decorators. Very meta!

07Decorators that take arguments

Sometimes you want to configure a decorator, like @repeat(3) or @retry(times=5). That needs one more layer: a function that takes the arguments and returns a decorator. It's a decorator factory.

🏭The Factory Analogy

Imagine a factory that makes gift wrap machines. You tell the factory "I want a machine that uses red paper." The factory builds that specific machine and hands it to you. Then you use that machine to wrap your gift. The factory doesn't wrap the gift itself — it builds the wrapper.

1
Outer: takes the config

repeat(times) receives the argument and returns the actual decorator.

2
Middle: the decorator

decorator(func) receives the function, like every decorator so far.

3
Inner: the wrapper

wrapper(*args, **kwargs) does the work and can see both times and func.

Three layers of a decorator with arguments

factory (outer)
→
decorator(func)
decorator (middle)
→
wrapper()
wrapper (inner)
decorator_factory.py
import functools

def repeat(times):                       # 1. takes the argument
    def decorator(func):                   # 2. the real decorator
        @functools.wraps(func)
        def wrapper(*args, **kwargs):    # 3. the wrapper
            for _ in range(times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(times=3)                         # note the parentheses → it's called
def cheer(team):
    print(f"Go {team}!")

cheer("Python")
OutputGo Python!
Go Python!
Go Python!
→Spot the difference

@announce (no parens) uses the decorator directly. @repeat(3) (with parens) calls repeat first, and the decorator it returns is what actually wraps your function.

Why three layers instead of two?
Because decorators are functions that take functions and return functions. If you want the decorator itself to take arguments, you need an extra layer: one to take the arguments, one to take the function, and one to be the wrapper. Think of it like: factory → machine → wrapped gift.

08Real-world decorators

These are the patterns you'll actually reach for. Each is a complete, copy-paste-ready example built from everything above.

A. Timing how long a function takes

timer.py
import functools, time

def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@timer
def slow_square(n):
    time.sleep(0.5)
    return n * n

print(slow_square(9))
Outputslow_square took 0.5003s
81
⏱️What's happening?

The wrapper is a stopwatch. It presses "start" before your function runs, presses "stop" after it finishes, and tells you the time. Your function doesn't know it's being timed — it just does its job.

B. Logging every call

logger.py
import functools

def log_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        signature = ", ".join(
            [repr(a) for a in args] +
            [f"{k}={v!r}" for k, v in kwargs.items()]
        )
        print(f"CALL  {func.__name__}({signature})")
        result = func(*args, **kwargs)
        print(f"RET   {func.__name__} -> {result!r}")
        return result
    return wrapper

@log_calls
def power(base, exponent=2):
    return base ** exponent

power(3, exponent=4)
OutputCALL power(3, exponent=4)
RET power -> 81

C. Caching results (memoization)

Store results keyed by arguments so repeated calls with the same input return instantly. (For real code, prefer the built-in functools.lru_cache shown in section 11 — this shows how it works underneath.)

memoize.py
import functools

def memoize(func):
    cache = {}                           # closure keeps the cache alive
    @functools.wraps(func)
    def wrapper(*args):
        if args not in cache:
            cache[args] = func(*args)    # compute once, store it
        return cache[args]               # reuse thereafter
    return wrapper

@memoize
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(fib(35))   # fast, even though it's naive recursion
Output9227465
🗂️The Filing Cabinet Analogy

Every time your function computes a result, the wrapper writes it down in a filing cabinet (the cache) indexed by the arguments. Next time the same arguments come in, it just looks up the filing cabinet instead of computing again. This turns an impossibly slow calculation into an instant lookup.

D. Retrying on failure

A configurable decorator (a factory, from section 07) that re-runs a function if it raises an exception:

retry.py
import functools, time

def retry(times=3, delay=1.0):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as err:
                    print(f"attempt {attempt} failed: {err}")
                    if attempt == times:
                        raise            # give up, re-raise the last error
                    time.sleep(delay)
        return wrapper
    return decorator

@retry(times=3, delay=0.2)
def flaky():
    import random
    if random.random() < 0.7:
        raise ConnectionError("network hiccup")
    return "success"

print(flaky())
🔄The Patient Parent Analogy

This decorator is like a patient parent teaching a child to ride a bike. The kid falls (raises an exception). The parent says "try again" up to 3 times. If the kid still can't do it after 3 tries, the parent accepts defeat and lets the error happen.

E. Access control

requires_role.py
import functools

def requires_role(role):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(user, *args, **kwargs):
            if user.get("role") != role:
                raise PermissionError(f"{role} role required")
            return func(user, *args, **kwargs)
        return wrapper
    return decorator

@requires_role("admin")
def delete_database(user):
    return "database deleted"

admin = {"name": "Ada", "role": "admin"}
print(delete_database(admin))          # works
# delete_database({"role": "guest"})   # -> PermissionError
Outputdatabase deleted

09Class-based decorators

A decorator just has to be callable — and any class with a __call__ method is callable. Classes shine when your decorator needs to hold state, like a counter, across calls.

🤖The Robot Analogy

A function decorator is like a tool that does one job. A class decorator is like a robot that does the job AND keeps a notebook of everything it did. The robot (class) remembers how many times it was called because it has a notebook (instance variable).

count_calls.py
import functools

class CountCalls:
    def __init__(self, func):
        functools.update_wrapper(self, func)  # class-form of @wraps
        self.func = func
        self.count = 0

    def __call__(self, *args, **kwargs):       # runs on every call
        self.count += 1
        print(f"call #{self.count} of {self.func.__name__}")
        return self.func(*args, **kwargs)

@CountCalls
def hello():
    print("Hello!")

hello()
hello()
print("total calls:", hello.count)   # state lives on the instance
Outputcall #1 of hello
Hello!
call #2 of hello
Hello!
total calls: 2
Step 1
Python sees @CountCalls and calls CountCalls(hello). This creates an instance of the class.
Step 2
__init__ stores the original function in self.func and sets self.count = 0.
Step 3
The instance is assigned to the name hello. Now hello is an object, not a function.
Step 4
When you call hello(), Python runs hello.__call__() — which increments the counter and calls the original function.
→Function or class?

Use a function decorator for most cases — it's lighter. Reach for a class when you need to expose state or methods on the decorated object (like reading hello.count above).

10Stacking decorators

You can apply several decorators to one function. They wrap from the inside out — the one closest to the function runs first at definition time, and its wrapper sits innermost at call time.

🥞The Layer Cake Analogy

Imagine putting on clothes: underwear first, then pants, then a jacket. The jacket goes on last but is the outermost layer. When you undress, the jacket comes off first. Decorators work the same way — the last one applied becomes the outermost wrapper.

stacking.py
def bold(func):
    @functools.wraps(func)
    def wrapper(*a, **k):
        return "" + func(*a, **k) + ""
    return wrapper

def italic(func):
    @functools.wraps(func)
    def wrapper(*a, **k):
        return "" + func(*a, **k) + ""
    return wrapper

import functools

@bold          # applied second (outer)
@italic        # applied first  (inner)
def greet():
    return "hi"

print(greet())
Output<b><i>hi</i></b>
How the wrapping happens (bottom to top)
greet()
original
→
italic()
wraps first
→
bold()
wraps second

Result: greet = bold(italic(greet))

★Reading the stack

Stacked decorators are equivalent to greet = bold(italic(greet)). Bottom-up at definition; the topmost decorator becomes the outermost layer at call time. Order matters when the decorators interact.

What if I swap the order?
Then you get greet = italic(bold(greet)) instead. The result would be "<i><b>hi</b></i>". Same ingredients, different order, different result.

11Built-in decorators you'll use

Python and its standard library ship with decorators you'll meet constantly. Recognizing them is half the battle.

@property

Turns a method into a read-only attribute. Access obj.area with no parentheses while logic runs behind it.

@staticmethod

A method that takes no self or cls — just a plain function living in a class's namespace.

@classmethod

Receives the class as cls instead of an instance. Common for alternative constructors.

@functools.lru_cache

Production-ready memoization. Caches results automatically with an optional size limit.

@functools.wraps

The metadata-preserving helper from section 06. Use it in every wrapper.

@dataclass

From dataclasses: auto-generates __init__, __repr__, and more for data-holding classes.

builtins_in_action.py
import functools

class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property                       # access as circle.area, not circle.area()
    def area(self):
        return 3.14159 * self.radius ** 2

    @classmethod                    # alternative constructor
    def unit(cls):
        return cls(radius=1)

    @staticmethod                   # no self / cls needed
    def describe():
        return "A circle is round."

@functools.lru_cache(maxsize=None)  # automatic caching
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

c = Circle(5)
print(c.area)          # 78.53975  (no parentheses)
print(Circle.unit().radius)   # 1
print(Circle.describe())
print(fib(50))         # instant, thanks to lru_cache
Output78.53975
1
A circle is round.

🔧Built-in = Batteries Included

Python gives you these decorators for free because they're so commonly needed. You don't have to write your own caching or property logic — just slap on the decorator and Python handles the hard parts.

12Common pitfalls

A short list of the mistakes that trip people up. Each one has a quick fix you've already seen above.

!Forgetting to return the result

If your wrapper calls func(*args, **kwargs) but never returns it, the decorated function returns None. Always capture and return result.

!Returning wrapper() instead of wrapper

The decorator must return the wrapper function object. Adding parentheses calls it immediately and returns whatever it produced — a classic bug.

!Skipping @functools.wraps

Without it, __name__, __doc__, and the signature report as the wrapper's. Breaks debuggers, docs, and some frameworks.

!Confusing @deco with @deco()

A plain decorator takes no parentheses. A decorator factory (one that takes arguments) must be called: @repeat(3). Mixing these up gives cryptic "missing argument" or "not callable" errors.

!Not forwarding *args, **kwargs

A wrapper with a fixed signature can only decorate functions with that exact signature. Use *args, **kwargs to stay general.

🩹Quick Fixes Cheat Sheet

Function returns None? → Add return result.
Function runs immediately on import? → Remove parentheses from return wrapper.
Getting "not callable" errors? → Check if you wrote @deco() when you meant @deco, or vice versa.
Function name shows as "wrapper"? → Add @functools.wraps(func).

🎓Final Thought

If you remember nothing else, remember this: a decorator is a gift wrapper for functions. It takes your function, puts a box around it, and hands back the box. When someone calls the box, the box does its thing first, then calls your function, then does more stuff, then returns the result. That's it. Everything else is just details about what kind of box you want.
