☁️ Topic 1 — Infrastructure
Cloud Computing
Cloud computing is the on-demand delivery of IT resources — servers, storage, databases, networking, software — over the internet with pay-as-you-go pricing. It's the foundation every modern system is built on.

What is Cloud Computing?

The Core Idea
Instead of buying and maintaining physical servers, you rent capacity from a provider (AWS, GCP, Azure) and pay only for what you use. The provider handles hardware, power, cooling, and physical security. You focus on your application.
On-Demand Pay-as-you-go Elastic Scaling Global Reach Managed Services

The 3 Service Models

The 3 Deployment Models

☁️ Public Cloud
Resources shared across many customers (multi-tenant). Managed entirely by the provider. Cheapest, most scalable. Examples: AWS, GCP, Azure.
🏢 Private Cloud
Cloud infrastructure dedicated to one organisation. On-premises or hosted. More control and security. Higher cost. Used by banks, governments.
🔀 Hybrid Cloud
Mix of public + private. Sensitive data stays on-prem; burst workloads run in public cloud. Best of both worlds. Most enterprises use this.

Key Cloud Concepts for System Design

Regions & Availability Zones (AZs)
A Region is a geographic area (us-east-1). Each region has 2–6 AZs — physically separate datacentres with independent power/networking. Deploy across AZs for high availability.
Horizontal vs Vertical Scaling
Vertical = bigger machine (scale up). Horizontal = more machines (scale out). Cloud enables auto-scaling — add/remove instances automatically based on CPU/traffic.
Managed Services
RDS (managed Postgres), ElastiCache (managed Redis), S3 (object storage), Lambda (serverless). Let the cloud handle ops — you write business logic.
Serverless / FaaS
AWS Lambda, GCP Cloud Functions. Run code without managing servers. Pay per invocation. Auto-scales to zero. Great for event-driven, bursty workloads.
CDN — Content Delivery Network
Distributes static assets (images, JS, CSS) to edge nodes globally. Users get served from the nearest edge — sub-50ms globally. CloudFront, Cloudflare, Fastly.

Cloud Architecture — Reference Diagram

System Design Tip: Always deploy across at least 2 AZs. Use managed services (RDS, ElastiCache, S3) instead of self-managing — they handle backups, failover, and patching. Auto-scaling groups ensure capacity matches demand automatically.

Do

  • Deploy app servers across multiple AZs
  • Use managed services — offload operational burden
  • Enable auto-scaling with proper health checks
  • Use CDN for all static assets globally
  • Tag everything — cost visibility is critical
  • Use IAM roles, not hardcoded credentials

Don't

  • Deploy in a single AZ (one outage = full outage)
  • Run your own database if a managed one exists
  • Commit credentials to source control
  • Ignore cloud costs — they compound fast
  • Skip backups and disaster recovery testing
📊 Topic 2 — Observability
Logging & Monitoring
You can't fix what you can't see. Logging and monitoring are the eyes of your system. Without them, debugging production incidents is guesswork. With them, you understand exactly what's happening and why.

The 3 Pillars of Observability

📝 Logs
Timestamped, structured records of discrete events. "User 42 logged in at 14:03:22". Human-readable. Rich context. Used for debugging and auditing.
📈 Metrics
Numeric measurements over time. CPU 72%, p99 latency 340ms, error rate 0.1%. Aggregatable. Alertable. Used for dashboards and anomaly detection.
🔍 Traces
Track a single request across multiple services end-to-end. Shows which service added latency. Essential in microservices. Used for performance analysis.

Structured Logging — The Right Way

// ❌ Bad — Unstructured log (hard to query/parse) console.log("User 42 placed order 99 for $29.99 at 14:03:22"); // ✅ Good — Structured JSON log (queryable, parseable) logger.info({ event: "order.created", userId: 42, orderId: 99, amount: 29.99, currency: "USD", timestamp: "2025-01-15T14:03:22Z", traceId: "abc-123-def", // link to distributed trace service: "order-service", severity: "INFO" }); // Search in Kibana/Grafana: event="order.created" AND userId=42 // Alert on: error_rate > 1% in last 5 minutes

The Monitoring Stack — End to End

Key Metrics to Track — Golden Signals

Latency
How long requests take. Track p50, p95, p99 — not just average. p99 = worst experience for 1 in 100 users.
Traffic
How much demand. Requests per second, queries/sec, messages/sec. Baseline traffic to detect anomalies.
Errors
Rate of failed requests. 5xx responses, exceptions, timeouts. Alert when error rate exceeds 1% over 5 min.
Saturation
How full resources are. CPU %, memory %, disk I/O, DB connection pool usage. Signal before you run out.
💡 Distributed Tracing insight: Add a traceId to every log line and HTTP header. When a request spans 5 microservices, you can pull all related logs with a single query: traceId = "abc-123". Without this, debugging takes hours.
🔢 Topic 3 — Distributed Systems
Hashing & Consistent Hashing
Hashing decides which server handles which data. Regular hashing breaks when you add or remove servers — causing massive cache invalidation. Consistent hashing solves this elegantly.

Regular Hashing — The Problem

How it Works (and why it fails)
With N servers, assign request by: server = hash(key) % N. Simple. Works great — until you add or remove a server. Now N changes, and almost every key maps to a different server. All cached data is suddenly on the wrong server → massive cache miss storm.
// Regular hashing — breaks on server change function getServer(key, servers) { const hash = murmurHash(key); // e.g. 1234567 return servers[hash % servers.length]; // modulo N } // With 3 servers: "user:42" → hash=1234567 → 1234567 % 3 = 1 → Server-B // Add 1 server (now 4): "user:42" → 1234567 % 4 = 3 → Server-D ← WRONG! // Every key remaps → 75%+ of cache becomes invalid instantly

Consistent Hashing — The Solution

The Big Idea
Place both servers and keys on a virtual ring from 0 to 2³²-1. Each key is assigned to the next server clockwise on the ring. When a server is added or removed, only the keys that were assigned to that server need to move — typically only K/N keys (K = total keys, N = servers). Everything else stays put.

The Hash Ring — Visual

What Happens When a Server is Added/Removed

➕ Server Added
New server E placed on ring between A and B. Only keys that were going to B (but now fall between A→E) move to E. Typically ~1/N of keys = just 25% with 4 servers. Everything else untouched.
➖ Server Removed
Server B crashes. Its keys now flow to the next clockwise server C. Only B's keys are affected. A, D, and their keys are completely unaffected. Graceful degradation.

Virtual Nodes — Solving Uneven Distribution

The Problem with a Basic Ring
With only 4 servers on the ring, load distribution can be uneven — server A might get 40% of traffic, server C only 15%. Virtual nodes (vnodes) fix this: each physical server gets mapped to multiple positions on the ring (e.g. 150 virtual nodes per server). This distributes load far more evenly. Used by Cassandra, DynamoDB, Riak.
// Consistent hashing with virtual nodes class ConsistentHash { constructor(servers, vnodes = 150) { this.ring = new SortedMap(); servers.forEach(server => this.addServer(server, vnodes)); } addServer(server, vnodes) { for (let i = 0; i < vnodes; i++) { // Each server gets 150 positions on the ring const hash = murmurHash(`${server}:vnode:${i}`); this.ring.set(hash, server); } } getServer(key) { const hash = murmurHash(key); // Find next clockwise position on ring return this.ring.ceilingEntry(hash)?.value ?? this.ring.firstEntry()?.value; // wrap around } }

⚖️ Topic 4 — Distributed Systems
CAP Theorem
CAP Theorem states that a distributed data system can only guarantee 2 of 3 properties simultaneously: Consistency, Availability, and Partition Tolerance. Understanding this shapes every database and distributed system decision.

The Three Properties

🔵
Consistency (C)
Every read receives the most recent write or an error. All nodes see the same data at the same time. No stale reads.
🟢
Availability (A)
Every request receives a non-error response, but it might not be the most recent write. System always responds — even if data is stale.
🟡
Partition Tolerance (P)
System continues operating when some network messages are lost or nodes can't talk to each other (network partition).
The Critical Insight: Network partitions always happen in distributed systems — cables fail, switches drop packets, data centres lose connectivity. P is non-negotiable. Therefore, the real choice is: when a partition occurs, do you sacrifice C or A?

CAP Triangle — Visual

CP vs AP — The Real Choice

CP — Consistency + Partition Tolerance
During a network partition, the system refuses to respond rather than return stale data. Guarantees every read gets the most recent write. May return errors or become unavailable.

Examples: HBase, Zookeeper, etcd, Redis (when configured), MongoDB (default)
Use when: Financial transactions, inventory, user balances — where stale = wrong
AP — Availability + Partition Tolerance
During a partition, the system keeps serving requests even if some nodes have stale data. Always responds — but data might be slightly out of date. Resolves conflicts later (eventual consistency).

Examples: Cassandra, DynamoDB, CouchDB, DNS
Use when: Social feeds, product catalogue, user preferences — where slightly stale is OK

Real-World Scenario — Network Partition

PACELC — The Extended Model

Beyond CAP — What Happens When There's No Partition?
CAP only describes behaviour during a partition. PACELC extends this: even without a partition (the normal state), there's still a tradeoff between Latency (L) and Consistency (C).

PA/EL — Dynamo, Cassandra: available during partition; low latency otherwise
PC/EC — BigTable, HBase: consistent during partition; consistent otherwise
PA/EC — MongoDB: available during partition; consistent otherwise

💡 Interview Answer Framework: "CAP says we can only guarantee 2 of 3. Since network partitions are inevitable in distributed systems, I need to choose between CP and AP. For [payments/inventory] I'd pick CP — I'd rather return an error than show wrong data. For [user feed/preferences] I'd pick AP — eventual consistency is fine and availability matters more."

Do

  • Choose CP for financial data, inventory, user balances
  • Choose AP for social feeds, analytics, recommendations
  • State your CAP choice explicitly in design interviews
  • Know that most modern DBs let you tune consistency level per query
  • Consider PACELC for latency vs consistency in normal operation

Don't

  • Say "I'll use CA" — partitions always happen, CA is theoretical
  • Pick a DB without justifying its consistency model
  • Assume SQL = consistent and NoSQL = eventual (wrong)
  • Ignore eventual consistency lag in AP systems design
  • Use strong consistency everywhere — it costs latency
