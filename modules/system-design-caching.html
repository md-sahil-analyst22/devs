⚡ Foundation — Overview
Caching Deep Dive
Caching is one of the highest-leverage tools in system design. A well-placed cache can reduce database load by 90%, cut latency from 200ms to 1ms, and allow a system to serve 10× more traffic without adding servers.

What is Caching?

The Core Idea
A cache is a fast, temporary storage layer that sits in front of a slower data source (database, API, filesystem). Instead of recomputing or re-fetching expensive data every time, you store the result and serve it from memory. The fundamental tradeoff: speed vs freshness.

Why Cache? — The Numbers

L1 CPU Cache
~1 ns
Inside CPU chip. Tiny (32–64 KB). Fastest store on earth.
RAM / Redis
~100 µs
In-memory. Redis, Memcached. Standard app cache layer.
SSD / DB
~1–10 ms
Disk-backed. Postgres, MySQL. Much slower than RAM.
Network / HDD
~50–200 ms
Remote DB, cold disk. Worst case for a user request.
The Cache Hierarchy Insight: Memory is ~10,000× faster than a network call to a database. Serving a cached response from Redis (0.1ms) vs a DB query (10ms) is a 100× speed improvement — on every single request.

Eviction Policies

LRU — Least Recently Used
Evicts the item that hasn't been accessed the longest. Best general-purpose policy. Default in Redis. Works well for temporal locality.
LFU — Least Frequently Used
Evicts the item accessed fewest times. Keeps "hot" popular items. Better than LRU when access patterns are uneven. Redis 4.0+ supports this.
TTL-Based Expiry
Items expire after a set duration regardless of use. Simple to reason about. Forces refresh. Best for data with natural expiry (sessions, tokens, prices).
Phil Karlton's famous quote: "There are only two hard things in Computer Science: cache invalidation and naming things." — This guide is your complete weapon against both.

How Cache-Aside Works

1
Application checks the cache first
Before touching the database, the app sends a GET user:42 to Redis. This is the "read-through" attempt.
2
Cache HIT → Return data immediately
If Redis has the data, return it directly to the caller. No DB involved. Sub-millisecond response. ✅
3
Cache MISS → Fetch from DB
If Redis returns nil, the application queries the database directly. This is the expensive path.
4
Populate cache, return data
App writes the DB result into Redis with a TTL: SET user:42 <data> EX 3600. Future requests will hit the cache.

Cache-Aside — Flow Diagram

Cache-Aside Code Pattern

async function getUser(userId) { const cacheKey = `user:${userId}`; // ① Check cache first const cached = await redis.get(cacheKey); if (cached) { return JSON.parse(cached); // ② Cache HIT — return immediately } // ③ Cache MISS — query database const user = await db.query('SELECT * FROM users WHERE id = $1', [userId]); // ⑤ Populate cache (TTL = 1 hour) await redis.set(cacheKey, JSON.stringify(user), 'EX', 3600); return user; }

⚖️ Read Caching — Analysis
Read Caching Strategies — Pros & Cons
Every read caching strategy comes with trade-offs. This section gives you the full honest picture so you can confidently choose — and defend your choice in an interview.
1
Cache-Aside (Lazy Loading)
Most widely used

✅ Pros

  • Only requested data is cached — no wasted memory on unused rows
  • Cache failure is non-fatal — app falls back to DB automatically
  • Works with any cache technology (Redis, Memcached, local)
  • Simple to implement — just wrap existing DB calls
  • Full control over TTL per data type
  • Cache can handle different data models than DB

❌ Cons

  • Cold start penalty — first 3 reads always miss (request, cache miss, DB hit)
  • Stale data risk — if DB updated externally, cache serves old data until TTL expires
  • Cache stampede — on cold start, many requests flood DB simultaneously
  • Cache-writing logic scattered through application code
  • Must invalidate cache on write (extra complexity)
2
Read-Through
Framework-managed

✅ Pros

  • Application code is cleaner — no manual cache logic in service layer
  • Cache loading logic is centralized in one place
  • Consistent caching behavior across all code paths
  • Application fully decoupled from the database
  • Easier to test — mock the cache, not the DB

❌ Cons

  • Requires framework support (not just vanilla Redis)
  • Cold start still slow — first-time misses go to DB
  • Less transparent — harder to debug what's hitting DB
  • Cache library becomes a critical dependency
  • Less flexibility for per-request cache decisions

Common Read Caching Problems & Fixes

🚨 Problem: Cache Stampede (Thundering Herd)
When a popular cache key expires, hundreds of concurrent requests all see a miss simultaneously, all query the DB at the same time, and all try to write the same key back. DB gets hammered.
// Solution 1: Mutex Lock — only one thread fetches from DB async function getWithLock(key) { const cached = await redis.get(key); if (cached) return JSON.parse(cached); const lock = await redis.set(`lock:${key}`, '1', 'NX', 'EX', 5); if (!lock) { await sleep(50); // wait, another process is fetching return getWithLock(key); // retry — will hit cache this time } const data = await db.query('...'); await redis.set(key, JSON.stringify(data), 'EX', 3600); await redis.del(`lock:${key}`); return data; } // Solution 2: TTL Jitter — stagger expiry times to avoid mass simultaneous expiry const ttl = 3600 + Math.floor(Math.random() * 300); // 3600 ± 300s await redis.set(key, data, 'EX', ttl);
🔄 Problem: Stale Data
A user updates their profile in the DB. The cache still serves the old name for the next 60 minutes. Classic consistency problem.
Fix 1: Short TTL
Set TTL to 60–300 seconds. Data is slightly stale but self-heals quickly. Simple. Appropriate for non-critical data.
Fix 2: Explicit Invalidation
On every write to DB, also DEL user:42 from cache. Next read will re-populate. Most correct but adds write complexity.
Fix 3: Event-Driven Invalidation
DB emits a change event (via Kafka/CDC). A separate service listens and invalidates/updates cache. Clean separation of concerns.

💡 Interview Answer Template: "I'd use cache-aside (lazy loading) with Redis. On a cache miss, the application fetches from the DB and populates the cache with a TTL appropriate for how frequently the data changes. On writes, I invalidate the cache key immediately to prevent stale reads."

Do

  • Add TTL jitter to prevent stampedes
  • Invalidate cache on every write to DB
  • Monitor cache hit rate — target >90%
  • Use short TTL for user-facing mutable data
  • Consider local in-process cache for hot keys
  • Pre-warm cache after deploy / restart

Don't

  • Cache without a TTL (stale data forever)
  • Cache PII or sensitive data without encryption
  • Ignore cold start — it can break your DB
  • Use the same TTL for all data types
  • Skip monitoring — silent cache misses are invisible

⚖️ Write Caching — Analysis
Write Caching Strategies — Pros & Cons
Write caching is where real consistency vs performance tradeoffs live. Understanding each strategy's failure modes and strengths is essential for system design interviews and production systems.
1
Write-Through
Strong consistency — write to cache + DB atomically

✅ Pros

  • Strong consistency — cache and DB are always in sync after a write
  • No stale data in cache — every read after a write is correct
  • No data loss risk — DB is updated synchronously
  • Simple to reason about — no async complexity
  • Cache is always warm — no cold-start cache misses after writes

❌ Cons

  • Higher write latency — must wait for both cache AND DB to confirm
  • Write penalty on every operation even if data is never read again
  • Cache fills with written-but-never-read data (cache pollution)
  • Higher write traffic — every write hits two systems
  • Not suitable for write-heavy workloads with low read ratios
2
Write-Behind (Write-Back)
Maximum write speed — async DB persistence

✅ Pros

  • Lowest write latency — app gets ACK immediately after cache write
  • Write coalescing — 100 updates to same key = 1 DB write (huge savings)
  • DB protected from write spikes — queue absorbs burst traffic
  • Massive write throughput possible
  • Works well with batch DB operations

❌ Cons

  • Data loss risk — if cache fails before async flush, writes are gone
  • Complex implementation — need reliable write queue, retry logic, idempotency
  • Eventual consistency — DB lags behind cache
  • Hard to recover from partial failures
  • Not suitable where data durability is non-negotiable (finance, medical)
3
Write-Around
Skip cache on write — prevents pollution

✅ Pros

  • No cache pollution — cache only holds frequently-read data
  • Good for write-once, rarely-read data (logs, audit trails)
  • Simple — writes are just DB writes, no cache logic needed
  • Cache stays focused on hot data — better hit rate
  • Lower memory usage in cache for high-write workloads

❌ Cons

  • High read miss after write — first read of newly written data always misses cache
  • Slow initial reads for recently written data
  • Inconsistency window between cache and DB
  • Not suitable when written data is read back immediately
  • Must combine with read cache strategy (Cache-Aside)

Combining Strategies — Real Architecture

🏗️ Production Pattern: E-Commerce Platform
Real systems mix strategies per data type:

Product catalog → Write-Through — price/stock changes must be immediately consistent in cache
User cart & sessions → Write-Through — cannot lose cart data, reads are frequent
View counts, likes, clicks → Write-Behind — high throughput, eventual consistency is fine
Order records, audit logs → Write-Around — write once, rarely re-read, don't pollute cache

Write-Behind Deep Dive: Implementation

// Write-Behind with Redis List as durable write queue async function updateUserProfile(userId, data) { const key = `user:${userId}`; // ① Write to cache immediately (instant ACK to caller) await redis.set(key, JSON.stringify(data), 'EX', 3600); // ② Enqueue for async DB flush (durable queue) await redis.lpush('write-queue', JSON.stringify({ table: 'users', id: userId, data, timestamp: Date.now() })); return { success: true }; // Respond before DB write! } // Background worker flushes queue to DB async function flushWorker() { while (true) { const item = await redis.brpop('write-queue', 0); // blocking pop const { table, id, data } = JSON.parse(item[1]); await db.query( `UPDATE ${table} SET data = $1 WHERE id = $2`, [data, id] ); } }
⚠️ Write-Behind Data Loss Scenario: If Redis crashes after writing to cache but before the background worker flushes to DB, those writes are lost. Mitigation: use Redis Persistence (AOF mode), a durable queue like Kafka, or ensure at-least-once delivery with idempotent DB writes.

💡 Interview Answer Template: "For this system I'd use Write-Through for [user data / product catalog] since reads are frequent and consistency is critical. For [counters / analytics events], I'd use Write-Behind to absorb the write spike and flush asynchronously — accepting eventual consistency there is fine."

Do

  • Match write strategy to each data type separately
  • Use Write-Behind only with a durable queue (Kafka, not memory)
  • Make Write-Behind workers idempotent (retry-safe)
  • Monitor write queue depth — backup = alarm
  • Test cache failure scenarios in staging
  • Use transactions where cache + DB must be atomic

Don't

  • Use Write-Behind for financial/medical data
  • Forget to invalidate cache after Write-Around
  • Apply one strategy to all data types blindly
  • Skip error handling in async write workers
  • Ignore the write queue as a single point of failure
