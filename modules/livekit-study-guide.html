What is LiveKit?

LiveKit is an open-source, full-stack real-time communication platform built for the AI era. It wraps WebRTC — the browser-native protocol for real-time audio/video — into a manageable, scalable abstraction that works across every platform and powers AI voice agents, video calls, and everything in between.

The two things LiveKit is

1. A real-time media server (SFU)
LiveKit Server is a Selective Forwarding Unit — it routes audio/video between participants in a room. Built in Go for extreme performance. Handles WebRTC signaling, ICE negotiation, NAT traversal, codec negotiation, simulcast, adaptive bitrate, and QoS so you don't have to.
2. An AI agents framework
LiveKit Agents is a Python/Node.js framework for building AI participants that join rooms. Agents can speak, listen, process video, and connect to any AI provider. The framework handles the STT→LLM→TTS pipeline, turn detection, interruption, and multi-agent coordination.
The core insight: Traditional HTTP was never designed for real-time media. WebRTC solves that but is extremely complex to operate. LiveKit wraps WebRTC into an abstraction as simple as joining a "room" — and adds AI-first capabilities that no other platform offers out of the box.

Module 5 · WebRTC Foundations

WebRTC Fundamentals

WebRTC (Web Real-Time Communication) is the browser-native technology for peer-to-peer audio, video, and data. LiveKit is built on top of it. Understanding WebRTC helps you understand why LiveKit exists and how it works.

The WebRTC stack does 4 things: (1) Discovers a network path between peers (ICE), (2) Negotiates media capabilities (SDP), (3) Encrypts the connection (DTLS), (4) Transmits encrypted media (SRTP). Each step has significant complexity — LiveKit automates all of it.

WebRTC connection establishment process

1
SDP Offer — "Here's what I can do"
Peer A creates an SDP (Session Description Protocol) document listing: which codecs it supports (Opus, VP8, H264), what audio/video formats, bitrate constraints, and its ICE credentials. Sends to Peer B via signaling (WebSocket).
2
SDP Answer — "Here's what I can do too"
Peer B creates an SDP answer with its capabilities. The intersection of both SDPs defines what will actually be used. Sends back to Peer A via signaling. Now both know what to send.
3
ICE candidate gathering — "Here's how to reach me"
Each peer gathers ICE candidates — possible network addresses: local IP (host), public IP via STUN (server-reflexive), TURN relay address (relayed). Exchange via signaling. Try each until one works.
4
DTLS handshake — encrypted channel
Once a working ICE candidate pair is found, DTLS (Datagram TLS) handshake establishes encryption. Certificates are exchanged and verified. Shared secret established for SRTP.
5
SRTP streams — media flows
Audio and video encrypted with SRTP (Secure Real-time Transport Protocol) flow between peers. In LiveKit's case, all peers send to the SFU server, which routes to other participants.

SFU vs MCU vs P2P

Three architectures for multi-party real-time communication. LiveKit uses SFU. Understanding the difference explains why SFU is the right choice for most production applications.

P2P — Peer-to-Peer (mesh)

Direct browser-to-browser connections
Each participant connects to every other participant directly. 4 participants = 6 connections. 10 participants = 45 connections. N participants = N*(N-1)/2 connections.

Upload bandwidth grows exponentially. With 5 people, each browser uploads 4 streams. At HD video (2 Mbps each), that's 8 Mbps upload — impossible on most home connections. P2P breaks at ~4 participants.

SFU — Selective Forwarding Unit (LiveKit)

← encrypted →
💻 Desktop C
downloads 2 streams

downloads 3 streams
Each participant uploads ONCE. SFU forwards to all others. Bandwidth scales linearly, not exponentially.

MCU — Multipoint Control Unit

Server mixes all streams into one
The server receives all streams, decodes them, mixes video/audio into a single composite stream, and sends one stream to each participant — just like a Zoom gallery view rendered on the server.

Pros: Each participant downloads only 1 stream regardless of participant count. Works on very slow connections.
Cons: Massive server-side compute (decoding + re-encoding all streams). High latency from transcoding. Very expensive to run.

ICE, STUN & TURN

The network traversal layer of WebRTC. The hardest part. LiveKit handles all of this for you — but understanding it helps you debug connectivity issues.

The NAT problem

Why NAT traversal is hard: Most devices are behind NAT routers — they have a private IP (192.168.x.x) but share a public IP. Direct connections are impossible without knowing the public IP and the mapped port. This is what ICE, STUN, and TURN solve.

ICE — Interactive Connectivity Establishment

ICE is the overall framework. It gathers all possible ways to reach a peer (candidates) and tries them in priority order until one works. Types of ICE candidates:

Host candidate (best)
Direct local IP address. Works when both peers are on the same network. No external server needed.
Server-reflexive candidate (STUN)
Public IP + port as seen by a STUN server. Works in ~85% of cases. Requires outbound UDP.
Relayed candidate (TURN) — last resort
All media relayed through TURN server. Works in all cases including symmetric NAT and corporate firewalls. Adds latency and cost.

STUN vs TURN comparison

STUN (Session Traversal Utilities for NAT)

  • Helps peer discover its public IP and port
  • Server just reflects your IP back ("here's your public address")
  • Minimal bandwidth — just for discovery
  • Free: stun.l.google.com:19302
  • Fails with symmetric NAT (strict corporate firewalls)
  • Works for ~85% of connections

    • TURN (Traversal Using Relays around NAT)

  • Relay server — all media flows through it
  • Required when direct path fails (~15% of connections)
  • High bandwidth cost — relays all audio/video
  • Works in every network environment
  • LiveKit Cloud provides TURN automatically
  • Self-hosting: needs coturn or Pion TURN
    • LiveKit Cloud = free STUN + TURN included. You never configure STUN/TURN manually. When self-hosting, LiveKit bundles a TURN server or you can point it to your own. The LIVEKIT_TURN_* env vars configure this.

    SDP & Signaling

    SDP is the document that describes what a peer wants to send and receive. Signaling is the exchange of SDPs and ICE candidates. LiveKit uses a custom signaling protocol over WebSocket — you never write SDP directly.

    What SDP looks like (simplified)

    LiveKit Rooms

    A Room is the fundamental unit of LiveKit. It's a virtual space where participants communicate. Rooms are created on demand, expire when empty, and are identified by a unique name within your LiveKit project.

    Room lifecycle

    1
    Room creation (explicit or implicit)
    Rooms can be pre-created via REST API with specific settings, or they're created automatically when the first participant joins. Pre-creating allows you to configure max participants, codec preferences, and recording.
    2
    Participants join with access tokens
    Each participant joins with a JWT access token that specifies their identity, permissions (can publish audio/video?), and the room name. The token is generated server-side and sent to the client.
    3
    Media flows between participants via SFU
    Published tracks are forwarded to all subscribers. Events propagate to all participants (participant joined, track published, metadata updated).
    4
    Room expires when last participant leaves
    By default, rooms auto-delete when empty. You can configure empty_timeout to keep rooms alive for a period after all participants leave (useful for recordings to complete).

    Creating and managing rooms via API

    # Python Server SDK — room management from livekit import api import asyncio async def manage_rooms(): lk = api.LiveKitAPI( url="https://your-project.livekit.cloud", api_key="your_api_key", api_secret="your_api_secret" ) # Create room with configuration room = await lk.room.create_room(api.CreateRoomRequest( name="meeting-room-123", max_participants=20, empty_timeout=300, # 5 min before auto-delete when empty metadata='{"type": "customer_call"}' )) # List active rooms rooms = await lk.room.list_rooms(api.ListRoomsRequest()) # Get participants in a room participants = await lk.room.list_participants( api.ListParticipantsRequest(room="meeting-room-123") ) # Remove a participant await lk.room.remove_participant(api.RoomParticipantIdentity( room="meeting-room-123", identity="user_456" )) # Delete a room (disconnects all participants) await lk.room.delete_room(api.DeleteRoomRequest(room="meeting-room-123")) await lk.aclose()

    Room state — what a room knows

    Room properties
    Name, SID (unique ID), creation time, participant count, metadata (your custom JSON string), active recording flag, active egress flag.
    Room settings
    Max participants, empty_timeout, codec preferences (force VP8, H264, etc.), audio/video presets, DTLS certificate, egress settings.
    Participants list
    All connected participants (human + agents). Each has identity, name, metadata, permissions, published tracks, connection quality.
    Data channels
    Reliable (TCP-like) and lossy data channels for custom messages. Used for chat, cursor positions, state sync — any non-media data.

    Participants — Who's in the Room

    A participant is anyone (human or AI agent) connected to a room. LiveKit distinguishes between local participants (you), remote participants (others), and tracks they publish or subscribe to.

    Participant types

    Human participant
    A browser, mobile app, or desktop app connected via a client SDK. Has a camera, microphone, and screen share. Receives video/audio from others. Controlled by the user.
    AI Agent participant
    A programmatic participant running on your server. Publishes synthesized speech (TTS), subscribes to user audio (for STT), processes video, and sends data messages.

    A virtual participant that joins only to record or stream. Subscribes to all tracks and sends to S3, YouTube, Mux, etc. No publishing.

    Tokens & Authentication

    LiveKit uses JWT access tokens for authentication. Every participant joining a room must present a valid token signed with your API secret. Tokens are always generated server-side — never in client code.

    Token structure — what's inside

    # JWT payload claims (decoded) { # Standard JWT claims "iss": "your_api_key", ← your API key (issuer) "sub": "user_alice", ← participant identity "iat": 1705000000, ← issued at (unix timestamp) "exp": 1705006000, ← expires (1 hour later) "nbf": 1705000000, ← not valid before # LiveKit-specific claims "name": "Alice Smith", ← display name "metadata": "{...json...}", ← custom JSON metadata "sha256": "...", ← metadata hash (integrity) # Video grants (permissions) "video": { "roomCreate": false, ← can create rooms "roomJoin": true, ← can join this room "room": "meeting-room-123", ← which room "canPublish": true, "canSubscribe": true, "canPublishData": true, "canUpdateMetadata": false, "hidden": false, "recorder": false, "agent": false } }

    Token generation (Python)

    from livekit import api from datetime import timedelta import os def create_room_token( room_name: str, identity: str, display_name: str = "", is_admin: bool = False, can_publish: bool = True, metadata: dict = None ) -> str: token = api.AccessToken( api_key=os.getenv("LIVEKIT_API_KEY"), api_secret=os.getenv("LIVEKIT_API_SECRET") ) token.with_identity(identity) token.with_name(display_name or identity) token.with_ttl(timedelta(hours=1)) if metadata: token.with_metadata(json.dumps(metadata)) token.with_grants(api.VideoGrants( room_join=True, room=room_name, can_publish=can_publish, can_subscribe=True, can_publish_data=True, room_admin=is_admin, hidden=False, )) return token.to_jwt() # FastAPI endpoint that generates tokens @app.post("/api/livekit/token") async def get_room_token(room_name: str, user = Depends(get_current_user)): token = create_room_token( room_name=room_name, identity=user.id, display_name=user.name, metadata={"user_id": user.id} ) return {"token": token, "ws_url": os.getenv("LIVEKIT_URL")}
    Security rule: Never generate tokens in frontend code. The API secret must never leave your server. The token is the only thing sent to the client — it contains just enough permissions for that specific user in that specific room.

    LiveKit Agents Framework

    The Agents framework is LiveKit's most powerful feature. It lets you build AI participants that join rooms and interact with humans using voice, video, and data. It handles all the complexity of real-time AI pipelines.

    What makes Agents special: An agent is a LiveKit participant that runs Python/Node.js code server-side. It hears what humans say (via STT), thinks (via LLM), speaks back (via TTS), and can process video — all with built-in turn detection, interruption handling, and sub-500ms end-to-end latency.

    Agent types

    VoicePipelineAgent
    The standard voice agent. Orchestrates the STT → VAD → LLM → TTS pipeline explicitly. You configure each component separately. Full control over each step. Best for production voice agents where you need custom behavior.
    MultimodalAgent
    Uses a multimodal model (like GPT-4o Realtime) that natively handles audio without separate STT/TTS steps. Lower latency, more natural conversation. The model does everything — audio in, audio out. Best for cutting-edge conversational AI.

    Agent worker — the deployment unit

    How job dispatching works

    1
    Worker connects to LiveKit Server
    Your agent process connects to LiveKit Server and registers as a worker. It's idle, waiting for jobs. Multiple workers can register for load balancing.
    2
    Job dispatch triggered
    When a participant joins a room (or you manually dispatch via API), LiveKit sends a job to an available worker. Default: trigger on first participant join. Custom: trigger via dispatch API.
    3
    Worker spawns agent process
    Worker spawns a subprocess (or async task) running your entrypoint function. The agent connects to the room as a participant with its own identity and token.
    4
    Agent runs, handles the conversation
    Agent subscribes to audio, runs the pipeline, publishes responses. When the room is empty or job ends, agent cleans up and worker becomes available for new jobs.

    VAD & Turn Detection

    Voice Activity Detection (VAD) determines when a user is speaking. Turn detection determines when they've finished speaking and the agent should respond. Getting this right is critical for natural conversation flow.

    VAD — Voice Activity Detection

    What VAD does
    VAD analyzes the incoming audio stream and classifies each frame as "speech" or "silence/noise." This controls when the STT model processes audio and when the agent should start responding. LiveKit uses Silero VAD — a small, fast neural network that runs locally (no API calls).
    # Silero VAD configuration vad = silero.VAD.load( min_speech_duration=0.05, # 50ms - how long before classifying as speech min_silence_duration=0.55, # 550ms of silence = speech ended prefix_padding_duration=0.5, # include 500ms before speech start max_buffered_speech=60, # max 60 seconds of buffered speech activation_threshold=0.5, # 0-1, higher = less sensitive )

    Turn detection — when to respond

    Turn detection goes beyond VAD — it uses semantic understanding to know if the user is done with their thought, or just pausing mid-sentence.

    Silence-based (VAD only)
    Respond after N seconds of silence. Simple but can be wrong. "I want to book a... um... flight to London" — the agent responds at the pause. Too aggressive.
    Turn detection model
    A small model that reads the transcription and predicts "done speaking" vs "mid-thought." More accurate. LiveKit provides a trained turn detector plugin. Reduces false positives significantly.
    # Using the built-in turn detector from livekit.plugins import turn_detector agent = VoicePipelineAgent( vad=silero.VAD.load(), stt=deepgram.STT(), llm=openai.LLM(), tts=openai.TTS(), turn_detector=turn_detector.EOUModel(), # End-of-utterance model min_endpointing_delay=0.5, # wait 500ms after VAD silence max_endpointing_delay=6.0, # max 6s even if model unsure )

    Takes a screenshot/recording of any URL in a headless browser and injects it into a room. Use for recording any web-based view or custom layout.
    RTMP Egress
    Streams the room live to YouTube, Twitch, Mux, Cloudflare Stream, or any RTMP destination. For interactive livestreaming.

    Ingress — Bring External Media In

    Pull media from an HTTP URL (MP4, HLS, DASH). Play a video file into a room. Good for pre-recorded content, intros, or background media.

    Secure Reliable Transport. Used by broadcast-grade equipment. Low latency, high reliability for professional video production.

    Security Best Practices

    LiveKit is built on encrypted WebRTC (DTLS-SRTP) so media is always encrypted. The main security concerns are token management, API key protection, and webhook verification.

    Always do

  • Generate tokens server-side only — never in frontend
  • Store API key + secret in env vars / Azure Key Vault
  • Set short TTL on tokens (1 hour max)
  • Verify webhook signatures with WebhookReceiver
  • Use Nginx IP allowlist for webhook endpoints
  • Set room-specific permissions (canPublish per user)
  • Use HTTPS for all token delivery endpoints
  • Set max_participants on rooms to prevent abuse
  • Rotate API keys periodically

    • Never do

  • Put LIVEKIT_API_SECRET in client JavaScript
  • Accept webhooks without signature verification
  • Issue tokens with roomAdmin=true to regular users
  • Use * for CORS origins in production
  • Log full JWT tokens in application logs
  • Issue tokens valid for more than 24 hours
  • Commit .env files with API keys to git

    • Token scoping — minimal permissions

    Operations · Troubleshooting

    Troubleshooting Guide

    Common problems and exactly how to fix them.

    Agent joins room but user can't hear it +
    Check 1: Is the agent actually publishing audio? Add @agent.on("agent_speech_started") log — if it fires, TTS is working.

    Check 2: Did the user subscribe to the agent's audio track? In the JS SDK, check room.remoteParticipants — is the agent there? Is its audio track subscribed?

    Check 3: Is the token correct? The agent's token must have can_publish=True. The user's token must have can_subscribe=True.

    Check 4: Browser autoplay policy. Chrome blocks autoplay. You must call track.attach() after a user gesture (button click), or call room.startAudio() on user interaction.
    STT not transcribing / transcription is wrong +
    Check 1: Is VAD detecting speech? Add @agent.on("user_started_speaking") log. If it never fires, VAD isn't detecting audio — check audio track is subscribed with auto_subscribe=AutoSubscribe.AUDIO_ONLY.

    Check 2: Is the Deepgram/STT API key valid? Check agent logs for STT connection errors.

    Check 3: Is audio quality poor? Try lowering activation_threshold in VAD config. Check for background noise — use noise cancellation plugin.

    Check 4: STT language mismatch. Set language="en-US" explicitly in Deepgram STT config.
    High latency — agent responds slowly +
    Reduce VAD silence threshold: min_silence_duration=0.3 (default 0.5). Agent starts processing sooner.

    Enable preemptive synthesis: preemptive_synthesis=True starts TTS while LLM is still generating. Saves 200-400ms.

    Use faster LLM: GPT-4o mini < GPT-4o. Claude Haiku < Sonnet. Groq (Llama) is fastest at ~600 tokens/sec.

    Use faster TTS: Cartesia Sonic (~50ms) > ElevenLabs (~150ms) > OpenAI TTS (~200ms).

    Use faster STT: Deepgram Nova-2 streaming is ~100ms. Avoid batch Whisper (~500ms).
    Webhook signature verification failing (403 errors) +
    Check 1: Are you reading the raw bytes before parsing JSON? You must pass raw bytes to WebhookReceiver, not parsed JSON.

    Check 2: Is the Authorization header being forwarded by Nginx? Some Nginx configs strip authorization headers. Add proxy_set_header Authorization $http_authorization;.

    Check 3: Are the API key/secret in WebhookReceiver the same as the LiveKit server configuration? If testing locally with a different LiveKit project, keys must match.
    Agent process crashes / restarts unexpectedly +
    Check logs: The agent framework logs errors before shutdown. Add logging.basicConfig(level=logging.DEBUG) to see all output.

    Wrap entrypoint in try-except: Unhandled exceptions kill the process. Add a global exception handler and log it before re-raising.

    API key limits: OpenAI rate limits cause HTTP 429 errors which crash the agent. Add retry logic or use max_retry=3 in WorkerOptions.

    Memory leaks: Ensure await agent.aclose() is called when the room ends. Otherwise each job leaks memory.
    Room not auto-dispatching agent when participant joins +
    Check 1: Is the worker running and connected to the LiveKit server? Check worker process logs — it should say "Connected to LiveKit server".

    Check 2: Agent dispatch requires LiveKit Server 1.7+ or LiveKit Cloud. Older servers don't support auto-dispatch.

    Check 3: For explicit dispatch, you must call lk.agent.create_agent_dispatch() from your backend when a user starts a call. The worker won't auto-join unless configured for that.

    Manual workaround: Use the dispatch API from your FastAPI backend when the user clicks "Start Call".
