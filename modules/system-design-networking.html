🌐 Topic 1 — Foundations
IP Address
An IP address is the fundamental addressing system that lets devices find and communicate with each other across networks. Every device on the internet has one.

What is an IP Address?

Definition
An IP (Internet Protocol) address is a unique numerical label assigned to every device connected to a computer network. Think of it like a home address — it tells the network exactly where to deliver data packets.
IPv4
32-bit address written as 4 octets. Example: 192.168.1.1. Supports ~4.3 billion unique addresses. Now mostly exhausted.
IPv6
128-bit address written in hex. Example: 2001:0db8::1. Supports 340 undecillion addresses. The long-term solution.

How it Works — Diagram

Why it Matters in System Design

  • Routing — routers use IP addresses to forward packets hop-by-hop toward the destination.
  • Private vs Public IPs — private IPs (10.x, 172.x, 192.168.x) are used inside networks; NAT maps them to a public IP for internet access.
  • Static vs Dynamic — servers use static IPs; home devices get dynamic IPs via DHCP.
  • Subnetting — large networks split into subnets using a subnet mask. Essential for VPC design in cloud.

🔍 Topic 2 — Foundations
DNS — Domain Name System
DNS is the internet's phone book. It translates human-readable domain names like google.com into machine-readable IP addresses like 142.250.80.46.

What is DNS?

The Big Idea
Humans remember github.com. Computers need 140.82.121.4. DNS is the distributed system that bridges this gap — performing the lookup billions of times per day, globally.

DNS Resolution — Step by Step

1
Browser Cache Check
Browser checks its own DNS cache. If github.com was visited recently and the TTL hasn't expired, uses the cached IP immediately.
2
OS / Recursive Resolver
OS checks its cache, then asks your ISP's recursive resolver (or 8.8.8.8 if using Google DNS). The resolver does the heavy lifting.
3
Root Name Server
The recursive resolver asks one of 13 root server clusters. The root doesn't know the IP — but it knows who manages .com TLDs.
4
TLD Name Server
The .com TLD server points to GitHub's authoritative nameserver.
5
Authoritative Name Server
GitHub's authoritative nameserver finally returns the actual IP address. The resolver caches it for the TTL duration and returns it to your browser.

⚡ TTL Matters: DNS records have a TTL (Time-to-Live) in seconds. Low TTL = faster propagation but more DNS queries. High TTL = fewer queries but slow to update. During a server migration, lower TTL first.

Do

  • Use CDN with Anycast DNS for global performance
  • Lower TTL before a migration, raise after
  • Use health checks with DNS failover
  • Understand split-horizon DNS for internal/external

Don't

  • Hardcode IP addresses in code (use DNS)
  • Set TTL=0 in production (hammers servers)
  • Rely on DNS alone for failover speed
  • Forget DNS propagation delay during deploys
🖥️ Topic 3 — Foundations
Client & Server
The client-server model is the backbone of the internet. Understanding this split — who requests, who responds — is step one in every system design interview.

The Model

🖱️ Client
The requester. Initiates communication. Examples: browser, mobile app, CLI tool, another server. A client says "give me X".
🗄️ Server
The responder. Listens for requests, processes them, returns data. Examples: web server, API server, database. A server says "here is X".

Request-Response Cycle

Types of Clients

Thin Client
Minimal local processing. Relies heavily on the server. Example: web browser rendering HTML from server. Low compute cost on the client side.
Thick Client
Does heavy processing locally. Desktop apps, mobile apps, games. Server mainly stores data. Faster UX but harder to update.
Server as Client
A server can be a client to another server. Microservices call each other. Your API calls Stripe's API — your server is the client there.

Stateful vs Stateless Servers

Stateful
Server remembers client state between requests. Example: WebSocket connections, gaming servers. Harder to scale horizontally.
Stateless
Each request is self-contained with all info needed. Example: REST APIs with JWT tokens. Easy to scale — any server can handle any request.
System Design Principle: Prefer stateless servers for horizontal scalability. Move state to a shared layer (Redis, DB) instead of keeping it in server memory. This lets you spin up any number of server instances behind a load balancer.
📡 Topic 4 — Protocols
Protocols — Introduction
A protocol is a set of rules that governs how data is transmitted between devices. Without agreed-upon protocols, devices couldn't communicate reliably.

What is a Protocol?

Definition
A protocol defines the format, order, and meaning of messages exchanged between communicating entities. It's a contract: "if you send data in this exact format, I'll understand it."

The OSI Model — 7 Layers

Layer 7 — Application
Protocols: HTTP, HTTPS, FTP, SMTP, DNS, WebSocket. What you use in code.
Layer 6 — Presentation
Encryption (TLS/SSL), compression, encoding (JSON → binary). Data formatting.
Layer 5 — Session
Manages sessions between applications. Authentication, reconnection.
Layer 4 — Transport
Protocols: TCP, UDP. Handles ports, segmentation, reliability (TCP) or speed (UDP).
Layer 3 — Network
Protocols: IP, ICMP. Logical addressing and routing between networks.
Layer 2 — Data Link
Protocols: Ethernet, WiFi (802.11). MAC addresses, frames, switching.
Layer 1 — Physical
Bits over wire, fiber optic, or radio waves. Cables, hubs, repeaters.
Interview shortcut: You mainly care about layers 3 (IP), 4 (TCP/UDP), and 7 (HTTP/WebSocket) in system design. Know which protocol lives at which layer.

🔗 Topic 5 — Transport Protocol
TCP — Transmission Control Protocol
TCP is the reliable, ordered, connection-oriented transport protocol. It's the foundation of HTTP and most internet communication where data integrity matters.

Key Characteristics

✅ Reliable
Every packet is acknowledged. If no ACK received, sender retransmits. Data is guaranteed to arrive.
🔢 Ordered
Packets are numbered with sequence numbers. Receiver reorders them. Data arrives in the exact order sent.
🔌 Connection-Based
Must establish a connection (3-way handshake) before data flows. More overhead but ensures both sides are ready.

TCP 3-Way Handshake

TCP Flow Control & Congestion Control

Flow Control (Window Size)
Receiver tells sender how much buffer space it has (window size). Sender won't exceed this. Prevents receiver from being overwhelmed.
Congestion Control (Slow Start)
TCP starts sending slowly, doubles window each RTT until loss detected, then backs off. Prevents network congestion.

Use Cases

  • HTTP/HTTPS — all web traffic uses TCP. Every request guarantees complete, ordered data.
  • Email (SMTP, IMAP) — emails must arrive in full and in order.
  • File Transfer (FTP, SSH) — missing a byte would corrupt the file.
  • Databases — queries and transactions must be perfectly reliable.
⚠️ TCP Overhead: The 3-way handshake adds latency. HTTPS adds TLS handshake on top. For latency-critical, loss-tolerant apps (gaming, video streaming), TCP overhead is why UDP is preferred.
⚡ Topic 6 — Transport Protocol
UDP — User Datagram Protocol
UDP is the fast, connectionless transport protocol. It sacrifices reliability for speed — perfect when a dropped packet is better than a delayed one.

Key Characteristics

⚡ Fast
No handshake, no ACK, no retransmit. Just send. Much lower latency than TCP for the same network conditions.
❌ Unreliable
Packets may be lost, arrive out of order, or be duplicated. No delivery guarantee. App must handle this if needed.
📤 Connectionless
No connection established. Each datagram is independent. Can send to multiple destinations easily (broadcast/multicast).

Where UDP Wins

🎮 Online Gaming
A stale position update is useless. Better to drop it than retransmit. Games use UDP with custom reliability on top.
📹 Video Streaming
A dropped video frame causes a glitch, not corruption. WebRTC uses UDP. A retransmit would cause worse stuttering.
📡 DNS Queries
Simple request-response. Small payload. If no reply, client just resends. No need for a TCP connection setup overhead.
📞 VoIP / Video Calls
Skype, Zoom, WhatsApp calls use UDP. A 20ms audio gap sounds better than a 200ms retransmit delay.
QUIC Protocol: Modern HTTP/3 is built on QUIC, which runs over UDP but adds reliability, ordering, and multiplexing at the application layer — getting the best of both worlds. Used by Google since 2013.
🌍 Topic 7 — Application Protocol
HTTP — HyperText Transfer Protocol
HTTP is the foundation of data communication on the web. Every time you visit a website or call an API, HTTP is the language being spoken between client and server.

HTTP Request Structure

GET /api/users/42 HTTP/1.1 Host: api.example.com Accept: application/json Authorization: Bearer eyJhbGci... User-Agent: Mozilla/5.0

HTTP Response Structure

HTTP/1.1 200 OK Content-Type: application/json Cache-Control: max-age=3600 X-Request-Id: abc-123 { "id": 42, "name": "Alice", "email": "alice@example.com" }

🔄 Topic 8 — Application Protocol
WebSocket
WebSocket enables full-duplex, persistent communication over a single TCP connection. The server can push data to clients anytime — no polling needed.

HTTP vs WebSocket

HTTP (Request-Response)
Client asks → Server answers → Connection closes (or reused briefly). Server can NEVER initiate. For live data you must poll: GET /updates every second. Wasteful.
WebSocket (Full-Duplex)
Connection stays open. Server can send messages anytime. Client can send anytime. Both directions simultaneously. One long-lived TCP connection.

WebSocket Handshake

// 1. Client sends an HTTP Upgrade request GET /chat HTTP/1.1 Host: ws.example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZS... Sec-WebSocket-Version: 13 // 2. Server accepts the upgrade HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBi... // 3. Now it's a raw TCP pipe — HTTP is done

WebSocket Lifecycle Diagram

When to Use WebSocket

✅ Good Fit
Chat apps · Live dashboards · Collaborative editing (Google Docs) · Online gaming · Stock price tickers · Live sports scores
❌ Not a Fit
Standard REST APIs · One-time requests · Infrequent updates (use Server-Sent Events) · File uploads · Static content
Scaling WebSockets: WebSockets are stateful — a client is connected to ONE server. To scale horizontally, use a pub/sub broker (Redis, Kafka) so any server can push to any client. This is the key design insight.

Do

  • Use Redis Pub/Sub to broadcast across server instances
  • Implement heartbeat/ping-pong to detect dead connections
  • Reconnect with exponential backoff on client side
  • Namespace connections by rooms/channels

Don't

  • Store connection state only in server memory
  • Use WebSocket for simple request-response patterns
  • Forget authentication on the WebSocket handshake
  • Send unbounded data without flow control
🔀 Topic 9 — Infrastructure
Forward Proxy & Reverse Proxy
Proxies sit in the middle of communication. A forward proxy acts on behalf of clients. A reverse proxy acts on behalf of servers. Different direction, different purpose.

Forward Proxy

What it is
A forward proxy sits between a client and the internet. The server sees the proxy's IP, not the client's. The client explicitly configures it. Used for anonymity, content filtering, caching, and bypassing restrictions.
Anonymity
Client's real IP is hidden from the destination. Used by VPNs, Tor, corporate privacy tools.
Content Filtering
Corporations route employee traffic through a forward proxy to block social media or malicious sites.
Caching
Shared cache of responses for many clients. If 100 users visit the same site, proxy serves it from cache once.

Reverse Proxy

What it is
A reverse proxy sits between the internet and your servers. The client sees the proxy's IP, not the server's. The client has no idea multiple servers may be behind it. Used for load balancing, SSL termination, caching, and DDoS protection.

What a Reverse Proxy Does

  • Load Balancing — distributes incoming requests across multiple backend servers using round-robin, least-connections, or IP-hash strategies.
  • SSL/TLS Termination — handles HTTPS at the proxy. Backend servers communicate over plain HTTP internally, reducing their CPU load.
  • Caching — stores responses and serves them without hitting the backend. Nginx and Varnish do this excellently.
  • DDoS Protection — absorbs and filters malicious traffic before it reaches your servers. Cloudflare is a global reverse proxy.
  • Compression — gzip/brotli responses before sending to clients, reducing bandwidth.
  • Rate Limiting — enforce request limits per IP/user at the proxy level before requests even reach your app.

💡 In System Design Interviews: When asked to design any large-scale system, always mention a reverse proxy / load balancer as the entry point. Nginx or an AWS Application Load Balancer in front of your fleet is expected. Explain SSL termination and horizontal scaling.

Do

  • Use a reverse proxy as the single entry point
  • Terminate TLS at the proxy (not app servers)
  • Configure health checks on backend servers
  • Enable response caching at the proxy layer
  • Rate-limit at the proxy before reaching app code

Don't

  • Expose backend server IPs publicly
  • Skip the proxy layer "to reduce latency" (wrong)
  • Handle TLS in every individual app server
  • Ignore sticky sessions for stateful backends
  • Forget logging access at the proxy level
