◧ Topic 1 · Foundations
UML Overview
UML (Unified Modeling Language) is a standard visual notation for designing software before you build it. It gives every engineer a shared vocabulary — a box, an arrow, and a diamond mean the same thing to everyone. In interviews and design docs, it's how you communicate structure and behavior without writing a single line of code.

Why UML Still Matters

The Core Idea
Code shows how a system works line by line. UML shows what the pieces are and how they interact — at a glance. A single class diagram can capture what would take 500 lines of code to read. It's the blueprint you draw before the house, and the map you hand a new teammate on day one.

The Two Families of Diagrams

Structural vs Behavioral — The Mental Model

Structural = a photo
Freezes the system in time. What classes exist, what they contain, and how they connect. Nothing moves. Best example: the Class Diagram.
Behavioral = a video
Shows the system in motion. Who talks to whom, in what order, and how state changes over time. Best examples: Sequence and State Machine diagrams.

Which Diagram For Which Question

You want to answer…Reach forFamily
What are the classes and how do they relate?Class DiagramStructural
What can each user do with the system?Use Case DiagramBehavioral
In what order do objects call each other?Sequence DiagramBehavioral
What is the step-by-step workflow / logic?Activity DiagramBehavioral
What states can one object be in?State MachineBehavioral
Interview reality: you almost never need all 14. A strong LLD answer is usually one class diagram (structure) plus one sequence diagram (a key flow). Master those two first — the rest are situational.

The Shapes You'll See Everywhere

Before diving in, memorise this visual alphabet. Once you can name every shape and line on sight, you can read any UML diagram — even ones for diagram types this guide doesn't cover. Print this page; it's your decoder ring.

Four connector families cover almost everything: a plain line (relationship exists), a diamond (whole/part — hollow=weak, filled=strong), a triangle (type hierarchy — solid=extends, dashed=implements), and an arrow (direction/flow — filled=call, open=return/dependency). Everything else is a label.
▣ Topic 2 · Structural
Class Diagram
The class diagram is the backbone of object-oriented design. It shows the classes in a system, what data and behavior each holds, and how they connect. If you learn one UML diagram deeply, make it this one — it's the direct blueprint for your code.

Anatomy of a Class

Three Compartments, Top to Bottom
A class is a box split into three stacked sections: the name on top, the attributes (data) in the middle, and the operations (methods) at the bottom. A leading symbol marks each member's visibility.
# The class above, in Python class BankAccount: def __init__(self, account_id, owner_name, currency): self._account_id = account_id # - private self._balance = 0 # - private self._owner_name = owner_name # # protected (convention) self.currency = currency # + public def deposit(self, amt): ... # + public def withdraw(self, amt): ... # + public def _validate(self): ... # - private

Special Class Types

«interface»
A pure contract — method signatures, no implementation. Marked with the <<interface>> stereotype above the name. Classes realize it.
Abstract class
Cannot be instantiated on its own. Written in italics (or with <<abstract>>). Has some concrete and some abstract methods.
«enumeration»
A fixed set of named values, e.g. Status = {ACTIVE, CLOSED}. Marked <<enumeration>>; values listed in the body.

Relationships at a Glance

Classes rarely stand alone — the lines between them carry as much meaning as the boxes. Each connector has a precise notation. This is the single most important cheat-sheet in UML; the five relationship sections in this guide each drill into one row.

Multiplicity — How Many?

The numbers at each end of an association say how many objects participate. This is where a class diagram encodes real business rules.

NotationMeaningExample
1Exactly oneAn Order has exactly 1 Customer
0..1Zero or one (optional)A User may have 0..1 Avatar
* or 0..*Zero or moreA Customer has 0..* Orders
1..*One or more (at least one)An Order has 1..* LineItems
2..5A specific rangeA Game has 2..5 Players
Reading tip: multiplicity is read from the far end. On the line Customer 1 —— 0..* Order, the 0..* sits next to Order and means "one Customer has zero-to-many Orders." The 1 next to Customer means "each Order belongs to exactly one Customer."

Full Worked Example — Online Bookstore

Here is a complete class diagram that uses every relationship type at once. Trace each line and name the relationship — if you can read this diagram fully, you've mastered class diagrams. This is exactly the level of detail expected in an LLD interview.

Reading the Bookstore Diagram, Line by Line

  • Customer & Admin —▷ User — both inherit the abstract User (shared id/name/email). Solid line, hollow triangle. "A Customer is-a User."
  • Customer ◆— ShoppingCart — composition. The cart is created with the customer and dies with them. Filled diamond.
  • Customer —— Order — association with 1 : 0..*. A customer places many orders; each order belongs to one customer. Orders survive independently.
  • Order ◆— OrderItem — composition 1 : 1..*. Line items only exist inside their order. Delete the order → items gone.
  • OrderItem —— Book — association. An item points to the book it sells, but the book lives in the catalog on its own.
  • Order ⇢ PaymentMethod — dependency. The order uses a payment method to pay(), but doesn't own it. Dashed arrow.
  • CreditCard ⇠▷ PaymentMethod — realization. CreditCard implements the payment contract. Dashed line, hollow triangle.
  • Catalog ◇— Book — aggregation. The catalog groups books, but books exist even if the catalog object is discarded. Hollow diamond.
How to build one from scratch: (1) list the nouns → candidate classes. (2) list what each does → methods. (3) list what each holds → attributes. (4) draw the lines: ask "is-a?" (inheritance), "owns/part-of?" (composition/aggregation), "just uses?" (dependency), "same contract?" (realization). (5) add multiplicity. That five-step recipe turns any prose spec into a class diagram.
◎ Topic 3 · Behavioral
Use Case Diagram
A use case diagram is the highest-level, least technical UML diagram. It answers one question: who uses the system, and what can they do with it? No internal logic, no classes — just actors, goals, and the boundary of the system. It's the diagram you show a product manager.

The Four Building Blocks

Actor
A role that interacts with the system — a stick figure. Can be a person or an external system.
Use Case
A goal the actor achieves — an oval. Named as a verb phrase: "Place Order".
System Boundary
A rectangle around the use cases. Everything inside is your system; actors sit outside.
Relationships
Lines linking actors to use cases, plus «include» and «extend».

Example — Voice AI Support Platform

Include vs Extend — The One That Trips Everyone Up

«include» — always happens
The base use case always pulls in the included one. "Ask a Question" always includes "Transcribe Speech" — you can't do the first without the second. Arrow points to the included use case. Use it to factor out shared steps.
«extend» — sometimes happens
The extending use case runs only under a condition. "Escalate to Human" extends "Ask a Question" — it happens only if the AI can't answer. Arrow points to the base use case. Use it for optional / exceptional behavior.
Memory hook: include = mandatory sub-step (like calling a helper function every time). extend = optional add-on (like an if branch that fires only when a condition is met). The arrows point in opposite directions — include→child, extend→parent.

Do

  • Name use cases as user goals ("Reset Password")
  • Keep it to one clear system boundary
  • Model external systems as actors too
  • Use it early, to align on scope with non-engineers

Don't

  • Put implementation detail inside ovals
  • Turn it into a flowchart (that's an activity diagram)
  • Over-use include/extend — most links are plain
  • Model every tiny CRUD action as a use case

Second Example — ATM Machine

The classic interview warm-up. Notice how every transaction includes "Authenticate" (you can't do anything without your PIN), and "Print Receipt" extends the transactions (optional, only if you tap "yes").

Why this layout works: the three transactions each fan an «include» arrow up to Authenticate — modelling "always required first." Print Receipt sits below with an «extend» arrow pointing up — modelling "optional add-on." One glance tells you the whole access-control story without a single line of code.
⇄ Topic 4 · Behavioral
Sequence Diagram
A sequence diagram shows how objects collaborate over time — who sends which message to whom, and in what order. Time flows top to bottom. It's the sharpest tool for documenting a single important flow: a login, a checkout, or a voice-call pipeline.

The Notation

Lifeline
A vertical dashed line dropping from each participant. Represents that object existing through time.
Activation Bar
A thin rectangle on the lifeline — the object is actively doing work / holds the call stack.
Sync Message →
Solid line, filled arrowhead. Caller waits for the reply (a normal method call).
Return ⇠
Dashed line, open arrowhead. The result coming back to the caller.

Example — LiveKit Voice Call Pipeline

Message Types

Combined fragments: to show conditions and repetition, wrap messages in a labelled box: alt (if/else), opt (optional), loop (repeat), par (parallel). E.g. a loop box around the STT frames captures "stream chunks until the caller stops speaking."

Second Example — User Login with an alt Fragment

This is the pattern interviewers look for: showing the happy path and the error path in one diagram using an alt (alternative) box. The dashed line inside the box splits the two guarded branches.

The happy path
Guard [password valid] → controller returns 200 OK with a JWT. This is the top compartment of the alt box.
The error path
Guard [else] → controller returns 401 Unauthorized. The bottom compartment, split by the dashed divider.
Fragment quick-reference: alt = if/else (mutually exclusive branches) · opt = a single optional block (runs or doesn't) · loop = repeat while a condition holds · par = branches run in parallel · ref = "see this other sequence diagram." Master alt and loop first — they cover 90% of real diagrams.
⑃ Topic 5 · Behavioral
Activity Diagram
An activity diagram is UML's flowchart. It models a workflow or algorithm as a sequence of actions, with branching, looping, and parallel paths. Where a sequence diagram shows who talks to whom, an activity diagram shows the logic and flow of a single process.

The Notation

● Initial Node
A solid filled circle. Where the flow begins. Exactly one per diagram.
▢ Action
A rounded rectangle — a single step of work: "Validate Input", "Charge Card".
◆ Decision / Merge
A diamond. One incoming, multiple guarded outgoing paths — the branch point.
▬ Fork / Join
A thick bar. Splits flow into parallel paths (fork) or waits and rejoins them (join).

Example — RAG Chatbot Query Flow

Sequence vs Activity — Don't Confuse Them

AspectSequence DiagramActivity Diagram
FocusObjects exchanging messagesFlow of actions / logic
AxisTime (top→bottom)Control flow (any direction)
Parallelismpar fragmentFork / join bars (native)
Best forOne interaction, who-calls-whomBusiness process, algorithm, branching
Swimlanes: split an activity diagram into vertical or horizontal lanes, one per actor or component, to show who does what. E.g. lanes for "Client", "API", and "Vector DB" make ownership of each action obvious in the flow above.

Second Example — Order Fulfillment with Swimlanes

Swimlanes answer the question a plain flowchart can't: who is responsible for each step? Each vertical lane owns the actions inside it. Watch the flow cross lanes as responsibility hands off from Customer → System → Warehouse.

Reading swimlanes: follow the arrows — every time the flow crosses a lane boundary, responsibility has changed hands. Here the order is placed by the Customer, validated & tracked by the System, and physically fulfilled by the Warehouse. It's the clearest way to document a cross-team process.
◉ Topic 6 · Behavioral
State Machine Diagram
A state machine (or statechart) models the lifecycle of a single object: every state it can be in, and the events that move it between them. Use it whenever an object's behavior depends on its current state — a call, an order, a connection, a document in review.

The Notation

● Initial
Filled circle — the starting state when the object is created.
▢ State
Rounded rectangle — a named condition the object rests in.
→ Transition
Arrow labelled event [guard] / action. Moves object to a new state.
◉ Final
Circle-in-ring — the object's lifecycle ends here.

Example — Voice Call Lifecycle

Reading a Transition Label

event [guard] / action
Every transition can carry three parts. The event triggers it (hold()). The optional guard in brackets must be true for it to fire ([balance > 0]). The optional action after the slash runs during the transition (/ transcribe). Only event is required.
# The state machine above, as a simple enum + guard in Python class CallState(Enum): IDLE = 1; RINGING = 2; CONNECTED = 3 ON_HOLD = 4; ENDED = 5 def answer(self): if self.state == CallState.RINGING: # guard on current state self.state = CallState.CONNECTED # transition else: raise InvalidTransition(self.state)
Composite & history states: a state can nest a whole sub-machine inside it (a composite state). A history state (H) remembers which sub-state you were in when you left, so resume() returns you exactly where you paused — handy for the On-Hold → Connected path.

Second Example — E-commerce Order Lifecycle

Every order-management system is a state machine at heart. This one shows a clean linear happy path (Pending → Paid → Shipped → Delivered) plus branch-off states for cancellation and refunds — the real-world messiness.

The guard earns its keep here: cancel() [not shipped] — an order can only be cancelled before it ships. That single bracketed condition is a whole business rule captured visually. Without the guard, the diagram would wrongly allow cancelling a delivered order. This is why state machines beat prose specs: illegal transitions simply aren't drawn.
— Topic 7 · Relationships
Association
Association is the most general relationship: two classes are simply connected — one knows about the other and can use it. No ownership, no lifecycle dependency. It's drawn as a plain solid line, optionally with multiplicity, a name, and a navigation arrow.

The Notation

Key traits
"knows-a" · both objects have independent lifecycles · can be one-way (navigable) or two-way (bidirectional) · often carries multiplicity. It's the default when there's a link but no clear whole/part or ownership.
# Association: Teacher holds a reference to Students it did not create class Student: def __init__(self, id): self.id = id class Teacher: def __init__(self, name): self.name = name self.students = [] # just references — created elsewhere def assign(self, student): # link an existing Student self.students.append(student) # both live on their own; deleting the teacher doesn't delete students
Rule of thumb: if you can say "A is related to B" but not clearly "A owns B" or "A is part of B", it's a plain association. It's the safe default — reach for aggregation or composition only when ownership is real.
◇ Topic 8 · Relationships
Aggregation
Aggregation is a special "whole–part" association where the whole has parts, but the parts can exist independently of it. Think of it as weak ownership. Drawn with a hollow diamond on the whole's end.

The Notation

Key traits
"has-a" (weak) · shared/independent lifecycle — the part outlives the whole · the same part can belong to several wholes · deleting the whole does not delete the parts. Real example: a Playlist aggregates Songs — delete the playlist and the songs remain in the library.
# Aggregation: Team receives players it did NOT create and does not own class Player: def __init__(self, name): self.name = name class Team: def __init__(self, name, players): self.name = name self.players = players # passed in from outside # players live independently of the team messi = Player("Messi") team = Team("Inter Miami", [messi]) del team # messi still exists ✓
Aggregation vs Association: aggregation is just an association with an added whole/part semantic. In practice many teams treat the two interchangeably in code — the hollow diamond mainly documents intent: "this is a container of independently-owned parts."
◆ Topic 9 · Relationships
Composition
Composition is the strong whole–part relationship: the part cannot exist without the whole, and dies with it. The whole is responsible for creating and destroying its parts. Drawn with a filled diamond on the whole's end.

The Notation

Key traits
"owns-a" (strong) · coincident lifecycle — the part is created and destroyed by the whole · a part belongs to exactly one whole (not shared) · deleting the whole deletes the parts. Real example: an Order composes OrderLines — the lines have no meaning outside their order.
# Composition: House CREATES its own Rooms — they can't outlive it class Room: def __init__(self, area): self.area = area class House: def __init__(self, address): self.address = address self.rooms = [Room(20), Room(15)] # created INSIDE ✓ # no external reference to the rooms — # when the House is garbage-collected, its Rooms go with it
Aggregation vs Composition — the one-line test: "If I destroy the whole, do the parts survive?" Yes → aggregation (hollow ◇). No, they die too → composition (filled ◆). House/Room = composition. Team/Player = aggregation.
⇢ Topic 10 · Relationships
Dependency
Dependency is the weakest relationship: one class uses another temporarily — as a method parameter, a local variable, or a return type — without holding a lasting reference. If the used class changes, the user may break. Drawn as a dashed arrow with an open head.

The Notation

Key traits
"uses-a" · transient, no ownership, no stored reference · the dependency exists only for the duration of a call · the most common trigger is a method parameter, local variable, or return type. It's the relationship that says "a change here might ripple over there."
# Dependency: PaymentGateway appears ONLY as a parameter — not a field class OrderService: def checkout(self, gateway: PaymentGateway, amount): # uses it right here, then forgets it return gateway.charge(amount) # contrast with association, where gateway would be # stored as self.gateway and kept for the object's whole life
Dependency vs Association: both mean "A uses B", but the lifetime of the reference differs. Association = a stored field kept long-term (solid line). Dependency = a fleeting, method-local use (dashed line). If it's a constructor/field, it's association; if it's just a parameter, it's dependency.
⇠▷ Topic 11 · Relationships
Realization
Realization connects an interface (a contract) to the class that implements it. The interface promises what methods exist; the class delivers the how. Drawn as a dashed line with a hollow triangle pointing to the interface.

The Notation

Key traits
"implements" · the class provides concrete bodies for every method the interface declares · one interface can be realized by many unrelated classes · it's the backbone of polymorphism — code can depend on PaymentMethod and work with any implementer. This is exactly how you'd model swappable STT/TTS providers behind one interface.
# Realization: both classes fulfil the PaymentMethod contract from abc import ABC, abstractmethod class PaymentMethod(ABC): # «interface» @abstractmethod def pay(self, amount) -> bool: ... class CreditCard(PaymentMethod): # realizes it def pay(self, amount): return charge_card(amount) class UPIWallet(PaymentMethod): # realizes it too def pay(self, amount): return upi_collect(amount)

Realization vs Generalization

AspectRealization (implements)Generalization (extends)
Line styleDashed + hollow triangleSolid + hollow triangle
ConnectsClass → InterfaceSubclass → Superclass
InheritsOnly the contract (signatures)Contract + implementation + state
Keywordimplements / ABCextends / subclass
Meaning"fulfils a contract""is a kind of"
The only visual difference between realization and inheritance is solid vs dashed — both use the hollow triangle. Dashed → implementing an interface. Solid → extending a class. Get this one right and your class diagrams instantly read correctly.

Memorise the four connector shapes — line, diamond, triangle, and dashed-vs-solid — and you can read any class diagram on sight.

The 5-Step Recipe to Model Any System

1
Find the nouns → classes
Read the spec. Underline every noun: "A customer places an order for books." Those become candidate classes. Drop duplicates and vague ones.
2
Find the verbs → methods
"Customer places an order", "order calculates total." Verbs attach to the class doing the action: Customer.placeOrder(), Order.calculateTotal().
3
Add the data → attributes
What does each class need to remember? Order needs total, status, createdAt. Keep it to what the behavior actually uses.
4
Draw the lines → relationships
For each pair ask, in order: "is-a?" (inheritance) → "part-of that dies with it?" (composition) → "part-of that survives?" (aggregation) → "same contract?" (realization) → "just uses briefly?" (dependency) → else plain association. Add multiplicity.
5
Model the tricky behavior
Pick the one flow that's hard to explain in words and draw a sequence diagram. If an object has a complex lifecycle, add a state diagram. Stop there — don't over-document.

Common Mistakes to Avoid

Do

  • Start with Class + one Sequence — that's 80% of value
  • Use the filled/hollow diamond deliberately (ownership matters)
  • Add multiplicity — it encodes real business rules
  • Name use cases and methods as verbs
  • Keep diagrams focused — one question each

Don't

  • Confuse dashed (implements/uses) with solid (extends/knows)
  • Model every getter/setter — show intent, not noise
  • Turn a class diagram into an ER database schema
  • Draw all 14 diagram types "to be thorough"
  • Forget the arrow direction — it carries meaning
You're now fluent. You can read any UML diagram, pick the right one for a problem, and model a system from a blank page. The four shapes — line, diamond, triangle, arrow — plus the five diagram types are the entire language. Everything else is practice. Go design something.
