📑 Topic 1 · Data & Storage
Database Indexing
An index is a separate data structure that lets the database find rows without scanning every row. It's the difference between finding a word in a book by flipping every page vs using the book's index.

What is an Index?

The Core Idea
A database index is a sorted copy of selected columns with pointers to the original row. Without an index, every query scans every row (O(n)). With a B-Tree index, it's O(log n). For 1 million rows that's 1,000,000 checks vs ~20 checks.
Full Table Scan
O(n)
B-Tree Index
O(log n)
Hash Index
O(1)
1M rows scan
~20 hops

How a B-Tree Index Works

Index Types

B-Tree Index (Default)
Balanced tree — great for range queries (WHERE age > 25), ORDER BY, and equality. Default in PostgreSQL, MySQL. Most versatile index type.
Hash Index
Maps key → exact row location. O(1) equality lookups (WHERE id = 42). Cannot do range queries. Used in Redis, PostgreSQL hash indexes, in-memory DBs.
Composite Index
Index on multiple columns: CREATE INDEX ON users(country, age). Follows leftmost prefix rule — satisfies queries on (country), (country, age) but NOT age alone.
Covering Index
Index includes all columns a query needs — no need to touch the main table at all. Maximum performance. SELECT email FROM users WHERE id=1 — if index has (id, email), it's fully covered.

When to Add an Index

-- Check if a query uses an index (PostgreSQL) EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42; -- Output WITHOUT index: -- Seq Scan on orders (cost=0.00..18340.00 rows=1000000) ← BAD -- Create index CREATE INDEX idx_orders_user_id ON orders(user_id); -- Output WITH index: -- Index Scan on idx_orders_user_id (cost=0.43..8.45 rows=5) ← GOOD -- Composite for multi-column queries CREATE INDEX idx_orders_user_status ON orders(user_id, status); -- Covers: WHERE user_id=42 AND status='pending'

Index Tradeoffs

DimensionWithout IndexWith Index
Read SpeedO(n) — full scanO(log n) — tree traversal
Write SpeedFast — just insert rowSlower — update index too
Disk SpaceMinimal+10–30% per index
Range QueriesFull scan alwaysEfficient with B-Tree
Cardinality matters?NoHigh cardinality = best ROI
Index golden rules: Add indexes on columns in WHERE, JOIN ON, and ORDER BY clauses. Avoid indexing low-cardinality columns (gender, boolean — only 2 values, not worth it). Every index slows down INSERT/UPDATE/DELETE. Don't over-index OLTP tables.
📐 Topic 2 · Estimation
Capacity Estimation
Capacity estimation is how you figure out how many servers, how much storage, and how much bandwidth your system needs. Interviewers expect back-of-the-envelope calculations — confident numbers, not exact answers.

The Numbers You Must Memorise

The Estimation Framework — 5 Steps

1
Clarify Scale — DAU & Usage Pattern
How many Daily Active Users? What % perform each action? E.g. Twitter: 300M DAU, each reads 100 tweets/day, writes 1 tweet/day.
2
Calculate RPS (Requests Per Second)
RPS = (DAU × requests_per_user) ÷ 86,400 seconds. Account for peak = 2–3× average.
3
Estimate Storage
Storage/day = writes_per_day × data_size_per_write. Multiply by years for total. Don't forget replication (×3) and media vs metadata.
4
Estimate Bandwidth
Inbound = write_RPS × avg_write_size. Outbound = read_RPS × avg_response_size. Outbound usually dominates.
5
Derive Server / Cache Count
Servers = peak_RPS ÷ RPS_per_server. Cache RAM = hot_data_fraction × total_working_set.

Worked Example — Twitter at Scale

── GIVEN ──────────────────────────────────────────────────── DAU: 300M users Reads per user: 100 tweets/day Writes per user: 1 tweet/day (write-heavy asymmetry: 100:1 read:write) Avg tweet size: 300 bytes (text) + 10% have image (~300KB) ── REQUESTS PER SECOND ────────────────────────────────────── Read RPS = (300M × 100) ÷ 86,400 ≈ 347,000 RPS Write RPS = (300M × 1) ÷ 86,400 ≈ 3,500 RPS Peak (×3) = ~1M read RPS at peak hours ── STORAGE (per day) ──────────────────────────────────────── Text = 3,500 × 300 bytes ≈ 1 MB/day (trivial) Media = 3,500 × 10% × 300KB ≈ 100 GB/day Total = 100GB/day × 365 ≈ 36 TB/year With 3× replication ≈ ~110 TB/year ── BANDWIDTH ──────────────────────────────────────────────── Outbound = 347,000 × 300B ≈ ~100 MB/s (text) With media (CDN offloads most) ≈ ~10 GB/s ── SERVERS ────────────────────────────────────────────────── API servers = 1M RPS ÷ 1K RPS/server ≈ 1,000 servers Cache hit 95% → only 50K RPS hit DB DB servers = 50K ÷ 10K QPS/server ≈ 5 DB servers
Interview tip: Round aggressively. Say "300M ÷ 10⁵ ≈ 3,000 writes/sec" not the exact number. State your assumptions out loud. The interviewer cares about your reasoning process, not the exact number. Being off by 2× is fine.

🌊 Topic 3 · Event Streaming
Apache Kafka
Kafka is a distributed event streaming platform built for high-throughput, fault-tolerant, real-time data pipelines. It's the backbone of event-driven architectures at Netflix, Uber, LinkedIn, and Airbnb.

What is Kafka?

A Distributed Commit Log
Kafka is fundamentally a distributed, ordered, immutable log. Producers append events to the end. Consumers read from any position and track their own offset. Events are retained for days/weeks — not deleted after consumption. Multiple consumer groups can each read the same event independently.
1M+ msgs/sec Persistent Log Replay Events Ordered per Partition Horizontally Scalable

Core Architecture

Key Concepts

Topic & Partitions
A Topic is a named log (like a category). Each topic is split into N Partitions — parallelism units. Events with the same key always go to the same partition, guaranteeing order per key.
Offset
Each event in a partition has a sequential offset (0, 1, 2…). Consumers commit their offset to track progress. On crash, they resume from the last committed offset. Replay by resetting offset.
Consumer Groups
Multiple consumers in a group share partitions (each partition assigned to one consumer). Multiple groups all read the same events independently. Fan-out is built-in and free.
Replication
Each partition has 1 Leader and N-1 Followers (replicas). Producers/consumers talk to the Leader. If the Leader dies, a Follower is elected. replication.factor=3 is standard.

Kafka vs Traditional Message Queue

DimensionRabbitMQ / SQSKafka
Message retentionDeleted after consumptionRetained for days/weeks
ReplayNot possibleYes — reset consumer offset
Throughput~100K msgs/sec~1M+ msgs/sec
Fan-outNeed separate queues per consumerMultiple consumer groups free
OrderingPer queue (best-effort)Strict per partition
Best forTask queues, simple work distributionEvent sourcing, audit logs, streaming analytics
When to use Kafka: Event sourcing, activity tracking (Uber trips), log aggregation, real-time analytics, Change Data Capture (CDC), microservice decoupling at high throughput. For simple background jobs — SQS/RabbitMQ is simpler and sufficient.
🔢 Topic 4 · Distributed Systems
Consistent Hashing
Consistent hashing solves the problem of distributing data across servers when servers are added or removed. Regular modulo hashing invalidates almost every key — consistent hashing moves only the minimum possible.

The Problem with Regular Hashing

Modulo Hashing Breaks on Change
server = hash(key) % N — works great until N changes. Add 1 server: N goes from 3 to 4, and ~75% of all keys remap to different servers. Your entire cache is instantly cold. Database gets hammered.
// Regular hashing — catastrophic on server change const servers = ["A", "B", "C"]; // N = 3 "user:42" → hash = 1234567 → 1234567 % 3 = 1 → Server B ✓ servers.push("D"); // N = 4 now "user:42" → hash = 1234567 → 1234567 % 4 = 3 → Server D ← WRONG! // 75% of all keys now map to wrong servers → cache wipeout

The Hash Ring Solution

Virtual Nodes — Even Distribution

Problem: Uneven Ring Distribution
With only 4 physical servers, Server A might land on 40% of the ring and Server C on 10% — very uneven load. Virtual nodes fix this: each physical server gets 100–200 positions on the ring. Load becomes evenly distributed regardless of server count.
class ConsistentHash { constructor(servers, vnodes = 150) { this.ring = new SortedMap(); servers.forEach(s => { for (let i = 0; i < vnodes; i++) { const hash = murmur3(`${s}:vnode:${i}`); this.ring.set(hash, s); // 150 positions per server } }); } getServer(key) { const h = murmur3(key); // next clockwise position (wrap around ring) return this.ring.ceiling(h) ?? this.ring.first(); } }
Used by: Apache Cassandra (token ring), Amazon DynamoDB (partition routing), Redis Cluster (16,384 hash slots), CDN edge routing, distributed caches. Any time you need to distribute keys across a changing set of nodes.
🔴 Topic 5 · In-Memory Store
Redis
Redis is an in-memory data structure store — used as a database, cache, message broker, and queue. It's the most widely deployed cache in the world, running at sub-millisecond latency with 100K+ operations per second on a single node.

What Makes Redis Special

Latency
<1 ms
Throughput
100K+ ops/s
Data Types
8+ types
Persistence
AOF + RDB

Redis Data Types & Use Cases

String — Most Basic
SET user:42 '{"name":"Alice"}' EX 3600 — Cache any value. Session storage, HTML fragments, API responses. Atomic increment with INCR for counters.
Hash — Object Storage
HSET user:42 name Alice age 30 — Store object fields individually. Update one field without fetching/re-serialising the whole object. Efficient for user profiles.
Sorted Set (ZSET) — Leaderboards
ZADD leaderboard 9500 "alice" 8800 "bob" — Automatically sorted by score. O(log N) insert. O(log N + M) range query. Perfect for leaderboards, priority queues, rate limiting.
List — Queue / Stack
LPUSH queue task1 / BRPOP queue 0 — Blocking pop makes it a perfect task queue. Use as a simple job queue without a full message broker.
Set — Unique Collections
SADD online-users user:42 — No duplicates. O(1) membership check. Great for online users, unique visitors, tags. Set operations: UNION, INTERSECT, DIFF.

Redis Patterns in System Design

Rate Limiting
INCR rate:user:42 — increment on each request. EXPIRE rate:user:42 60 — reset per minute. If count exceeds limit, reject. Atomic, no race conditions.
Distributed Lock
SET lock:resource "owner" NX EX 30 — NX = only if Not eXists. EX = auto-expire. Only one server holds the lock. Prevents concurrent access to shared resource.
Session Store
Store user sessions in Redis instead of server memory. Any server can validate any session. Enables stateless app servers behind a load balancer.
Pub/Sub
SUBSCRIBE channel / PUBLISH channel msg — Real-time messaging. WebSocket fan-out across multiple server instances. Ephemeral (no persistence).

Redis Persistence & High Availability

ModeHowTrade-off
RDB SnapshotFull dump to disk every N secondsFast restarts, possible data loss between snapshots
AOF LogAppend every write command to fileNear-zero data loss, larger files, slower restarts
Redis SentinelMonitors primary, auto-failover to replicaHA without cluster complexity, manual sharding
Redis Cluster16,384 hash slots distributed across nodesHorizontal scale + HA, more operational complexity

Do

  • Always set TTL to prevent memory exhaustion
  • Use Redis Cluster for data >50GB or >100K ops/s
  • Use pipeline / MULTI-EXEC for batch operations
  • Monitor eviction rate and memory usage
  • Use Redis for ephemeral data — not source of truth

Don't

  • Store large blobs (>1MB) — use S3 + Redis for reference
  • Use Redis as primary DB for critical financial data
  • Skip persistence config in production
  • Ignore hot key problem (one key getting millions of hits)
🔐 Topic 6 · Security
JWT — JSON Web Token
JWT is a compact, self-contained token for transmitting claims between parties. It's the standard for stateless authentication in REST APIs, microservices, and single-page applications.

What is a JWT?

A Signed, Encoded JSON Payload
A JWT is a Base64Url-encoded string with 3 parts separated by dots: Header.Payload.Signature. The server signs it with a secret key. Anyone can decode the header and payload (they're not encrypted), but only the server can verify the signature. No database lookup needed — the token is self-validating.

JWT Structure — Decoded

JWT Authentication Flow

1
Login — Server issues token
User sends POST /login with email + password. Server verifies credentials, creates JWT with userId, role, exp (expiry), signs it with secret key, returns token to client.
2
Client stores and sends token
Client stores JWT in memory (SPA) or httpOnly cookie (recommended). Sends it in every request: Authorization: Bearer <token>.
3
Server validates — no DB needed
Server verifies the signature using its secret key (or public key for RS256). Checks exp hasn't passed. Reads claims (userId, role) directly from token. Zero database calls.
// Issue JWT (Node.js / jsonwebtoken) const token = jwt.sign( { userId: 42, role: 'admin' }, // payload process.env.JWT_SECRET, // signing secret (keep safe!) { expiresIn: '1h' } // expiry ); // Verify JWT (middleware) const decoded = jwt.verify(token, process.env.JWT_SECRET); // decoded = { userId: 42, role: 'admin', iat: 1700000000, exp: 1700003600 } // No database query needed — server trusts signed claims

JWT Security Best Practices

  • Short expiry times — Access tokens: 15 min. Refresh tokens: 7–30 days. Shorter = less damage if stolen.
  • Refresh token rotation — Issue a new refresh token on every use. Invalidate old one. Detects token theft.
  • httpOnly cookie — Store refresh token in httpOnly cookie, not localStorage. JavaScript can't read it → XSS-safe.
  • Algorithm matters — Use HS256 (shared secret) for same-service or RS256 (public/private key pair) for microservices where multiple services need to verify but only one issues.
  • Never put secrets in payload — The payload is Base64 encoded, not encrypted. Anyone with the token can read it.
JWT Revocation Problem: If a user's account is compromised and you need to invalidate their JWT immediately — you can't. The token is valid until it expires. Solutions: (1) Very short expiry (15 min), (2) Token blocklist in Redis, (3) Increment a version counter in DB and include it in JWT — reject old versions.

Do

  • Use short-lived access tokens (15 min)
  • Store refresh tokens in httpOnly cookies
  • Verify signature AND expiry on every request
  • Use RS256 for multi-service architectures
  • Implement token refresh rotation

Don't

  • Store sensitive data in JWT payload
  • Use long-lived access tokens (>1h)
  • Store JWT in localStorage (XSS vulnerable)
  • Use algorithm "none" (critical vulnerability)
  • Skip signature verification — ALWAYS verify
