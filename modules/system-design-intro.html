🖥️ Topic 1 · Foundation
Client & Server
The client-server model is the backbone of every networked application. Understanding who requests and who responds is the first mental model in system design.

What & Why

🖱️ Client
The requester. Initiates all communication. Examples: browser, mobile app, CLI tool, or another service. Never waits for a push — it asks first.
🗄️ Server
The responder. Listens on a port, processes incoming requests, and returns data. Examples: web server, API server, database server.

How it Works

Stateful vs Stateless

Stateful Server
Remembers client between requests. Session stored in server memory. Hard to scale horizontally — same client must hit same server. Example: WebSocket connections.
Stateless Server ✓
Every request is self-contained (JWT token includes user identity). Any server can handle any request. Scale out easily with a load balancer. REST APIs are stateless.
Design Principle: Always design stateless servers. Move state to a shared layer (Redis, DB). This lets you add/remove servers freely — the foundation of horizontal scaling.
🗄️ Topic 2 · Foundation
Database
Databases are the persistent memory of your system. Choosing the right type — and understanding how they differ — is one of the most important system design decisions.

SQL vs NoSQL

SQL (Relational)
Structured tables with fixed schema. ACID transactions. Relationships via joins. Examples: PostgreSQL, MySQL, SQLite.

Best for: financial data, user records, anything needing strong consistency and complex queries.
NoSQL (Non-Relational)
Flexible schema. Scales horizontally by design. 4 subtypes: Document, Key-Value, Wide-Column, Graph. Examples: MongoDB, Redis, Cassandra, Neo4j.

Best for: high write throughput, flexible schemas, distributed scale.

NoSQL Types at a Glance

Document
JSON-like docs. Flexible schema. MongoDB, CouchDB. Great for content, catalogs, user profiles.
Key-Value
Hash map at scale. Redis, DynamoDB. Blazing fast for sessions, caches, leaderboards.
Wide-Column
Rows with dynamic columns. Cassandra, HBase. Ideal for time-series, analytics, IoT at massive scale.
Graph
Nodes + edges. Neo4j, Amazon Neptune. Social networks, fraud detection, recommendation engines.

How to Choose

NeedChooseWhy
ACID transactionsPostgreSQL / MySQLStrong consistency guarantees
Massive write throughputCassandra / DynamoDBDesigned for horizontal scale
Sub-ms reads, cacheRedisIn-memory key-value store
Flexible JSON dataMongoDBSchema-less document model
Relationship traversalNeo4jGraph traversal is O(hops) not O(joins)
Full-text searchElasticsearchInverted index built for search
ACID explained: Atomicity (all-or-nothing), Consistency (valid state always), Isolation (concurrent txns don't interfere), Durability (committed data survives crashes). SQL gives you this. Most NoSQL sacrifices some for speed.
📈 Topic 3 · Scaling
Vertical vs Horizontal Scaling
When your single server can't handle the load, you scale. There are two fundamental directions — and knowing when to use each is a core system design skill.

Vertical Scaling (Scale Up)

Add more power to the same machine
Upgrade the existing server: more CPUs, more RAM, faster SSD. Simple — no code changes. But there's a ceiling: the world's biggest server can't serve millions of users. And it's a single point of failure.

Horizontal Scaling (Scale Out)

Add more machines
Run the same application on multiple servers. A load balancer distributes traffic. Theoretically unlimited capacity — add more servers as needed. Requires stateless design. This is how Google, Netflix, and Facebook scale.
DimensionVerticalHorizontal
LimitHard ceiling existsTheoretically unlimited
Downtime to scaleUsually yes (reboot)None — add servers live
Failure riskSingle point of failureRedundant — others take over
Cost at scaleExponentialLinear
Code changes neededNoneRequires stateless design
Real-world strategy: Start with vertical scaling (quick wins, no complexity). When you hit the wall or need redundancy, switch to horizontal. Most production systems at scale are horizontal with auto-scaling groups.
⚖️ Topic 4 · Scaling
Load Balancer
A load balancer distributes incoming traffic across multiple backend servers. It's the key component that makes horizontal scaling possible and keeps systems highly available.

What & Why

The Traffic Distributor
Without a load balancer, one server gets all traffic — it crashes, your app is down. With a load balancer in front of a fleet of servers: traffic is spread evenly, one server can die without affecting users, you can add servers without downtime, and it handles health checks automatically.

How Load Balancing Works

Load Balancing Algorithms

Round Robin
Requests go to servers 1→2→3→1→2→3. Simple and even. Best when all servers have equal capacity. Default for most LBs.
Least Connections
Next request goes to the server with fewest active connections. Best for variable request durations (some requests take 10ms, others 5s).
IP Hash (Sticky)
Same client IP always goes to same server. Needed for stateful apps (WebSocket, sessions stored in memory). Breaks horizontal scaling benefits.
Layer 4 vs Layer 7 LB: L4 balances at TCP level (fast, no content inspection). L7 balances at HTTP level (routes by URL path, headers, cookies). AWS ALB is L7 — it can send /api/* to API servers and /static/* to CDN origin. Use L7 for microservices.
🗂️ Topic 5 · Data Layer
Database Sharding
Sharding is horizontal partitioning of a database. Instead of one massive database handling all data, you split rows across multiple database instances called shards.

Why Shard?

The Single DB Bottleneck
A single PostgreSQL instance typically maxes out around 10K–100K queries/second depending on hardware. When your app outgrows one DB, vertical scaling is expensive and limited. Sharding splits the data across N databases, each handling 1/N of the load.

How Sharding Works

Sharding Strategies

Hash-Based
shard = hash(user_id) % N. Even distribution. But adding shards changes mapping → resharding pain. Consistent hashing solves this.
Range-Based
Shard 0: users A–M, Shard 1: N–Z. Simple. But uneven — "A" names may be rare, causing hot shards.
Directory-Based
A lookup table maps each key to a shard. Most flexible — but the lookup table is a bottleneck and single point of failure.

Sharding Challenges

  • Cross-shard queries — JOINs across shards are expensive or impossible. Denormalise or avoid cross-shard joins in schema design.
  • Hot shards — If shard key is poorly chosen (e.g. timestamp), one shard gets all new traffic. Use hash-based keys for even spread.
  • Resharding — Adding a shard requires moving data. Use consistent hashing to minimise data movement (only ~1/N keys move).
  • No distributed transactions — An order spanning users on Shard 1 and inventory on Shard 2 can't use a simple ACID transaction.
When to shard: Only shard when you've exhausted read replicas and vertical scaling. Sharding adds enormous complexity. Most apps never need it — a well-tuned Postgres with replicas handles billions of rows.
🔄 Topic 6 · Data Layer
Database Replication
Replication copies your database to multiple nodes. It provides high availability (survive node failure), disaster recovery, and the ability to scale reads independently.

Primary-Replica (Master-Slave)

Most Common Pattern
One Primary handles all writes. One or more Replicas receive a copy of every write asynchronously. Reads can go to any replica (offloading the primary). If the primary dies, a replica is promoted to primary.

Replication Types

Synchronous
Write confirmed only after all replicas acknowledge. Zero data loss. But slower writes — must wait for all nodes. Used in financial systems.
Asynchronous ✓ Default
Write confirmed when primary writes. Replicas catch up shortly after. Faster writes. Tiny risk of data loss if primary crashes before replication. Most apps use this.
Semi-Synchronous
Write confirmed when at least 1 replica acknowledges. Balance between safety and speed. MySQL semi-sync replication.
Replication vs Sharding: Replication = same data on multiple nodes (for availability + read scale). Sharding = different data on different nodes (for write scale + storage scale). Most systems need replication first; sharding only at extreme scale.
⚡ Topic 7 · Data Layer
Cache
A cache is a fast temporary store that sits in front of a slower data source. Serving data from memory (Redis) instead of disk (Postgres) is the single biggest latency win in most systems.

Why Cache?

L1 CPU Cache
~1 ns
Redis (RAM)
~0.1 ms
DB on SSD
~1–10 ms
Network DB
~50–200 ms

Cache-Aside Pattern (Most Common)

Eviction & Key Design

TTL — Time to Live
Every key gets an expiry: SET user:42 data EX 3600. After 1h, Redis auto-deletes it. Balance freshness vs DB load.
LRU Eviction
When memory fills, evict Least Recently Used keys. Redis default. Keeps hot data; cold data drops naturally.
Cache Stampede
Many requests miss simultaneously → flood DB. Fix: mutex lock so only one fetches, or add TTL jitter: 3600 ± 300s.
Cache invalidation: The hardest problem. When DB data changes, invalidate the cache key immediately (DEL user:42). Or use short TTLs to self-heal. Serving stale data is usually fine; serving wrong financial data is not.
🌐 Topic 8 · Data Layer
Content Delivery Network (CDN)
A CDN is a globally distributed network of servers that caches your static content close to users worldwide. Instead of everyone hitting your origin server in Virginia, users in Tokyo get files from a Tokyo edge node.

What & Why

The Global Cache
Without CDN: every user downloads your 2MB bundle from your single origin server. User in Sydney waits 200ms for every asset. With CDN: that bundle is cached on 200+ edge nodes. Sydney user gets it from a nearby edge in <10ms. Your origin handles just the first request per region.

What to Put on a CDN

✅ CDN-able (Static)
JS bundles, CSS, images, fonts, videos, PDFs, HTML SPA shells. Any file that's the same for every user. Cache-Control: max-age=31536000.
❌ Not CDN-able (Dynamic)
User-specific API responses, personalised dashboards, real-time data. These change per user or per second — can't be globally cached.
Cloudflare AWS CloudFront Fastly Akamai Google Cloud CDN
CDN + DDoS protection: Cloudflare and others also absorb DDoS attacks at the edge — malicious traffic never reaches your origin. This is a free security benefit of CDNs that's often overlooked.
🏛️ Topic 9 · Architecture
Monolithic vs Microservices
Should your system be one big application or many small ones? This is one of the most consequential architectural decisions — and the right answer depends entirely on your context.

Monolithic Architecture

Single Deployable Unit
All features (auth, orders, payments, notifications) live in one codebase and deploy together. One process, one database. Simple to develop initially, simple to test, simple to deploy. Where every company starts.

Microservices Architecture

Many Independent Services
Each business capability is its own independently deployable service with its own database. Services communicate via APIs or message queues. Each can be scaled, deployed, and developed independently by a separate team.
DimensionMonolithMicroservices
DeploymentDeploy everything togetherDeploy each service independently
ScalingScale whole appScale only the bottleneck service
Development speedFast initiallySlow (infra overhead)
Operational complexityLowVery high
Team ownershipShared codebaseEach team owns their service
Technology choiceOne stackEach service can use any language
Start monolith, extract services: Build a monolith first. When a specific component (payments, video encoding) is the bottleneck or needs independent deployment, extract it. Amazon, Netflix, Uber all started as monoliths.
📬 Topic 10 · Architecture
Message Queue
A message queue enables asynchronous communication between services. The producer sends a message and moves on — the consumer processes it whenever it's ready. Decoupling at its finest.

Why Message Queues?

Decoupling
Order Service doesn't need to know Email Service exists. Just publish order.created. Add consumers without touching producers.
Load Leveling
10K orders/sec spike → queue absorbs it. Consumers process at steady 1K/sec. DB never gets overwhelmed. Buffer between burst and capacity.
Reliability
Consumer crashes? Messages persist in queue. On restart, processing resumes. Nothing lost. Automatic retry with Dead Letter Queue for failures.

Queue vs Pub/Sub vs Event Stream

Queue (Point-to-Point)
Each message consumed by one consumer. Work distribution. RabbitMQ, SQS. Good for task workers, job processing.
Pub/Sub (Fan-out)
Every subscriber gets every message. SNS, Redis Pub/Sub. Good for notifications — one event triggers many independent actions.
Event Stream
Ordered, persistent log. Consumers track their own position, can replay. Kafka. Good for audit logs, analytics, event sourcing.
Idempotency is critical: At-least-once delivery means the same message may arrive twice (e.g. after a consumer crash and retry). Design consumers to be idempotent — processing the same message twice produces the same result. Use a message ID to deduplicate.
🚪 Topic 11 · Architecture
API Gateway
An API Gateway is the single entry point for all client requests in a microservices architecture. Instead of clients calling 10 different services, they call one gateway that routes, authenticates, and rate-limits for all of them.

What an API Gateway Does

Key Responsibilities

  • Authentication & Authorization — Validate JWT tokens once at the gateway. No need for each service to implement auth separately.
  • Rate Limiting — Limit each API key to 1000 requests/min. Protects backends from abuse without touching service code.
  • SSL Termination — Handle HTTPS at the gateway. Internal service-to-service communication can use plain HTTP, reducing CPU overhead.
  • Request Routing — GET /users/* → User Service. POST /orders/* → Order Service. URL-based or header-based routing.
  • Request/Response Transform — Aggregate multiple service calls into one response. Translate protocols. Reshape JSON.
  • Observability — Log every request centrally. Inject trace IDs. Single place for access logs.
AWS API Gateway
Fully managed. Tight Lambda/ECS integration. WebSocket support. Pay per request. Best for AWS-native stacks.
Kong / KrakenD
Open-source, self-hosted. Highly configurable via plugins. Handles massive throughput. Used by Netflix, Lyft.
nginx / Traefik
Lightweight reverse proxy that also does gateway duties. Traefik auto-discovers Docker/K8s services. Great for self-hosted.

Do

  • Centralise auth in the gateway — don't repeat it in every service
  • Use rate limiting per API key/IP to prevent abuse
  • Inject a trace ID on every inbound request
  • Keep gateway logic thin — business logic belongs in services
  • Use circuit breakers to fail fast on unhealthy services

Don't

  • Put business logic in the gateway (it's infrastructure)
  • Create a "fat gateway" that becomes a monolith again
  • Skip health checks on downstream services
  • Forget the gateway is a single point of failure — make it HA
API Gateway vs Load Balancer: A Load Balancer routes traffic to identical instances of one service (L4/L7). An API Gateway routes to different services based on path/method, and adds cross-cutting concerns (auth, rate limiting, transforms). Use both: LB in front of the Gateway, and LB in front of each service fleet.
