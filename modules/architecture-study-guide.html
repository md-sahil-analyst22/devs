Module 1 · Foundations

Why does structure matter?

Before learning any pattern or folder convention, you need to understand the problem they all solve. This is the mental model everything else builds on.

The messy room problem
Imagine your entire codebase lives in one file — 10,000 lines, no folders. Everything mixed: database queries, UI logic, email sending, price calculations. When something breaks, where do you look? When you want to change email logic, you risk breaking the price calculator.

Folder structure and architecture are just ways of saying: put things in the right drawer.
The restaurant analogy
A restaurant has clearly separated areas — kitchen, dining room, storage, billing counter. If the chef also handled billing while serving tables and scrubbing dishes, everything would collapse. Software architecture is the same idea: separate areas, each with one job, communicating through clear interfaces.

Separation of Concerns — the #1 rule

Every architecture pattern, every folder convention, every "best practice" you'll ever read boils down to this one principle:

Separation of Concerns: Don't mix things that do different jobs. A file that sends emails should ONLY send emails. A component that renders a button should ONLY render a button.
What does "mixing" actually look like in code? +
Imagine a single function that: validates user input, queries the database, formats the response, sends a welcome email, logs the action, and returns HTML. When email breaks — you're in this function. When DB changes — same function. When UI changes — same function. One change = potential for everything to break.
What does "separated" look like? +
You have: UserValidator.ts (only validates), UserRepository.ts (only queries DB), EmailService.ts (only sends emails), UserController.ts (only coordinates the others). When email breaks — open EmailService.ts. Done. Zero risk of touching anything else.
Why does this connect to folders? +
Folder structure IS how you physically enforce separation of concerns on disk. A folder named /services/ tells every developer: business logic lives here. A folder named /components/ says: UI lives here. The folder name is a contract the whole team signs.

A file = a responsibility. A folder = a category.

src/ ├── components/ # everything that renders UI │ └── Button.tsx # ONE job: render a button ├── services/ # everything that calls APIs │ └── chat.ts # ONE job: chat API calls ├── utils/ # tiny helper functions │ └── format.ts # ONE job: format strings/dates └── pages/ # one file per screen/route └── ChatPage.tsx # ONE job: the chat screen
The test: Can you describe what a file does in one sentence without using the word "and"? If you need "and" — it's doing too much.
Module 1 · Foundations

The 3 things every app does

No matter how complex the application — a chatbot, a bank, a social network — every app does exactly three things. Understanding this unlocks everything else.

1. Store data
Saving messages, users, settings, files. This is your database layer. MySQL, PostgreSQL, MongoDB — all doing the same job.
2. Process logic
Rules: "can't send empty messages", "max 500 tokens", "only admins can delete". This is your business logic layer.
3. Show UI
What the user actually sees and clicks. HTML, React components, mobile screens. Knows nothing about databases.
Every architecture pattern is just a specific answer to: How should these three things talk to each other, and where should each one physically live in your codebase?

The layer sandwich

Think of your app as a sandwich. Each layer only talks to the layers directly above and below it — never skipping layers.

UI layer — top
What the user sees. React components, screens, templates. Knows nothing about databases or business rules.
↕
Logic layer — middle
Business rules. Validates inputs, transforms data, makes decisions. Knows nothing about HTML or the database engine.
↕
Data layer — bottom
Database queries, files, external API calls. Knows nothing about the UI or business rules above it.
Why layers give you superpowers
If you swap your database from MySQL to MongoDB, only the data layer changes. The UI and logic layers never know it happened. This is the fundamental superpower of layered architecture — swap out any layer without touching the others.
Module 2 · Folder Structures

Type-based structure

The first structure you'll encounter. Files are grouped by what type of thing they are — components, hooks, services, utils. Simple, fast to set up, breaks at scale.

src/ ├── components/ # ALL UI components │ ├── Button.tsx │ ├── Modal.tsx │ ├── Navbar.tsx │ └── ChatBubble.tsx ├── hooks/ # ALL custom hooks │ ├── useAuth.ts │ └── useChat.ts ├── services/ # ALL API call logic │ ├── auth.ts │ └── chat.ts ├── utils/ # ALL helper functions ├── context/ # ALL React context ├── types/ # ALL TypeScript types └── pages/ # Route-level components
When to use it
Portfolio sites, startup MVPs, personal projects, tutorials, prototypes, any project with fewer than ~10 distinct features. When speed matters more than scale.
When it breaks
When components/ has 80 files. When changing the auth feature means touching 5 different folders. When new teammates can't find anything.
The key problem: To build the "auth" feature you need files from components/, hooks/, services/, context/, and types/. That's low cohesion — related things are scattered across the codebase.

When does type-based stop working?

ScaleFiles per folderExperience
Small (1–5 features)5–15 filesComfortable, fast
Medium (5–15 features)15–50 filesStarting to scroll
Large (15+ features)50+ filesPain. Switch patterns.
Module 2 · Folder Structures

Feature-based structure

The most scalable frontend structure. Files are grouped by what they do — auth, chat, payments each own their components, hooks, and services. High cohesion: related code lives together.

src/ ├── features/ │ ├── auth/ # Everything auth-related │ │ ├── components/ # Auth UI only │ │ │ ├── LoginForm.tsx │ │ │ └── SignupModal.tsx │ │ ├── hooks/ # Auth hooks only │ │ │ └── useAuth.ts │ │ ├── services/ # Auth API calls only │ │ │ └── authApi.ts │ │ └── index.ts # Public interface of auth feature │ ├── chat/ # Everything chat-related │ └── agents/ # Everything agent-related ├── shared/ # Truly reusable across features │ ├── ui/ # Button, Modal, Input │ └── utils/ # formatDate, truncate └── app/ # Routing, global providers, store
The key insight: To change the auth feature, you open features/auth/ and everything you need is there. One folder, one feature, high cohesion. Deleting a feature = deleting one folder.

Two concepts that connect folders to architecture

High cohesion (good)
Things that change together, live together. When auth requirements change, you touch one folder — not 5.
Low coupling (good)
Features don't depend on each other's internals. Auth doesn't reach into payments. They talk through a shared interface (index.ts).

The index.ts contract

Each feature exports only what other features need to know about it. Everything else is private. This is the feature's "public API".

// features/auth/index.ts — the only file other features import from export { LoginForm } from './components/LoginForm'; export { useAuth } from './hooks/useAuth'; export type { User, AuthState } from './types'; // ✅ Correct — import from the feature's index import { useAuth } from '@/features/auth'; // ❌ Wrong — reaching into a feature's internals import { useAuth } from '@/features/auth/hooks/useAuth';

Layer-based structure

The standard for backend APIs and servers. Folders map to architectural layers: controllers, services, repositories, models. Predictable, industry-standard, mirrors MVC and Clean Architecture.

src/ ├── controllers/ # HTTP request handlers │ ├── chatController.ts # handles POST /chat │ └── userController.ts ├── services/ # Core business logic │ ├── chatService.ts # "can user send this message?" │ └── authService.ts ├── repositories/ # Database queries ONLY │ ├── messageRepo.ts │ └── userRepo.ts ├── models/ # Database schemas / ORM models │ ├── Message.ts │ └── User.ts ├── routes/ # Route definitions (URL → controller) ├── middleware/ # Auth, logging, rate limiting ├── validators/ # Input validation schemas └── config/ # DB connection, env variables
The data flow: Route → Middleware → Controller → Service → Repository → Database. Each layer has exactly one job and only calls the layer below it.

Module 2 · Folder Structures

Monorepo & Domain-Driven Design

Advanced structures for large platforms. Monorepo keeps multiple apps in one repo. DDD mirrors your business domains in code. Both require planning — don't start here.

Monorepo

Multiple apps (web, mobile, API, admin) and shared packages (UI library, types, config) in one repository. Managed with Turborepo, Nx, or pnpm workspaces.

my-platform/ # one Git repo for everything ├── apps/ │ ├── web/ # Next.js frontend │ ├── api/ # Node.js backend │ ├── mobile/ # React Native app │ └── admin/ # Admin dashboard ├── packages/ │ ├── ui/ # Shared component library │ ├── types/ # Shared TypeScript types │ ├── utils/ # Shared utility functions │ └── config/ # Shared ESLint, TS, Tailwind config ├── turbo.json # Turborepo build pipeline └── pnpm-workspace.yaml
Pros
Share types between API and web with no publishing. One PR changes backend + frontend together. Unified CI/CD. Consistent tooling everywhere.
Cons
Complex tooling setup. Slow CI if not configured correctly. Steep learning curve. Overkill for solo developers or small teams.

Domain-Driven Design (DDD)

Code mirrors real business domains. Each domain (Users, Orders, Payments) is fully self-contained with its own entities, use cases, repositories, and events.

src/ ├── domains/ │ ├── user/ │ │ ├── entities/ # User, Role, Permission │ │ ├── usecases/ # CreateUser, BanUser │ │ ├── repositories/ # IUserRepository interface │ │ └── events/ # UserCreated, UserBanned │ ├── orders/ │ └── payments/ ├── infra/ # DB, email, queue implementations ├── interfaces/ # HTTP API, GraphQL, CLI └── shared/ # ValueObjects, base classes
Use DDD when: your codebase has complex business rules that map to real-world domains. Fintech, healthcare, logistics. Not for simple CRUD apps — the overhead isn't worth it.
Module 3 · Architecture Patterns

MVC — Model View Controller

The original and most well-known pattern, invented in the 1970s. Every web framework you'll encounter is a variation of MVC. Understanding it first makes every other pattern make sense.

The three parts
View
The UI. HTML templates, JSX. Shows data to the user. Sends user input to the Controller. Has no business logic.
Controller
The middleman. Receives user requests, calls Model methods, decides which View to render. Coordinates, doesn't calculate.
Model
The data and rules. Database queries, business logic, data validation. Knows nothing about the UI.
Restaurant analogy: Controller = waiter (takes order, coordinates). Model = chef + pantry (makes food, manages ingredients). View = the dish presented to you at the table.

Real flow: user sends a chat message

User types message
→
ChatController
validates input
→
MessageModel
saves to DB
→
ChatView
renders response

MVC's main weakness: the fat controller

// ❌ A fat controller — doing way too much async function sendMessage(req, res) { // Validation (should be in validator) if (!req.body.text) return res.status(400).send(); // Auth check (should be in middleware) const user = await verifyToken(req.headers.auth); // Business logic (should be in service) if (user.plan === 'free' && messageCount > 10) return... // DB query (should be in repository) const msg = await db.messages.create({ text, userId: user.id }); // AI call (should be in service) const reply = await openai.complete(text); res.json({ reply }); } // This is why Clean Architecture and Hexagonal exist.
Module 3 · Architecture Patterns

MVVM & MVP

Both are reactions to MVC's weaknesses. MVVM is what modern frontend frameworks (React, Vue, Angular) use. MVP is what older native apps used. Understanding both clarifies why React works the way it does.

MVVM — Model View ViewModel

The dominant pattern for modern reactive UI. The ViewModel exposes reactive state — when state changes, the View automatically re-renders. No manual DOM manipulation.

View
Declarative UI. Pure render output. No logic. Auto-updates when ViewModel state changes. In React: JSX components.
ViewModel
Holds reactive state. Exposes commands and data. In React: useState, useReducer, Zustand store, Redux.
Model
API calls, business logic, local persistence. In React: fetch(), React Query, service functions.
// ViewModel — state + logic in a hook function useChatViewModel() { const [messages, setMessages] = useState([]); const [loading, setLoading] = useState(false); const sendMessage = async (text) => { setLoading(true); const reply = await chatService.send(text); // Model setMessages(prev => [...prev, reply]); setLoading(false); }; return { messages, loading, sendMessage }; // exposed to View } // View — pure render, zero business logic function ChatView() { const { messages, loading, sendMessage } = useChatViewModel(); return ( <div> {messages.map(m => <Bubble key={m.id} {...m} />)} <SendButton onSend={sendMessage} disabled={loading} /> </div> ); }

MVP — Model View Presenter

Similar to MVVM, but the View is completely passive and the Presenter is a 1-to-1 companion to the View. Popular in Android and Windows app development.

MVP vs MVVM key difference
In MVP, the View implements an interface (ILoginView). The Presenter calls methods on it directly. In MVVM, the View observes/subscribes to state — it doesn't get called by name.
When you'd see MVP today
Legacy Android apps (before Jetpack Compose), WinForms applications, some .NET desktop software. New projects almost universally prefer MVVM or a component-based approach.
Module 3 · Architecture Patterns

Clean Architecture

Invented by Robert C. Martin (Uncle Bob). Organizes code in concentric circles. The most powerful principle: dependencies only point inward. Inner layers are completely ignorant of outer layers.

Entities — innermost circle
Pure business objects. User, Message, Agent. No framework imports. No database. Would compile in a world with no internet.
Use Cases
Application rules. CreateUser, SendMessage, RunAgent. Imports entities only. Knows nothing about Postgres or Express.
Interface Adapters
Controllers, presenters, gateways. Translates between the web world and the use case world. Converts HTTP request → use case input.
Frameworks & Drivers — outermost
Express, Postgres, React, Redis, OpenAI SDK. The most replaceable things. Knows everything but is known by nothing inner.
The Dependency Rule: Source code dependencies may only point inward. An inner layer never mentions anything from an outer layer by name. This is the one non-negotiable rule.

Why this matters practically

I want to swap my database from PostgreSQL to MongoDB +
With Clean Architecture: only the outermost layer (infrastructure/persistence/) changes. Your entities, use cases, and interface adapters don't care what database you use. With a tightly coupled app: you'd be changing files in 10 different places.
I want to test my business logic without a real database +
Your use cases depend on a repository interface (IMessageRepository), not the actual Postgres implementation. In tests, inject a mock that just uses an in-memory array. Zero database setup. Fast. Reliable.
I want to add a CLI interface alongside the HTTP API +
Create a new adapter (CLIAdapter) in the interface adapters layer. Your use cases are untouched — they don't know they're being called from a CLI instead of HTTP. Just wire the CLI adapter to the same use cases.

In code

// ENTITY — innermost, zero dependencies class Message { constructor(public text: string, public userId: string) { if (!text.trim()) throw new Error('Message cannot be empty'); } } // USE CASE — imports entity, nothing else class SendMessageUseCase { constructor(private repo: IMessageRepository) {} // interface, not impl async execute(text: string, userId: string) { const msg = new Message(text, userId); // entity return this.repo.save(msg); // interface, DB-agnostic } } // INFRASTRUCTURE — outermost, knows everything class PostgresMessageRepository implements IMessageRepository { async save(msg: Message) { return db.messages.create(msg); } }
Module 3 · Architecture Patterns

Hexagonal Architecture & Event-Driven

Two advanced patterns that are especially powerful for AI platforms. Hexagonal lets you swap LLM providers without touching core logic. Event-driven enables real-time streaming and agent pipelines.

Hexagonal Architecture — Ports & Adapters

Think of your app core as a USB hub. It has ports (interfaces) that define what it needs. Adapters plug in like USB devices and implement those ports. Swap adapters without changing the hub.

Driving side (left)
Things that drive your app: HTTP API, CLI, tests, scheduled jobs. They call your core's ports.
Driven side (right)
Things your app drives: databases, LLMs, email, queues. Your core defines what it needs via ports, adapters implement it.
// PORT — what the core needs (interface) interface LLMPort { complete(prompt: string): Promise<string>; stream(prompt: string): AsyncGenerator<string>; } // ADAPTER 1 — OpenAI implements the port class OpenAIAdapter implements LLMPort { async complete(prompt) { return openai.chat.completions.create({ messages: [{ role: 'user', content: prompt }] }); } } // ADAPTER 2 — Anthropic implements the SAME port class AnthropicAdapter implements LLMPort { async complete(prompt) { return anthropic.messages.create({ messages: [{ role: 'user', content: prompt }] }); } } // CORE — never changes when you swap providers class ConversationService { constructor(private llm: LLMPort) {} // inject any adapter async reply(prompt: string) { return this.llm.complete(prompt); } }
For AI specifically: LLM providers change rapidly. OpenAI raises prices, Anthropic releases a better model, you want to test with a local Ollama model. Ports mean you write one new adapter file. Your entire business logic: untouched.

Event-Driven Architecture

Components communicate by publishing and subscribing to events — not by calling each other directly. Critical for real-time streaming and multi-step agent workflows.

LLM streams token
→
emits "token" event
→
SSE → client
Agent uses tool
→
emits "tool.called"
→
Logger + Billing react
Key benefit: Multiple listeners react to the same event independently. To add billing tracking to every agent tool call, just add a new listener — zero changes to the agent code itself.

Tools: Kafka, Redis Streams, BullMQ, Socket.io

ToolBest forScale
In-memory EventEmitterSingle-process apps, simple workflowsSmall

This is the missing link. Every architecture pattern has a natural folder structure. Once you see the mapping, both the pattern and the folders make complete sense.

The big insight: Architecture patterns describe HOW code should relate. Folder structures describe WHERE code should live. They're the same idea — one is conceptual, one is physical.

    Project stageFolder structureArchitectureWhy

    The 3 questions to ask for any file

    1
    What layer does this belong to?
    Is it UI, logic, or data? This determines which top-level folder it goes in (components/ vs services/ vs repositories/ vs domain/).
    2
    What feature does this belong to?
    Is it specific to auth, chat, payments? Or is it shared across features? This determines features/X/ vs shared/.
    3
    Can I describe this file's job in one sentence without "and"?
    If yes — good. If you need "and" — this file is doing too much and should be split.
    Module 5 · AI / Agent Platform

    Architecture for AI applications

    AI platforms don't fit neatly into one pattern. They use a hybrid: Clean Architecture at the core, Hexagonal for swappable LLMs, Event-driven for streaming and async agent loops, MVVM on the frontend.

    The complete layer breakdown

    Frontend — MVVM (React + Zustand)
    Chat UI, agent builder, flow canvas. Components are pure render. Hooks hold state. WebSocket / SSE receives streaming tokens in real time. Feature-based folder structure inside.
    ↕ HTTP / WebSocket / SSE
    API layer — thin MVC
    Express / FastAPI routes. Auth middleware. Rate limiting. Input validation. Thin — no business logic. Just receives requests and delegates to the orchestration layer below.
    ↓
    Orchestration layer — Use Cases (Clean Arch)
    ConversationService, AgentRunner, WorkflowEngine. The brain. Decides: retrieve memory → build prompt → call LLM → execute tools → stream back. Agent loops live here.
    ↓
    Domain layer — Entities (Clean Arch)
    Pure classes: Message, Conversation, Agent, Tool, Memory. Zero framework imports. Zero LLM SDK. 100% unit testable with no setup.
    ↓
    Infrastructure layer — Adapters (Hexagonal)
    OpenAI/Anthropic/Ollama adapters. Pinecone/pgvector. PostgreSQL. Redis. Tool executors (web search, code runner). Each implements a port interface. All swappable.

    4 things AI platforms need that normal apps don't

    Memory module
    Short-term: recent messages in context window
    Long-term: vector embeddings of past conversations
    Session: who is talking, their preferences
    Tool registry
    Register tools (web search, calculator, code interpreter)
    Agent discovers available tools dynamically
    Execute with input validation, sandboxing, timeouts
    Prompt management
    System prompt versioning (v1, v2, v3)
    Template variables: {{user_name}}, {{context}}
    A/B test different prompt strategies
    Observability
    Every LLM call logs: tokens, latency, model, prompt version
    LangSmith, LangFuse, or custom tracing
    You cannot debug AI without traces

    Learning Roadmap

    Your path from beginner to advanced

    Don't try to learn everything at once. Each stage builds on the last. Feel the pain before learning the cure — it makes the concepts stick much better.

    Week 1–2
    Build a tiny MVC app
    Express + a simple database (SQLite is fine) + a template engine. No React yet. Build a simple chat log: POST a message, GET all messages. Feel the controller-service-model split. Don't add complexity — just build and feel the pattern.
    Week 3–4
    Add React with feature-based folders
    Build a chat UI. Use type-based folders first. Then when components/ has 20 files, migrate to feature-based. Feeling the pain before the solution makes the pattern click permanently.
    Month 2
    Add an LLM with Hexagonal ports
    Create an LLMPort interface. Write one adapter for OpenAI, one mock adapter for testing. Wire it into your chat service. Notice how your business logic never imports the OpenAI SDK directly — only the adapter does.
    Month 3
    Migrate backend to Clean Architecture
    Extract domain entities (Message, Conversation). Create use cases. Move DB queries to repositories. Move LLM call to infrastructure. Feel how each layer becomes independently testable.
    Month 4
    Build the agent loop and streaming
    AgentRunner in application/ layer. Tool registry in infrastructure/tools/. Memory module. Stream tokens via SSE to the frontend. Add event-driven tool execution. This is where all the pieces connect into a real AI platform.
    Ongoing
    Observability, swap providers, scale
    Log every LLM call with LangFuse. Try swapping your OpenAI adapter for Anthropic — your business logic should be completely unchanged. Add a vector database. Test with a local Ollama model. Each swap proves your architecture is working.

    The critical SaaS concepts

    Plan-gated features
    Every feature checks the user's plan before executing. Use a guard/middleware that reads the user's current plan from DB and compares against feature requirements. Don't gate in the UI only — always enforce server-side.
    // @RequiresPlan('pro') decorator @Get('/advanced-analytics') @RequiresPlan('pro') async getAnalytics() { ... }

    The domain events pattern for orders

    // When an order is placed, emit an event class OrderService { async placeOrder(cartId: string, userId: string) { const order = await orderRepo.create({ cartId, userId }); // Emit event — multiple services react independently eventBus.emit('order.placed', { orderId: order.id, userId }); return order; } } // Notification service listens (not called directly) eventBus.on('order.placed', async ({ orderId, userId }) => { await emailService.sendOrderConfirmation(orderId, userId); }); // Inventory service listens separately eventBus.on('order.placed', async ({ orderId }) => { await inventoryService.reserveStock(orderId); }); // Adding analytics tracking = add one more listener.     Don't

    • Mix cart logic into order service
    • Decrement stock without transaction
    • Store live product prices in orders (snapshot!)
    • Trust client-sent cart totals
    • Send confirmation email synchronously

    The agent loop — how to implement it

    // application/AgentRunner.ts — the core loop class AgentRunner { constructor( private llm: ILLMPort, // hexagonal port private memory: IMemoryPort, // hexagonal port private toolExecutor: ToolExecutor ) {} async *run(userMessage: string, agentId: string) { const context = await this.memory.retrieve(userMessage); // RAG const prompt = promptBuilder.build(userMessage, context); let iteration = 0; while (iteration++ < MAX_STEPS) { // safety limit const response = await this.llm.complete(prompt); if (response.type === 'final') { yield { type: 'answer', content: response.text }; break; } if (response.type === 'tool_call') { yield { type: 'thinking', tool: response.tool }; const result = await this.toolExecutor.run(response.tool); yield { type: 'tool_result', result }; prompt.addToolResult(result); // feed back into context } } } }

    Memory: the 3 tiers

    In-context (short-term)
    Last N messages sent directly in the prompt. Managed by PromptBuilder. Limited by context window size.
    Vector store (long-term)
    Past conversations and documents embedded and stored. Retrieved by semantic similarity. Pinecone or pgvector.
    Working memory (session)
    Current task state, tool results, intermediate conclusions. Redis. Cleared when the session ends.

    What to follow

    • Always cap agent iterations — set MAX_STEPS (e.g. 10). Without a cap, a looping agent burns money and crashes.
    • Sandbox tool execution — code runner tools need a sandboxed environment (Docker, E2B). Never run agent-generated code on your server directly.
    • Trace every LLM call — use LangFuse or a custom tracing adapter. Token usage, latency, prompt version — you can't debug agents without traces.
    • The LLM port is non-negotiable — at this complexity level, you MUST be able to swap providers. Model landscape changes monthly.
    • Emit tool events — each tool call is an event. Multiple systems (billing, logging, UI) react. The agent loop doesn't call them directly.

    Do

    • Set MAX_STEPS limit on agent loop
    • Use ports for every LLM provider
    • Sandbox code execution tools
    • Trace every LLM call with token count
    • Stream intermediate steps to UI
    • Version your system prompts

    Don't

    • Import OpenAI SDK in application layer
    • Skip the iteration limit
    • Run agent code without sandboxing
    • Forget to handle tool timeouts
    • Mix memory logic into agent runner

    How real-time sync works

    // backend/gateway/collab.gateway.ts handleOperation(client, payload) { const { docId, operation, version } = payload; // 1. Transform against concurrent ops (OT) const transformed = ot.transform(operation, serverState[docId]); // 2. Apply to server document serverDoc.apply(transformed); // 3. Broadcast to everyone in the room (except sender) client.to(docId).emit('operation', transformed); // 4. Pub/Sub for multi-server scaling redis.publish(`doc:${docId}`, JSON.stringify(transformed)); } // frontend: optimistic update + reconcile onUserEdit(change) { doc.applyLocal(change); // immediate (optimistic) socket.emit('op', change); // send to server } socket.on('operation', (op) => doc.applyRemote(op)); // reconcile

    • Show live cursors with user colors
    • Handle WebSocket reconnection gracefully

    Don't

    • Write your own conflict resolution
    • Store all state only in memory
    • Broadcast to all users (use rooms)
    • Ignore offline / reconnect state
    • Skip operation versioning

    Multi-tenancy: the 3 isolation strategies

    Row-level isolation
    Every table has a tenant_id column. PostgreSQL Row-Level Security (RLS) enforces that queries only return rows matching the current tenant. Cheapest to run.
    Schema-per-tenant
    Each tenant gets their own Postgres schema. Strong isolation, easy to backup per tenant. More complex migrations. Medium cost.
    DB-per-tenant
    Each tenant gets their own database. Total isolation. Most expensive. Used only for enterprise customers with strict compliance needs (HIPAA, etc.).

    RBAC — Role-Based Access Control

    // The permission check middleware pattern function requirePermission(resource: string, action: string) { return (req, res, next) => { const { user, tenant } = req; // Check: does user's role in THIS tenant allow this action? const allowed = rbac.check({ role: user.roleInTenant(tenant.id), // roles are per-tenant resource, // e.g. 'project' action, // e.g. 'delete' }); if (!allowed) return res.status(403).json({ error: 'Forbidden' }); next(); }; } // Usage router.delete('/projects/:id', requirePermission('project', 'delete'), controller.delete);

    What to follow

    • Tenant context in every request — extract tenantId from JWT/subdomain in middleware. Every service and repository receives it. Never trust client-sent tenant ID.
    • Roles are per-tenant — a user can be Admin in Company A and Viewer in Company B. Store roles as a user_tenant_roles junction table.
    • Domain events across tenants — use a message queue (Kafka, RabbitMQ) for cross-domain events. TenantCreated triggers billing setup and welcome email.
    • Super-admin is a separate app — your internal admin dashboard is not a feature of the main app. It's a separate apps/admin/ with its own auth.
    • Audit log everything — enterprise customers demand it. Every data mutation writes to an audit log with user, action, timestamp, before/after values.

    Do

    • Extract tenantId in middleware
    • Use Postgres RLS for data isolation
    • Check permissions server-side always
    • Store roles per tenant, not globally
    • Write an audit log for every mutation
    • Version your domain events

    Don't

    • Trust client-sent tenantId
    • Share admin UI with end users
    • Use global roles across tenants
    • Delete tenant data immediately
    • Skip audit logging for compliance features
