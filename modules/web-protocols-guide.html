Module 1 · Start here

Web Protocols & APIs — Complete Map

Every modern application is built on communication between computers. This guide covers every protocol and API style you'll encounter — from the foundational HTTP request to real-time WebRTC calls, from simple REST APIs to streaming AI responses.

The core question every protocol answers: "How should two computers talk to each other?" Different situations need different answers — sometimes you need a quick request-response, sometimes a permanent connection, sometimes you want the server to push data, sometimes you need peer-to-peer video.

The complete protocol landscape

HTTPSHTTP over TLS (encrypted)Client → ServerAll production trafficBeginner

Long PollingHTTP, held open until dataClient waits, server respondsSimple push, chat appsMid

Choosing the right communication pattern

Need to fetch or send data once
→ HTTP REST API. Standard request-response. GET user profile, POST new message, PUT update order. Stateless, cacheable, universally supported.
Need real-time bidirectional chat
→ WebSocket. Persistent connection, both sides send freely. Chat apps, multiplayer games, collaborative editing, live dashboards.
Server needs to stream data to browser
→ SSE (Server-Sent Events). One-way stream from server. AI token streaming, live scores, stock tickers, progress updates.
Get notified when something happens
→ Webhook. External service calls your endpoint when an event occurs. Payment success, GitHub push, LiveKit call ended.
Real-time voice or video calls
→ WebRTC. Peer-to-peer media. Direct browser-to-browser. Voice agents, video conferencing, screen sharing.
High-performance microservices
→ gRPC. Binary protocol over HTTP/2. 10x faster than REST JSON. Microservice-to-microservice, streaming RPC.

The Client-Server Model

Everything on the internet is built on a simple idea: a client asks for something, a server provides it. Understanding this model — and how it extends to APIs, WebSockets, and WebRTC — is the foundation for everything else.

The basic model

Synchronous vs Asynchronous communication

Synchronous (blocking)

  • Client sends request and waits for response
  • Nothing else happens until response arrives
  • Simple to reason about
  • Can feel slow for long operations
  • Examples: REST API call, database query

    • Asynchronous (non-blocking)

  • Client sends request and continues doing other things
  • Gets notified when response is ready (callback/event)
  • More complex but more efficient
  • Essential for real-time and high-performance apps
  • Examples: Webhook, WebSocket message, SSE stream

    • The evolution of client-server communication

    1990s — Basic HTTP (request/response)
    Browser requests HTML page. Server sends it back. Every interaction = new connection. Static pages only.
    2000s — AJAX & REST APIs
    JavaScript fetches data without reloading page. REST APIs return JSON. Dynamic web apps born. Gmail, Google Maps.
    2010s — WebSocket & real-time
    Persistent connections. Slack, WhatsApp Web. Server pushes data without client asking. Live dashboards.
    2020s — WebRTC, AI streaming, Edge
    P2P video calls in browser. AI responses streamed token-by-token. Edge functions. Real-time everything.
    Module 3 · HTTP

    HTTP — HyperText Transfer Protocol

    HTTP is the language of the web. Every time you open a webpage, call an API, or fetch data — HTTP is the protocol carrying that communication. It defines the format of requests and responses between clients and servers.

    Created
    1989 by Tim Berners-Lee
    Port
    80 (HTTP) / 443 (HTTPS)
    Nature
    Stateless, text-based
    Transport
    TCP (HTTP/1,2) UDP (HTTP/3)

    Anatomy of an HTTP request

    # HTTP Request Structure POST /api/chat HTTP/1.1 ← Request line: method path version # Headers (key: value pairs) Host: api.yourapp.com ← which server Authorization: Bearer eyJhbGci... ← who you are Content-Type: application/json ← what format is the body Content-Length: 52 ← how big is the body Accept: application/json ← what format you want back User-Agent: Mozilla/5.0... ← who is making the request ← blank line = end of headers # Body (optional for GET, required for POST/PUT) { "message": "Hello, how are you?", "conversation_id": "conv_abc123" }

    Anatomy of an HTTP response

    HTTP/1.1 200 OK ← Status line: version status-code reason # Response headers Content-Type: application/json ← format of the body Content-Length: 156 ← size of body Cache-Control: no-cache ← don't cache this X-RateLimit-Remaining: 47 ← custom header Date: Mon, 20 Mar 2026 10:00:00 GMT ← blank line # Body { "reply": "I'm doing well, thanks for asking!", "conversation_id": "conv_abc123", "tokens_used": 24 }

    HTTP is stateless — what that means

    Stateless = every request is independent. The server has zero memory of previous requests. Request #100 knows nothing about request #99 from the same user. This is why you send an Authorization header with every request — the server doesn't remember you were authenticated in the last one.
    Stateless benefits
    Easy to scale horizontally — any server can handle any request. No need to route the same user to the same server. Highly cacheable. Simple to reason about.
    How to maintain "state"
    Client sends identity proof with every request: JWT token, session cookie, or API key. Server verifies it every time. State lives in the token, not on the server.

    HTTP vs HTTPS — the quick difference

    HTTP (plain)

  • Data sent as plain text
  • Anyone on the network can read it
  • No verification the server is real
  • Passwords, tokens, data exposed
  • Port 80
  • Never use for any real app

    • HTTPS (encrypted)

  • Data encrypted with TLS
  • Intercepted data is unreadable
  • Certificate proves server identity
  • All data protected in transit
  • Port 443
  • Always use this

    HTTP Methods & Status Codes

    HTTP methods define the intention of a request — what action you want to perform. Status codes tell you what happened. Together they form the vocabulary of web communication.

    HTTP Methods (Verbs)

    MethodPurposeHas body?Idempotent?Safe?Example
    GETRetrieve dataNoYesYesGET /users/123
    POSTCreate new resourceYesNoNoPOST /messages
    PUTReplace entire resourceYesYesNoPUT /users/123
    PATCHUpdate part of resourceYesSometimesNoPATCH /users/123
    DELETEDelete resourceSometimesYesNoDELETE /messages/456
    HEADGET without body (metadata)NoYesYesHEAD /files/video.mp4
    OPTIONSGet allowed methods (CORS)NoYesYesBrowser pre-flight check
    Idempotent = calling the same request multiple times has the same result as calling it once. DELETE /users/123 called 3 times = same as called once (user is deleted). POST /messages called 3 times = 3 messages created. Safe = no side effects, read-only.

    HTTP Status Codes — the complete story

    1xx — Informational
    100 Continue · 101 Switching Protocols (WebSocket upgrade) · 102 Processing
    2xx — Success
    200 OK · 201 Created · 204 No Content · 206 Partial Content (streaming)
    3xx — Redirection
    301 Moved Permanently · 302 Found (temp redirect) · 304 Not Modified (cache) · 307 Temp Redirect
    4xx — Client Error
    400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 409 Conflict · 422 Unprocessable · 429 Too Many Requests
    5xx — Server Error
    500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable · 504 Gateway Timeout
    Key differences
    401 vs 403: 401 = not authenticated (who are you?), 403 = authenticated but not authorized (I know who you are but you can't do this). 400 vs 422: 400 = malformed, 422 = valid format but invalid content.
    Module 5 · HTTP

    HTTPS & TLS — Secure Communication

    HTTPS = HTTP + TLS encryption. It does two things that matter: authentication (proves the server is who it claims to be) and encryption (makes data unreadable to eavesdroppers). Required for any production application.

    How TLS works — the handshake

    1
    Client Hello — "I want to connect securely"
    Browser sends: TLS version it supports, list of cipher suites it accepts, a random number (client random). "I can speak TLS 1.3, here are encryption algorithms I know."
    2
    Server Hello — "Here's who I am"
    Server picks cipher suite, sends its SSL certificate (signed by a CA like Let's Encrypt), another random number (server random). "I'll use TLS 1.3 with AES-256. Here's my certificate."
    3
    Certificate verification
    Browser checks: Is cert signed by a trusted CA? Is it for the correct domain? Is it expired? If all pass → server is legitimate. If any fail → browser shows "Not Secure" warning.
    4
    Key exchange — generating the session key
    Using the two randoms and the server's public key, both sides independently derive the same session encryption key. The key is never transmitted — both compute it separately from the same inputs. Diffie-Hellman magic.
    5
    Encrypted channel open
    All further HTTP communication is encrypted with the session key. Even if someone captures the packets, they see random bytes. Handshake takes ~50ms. Worth every millisecond.
    Symmetric vs Asymmetric encryption in TLS: The certificate uses asymmetric (public/private key) — slow but allows key exchange without a shared secret. The actual data uses symmetric (session key) — fast. TLS handshake = asymmetric. Ongoing communication = symmetric.
    Module 6 · HTTP

    HTTP/1.1 vs HTTP/2 vs HTTP/3

    HTTP has evolved significantly since its creation. Each version solves the performance problems of the previous one. Understanding the differences helps you configure Nginx correctly and understand why your apps behave the way they do.

    FeatureHTTP/1.1HTTP/2HTTP/3
    TransportTCPTCPUDP (QUIC)
    EncryptionOptional (HTTPS)Required in practiceRequired (built in)
    MultiplexingNo (one at a time)Yes (multiple streams)Yes (independent streams)
    Header compressionNone (repeated every req)HPACK compressionQPACK compression
    Head-of-line blockingYes — one slow req blocks allPartial (TCP level)None (per-stream)
    Server pushNoYes (rarely used)Yes
    Connection setup3-way TCP handshakeTCP + TLS handshakes0-RTT (instant reconnect)
    Year199720152022
    Used by~30% of sites~60% of sites~30% of sites (growing)

    HTTP/1.1 — the bottleneck

    # HTTP/1.1 Problem: HOL (Head-of-Line) blocking # Only 1 request at a time per connection # Browser opens 6 parallel connections to work around this Request 1: GET /app.js → waits for response Request 2: GET /style.css → CAN'T START until Request 1 finishes Request 3: GET /logo.png → waits in queue... # Each request resends all headers: Host: yourapp.com # sent again Authorization: Bearer ... # sent again Accept: application/json # sent again # (adds 400-800 bytes of overhead per request)

    HTTP/2 — multiplexing

    # HTTP/2 sends multiple requests over ONE connection # Streams are interleaved — no waiting Stream 1: GET /app.js ─────────────▶ response chunk ─▶ done Stream 2: GET /style.css ──────────▶ response chunk ──▶ done Stream 3: GET /logo.png ────────▶ response chunk ───▶ done # All 3 run simultaneously on one TCP connection # In Nginx — enable HTTP/2: listen 443 ssl http2; # that's all you need

    HTTP/3 — QUIC eliminates TCP problems

    HTTP/2's remaining problem: It still uses TCP. If one TCP packet is lost, ALL streams wait for retransmission (TCP head-of-line blocking). HTTP/3 uses QUIC (UDP-based), where streams are independent — a lost packet for stream 1 doesn't affect stream 2. Critical for mobile users on lossy connections.
    Module 7 · APIs

    What is an API?

    API stands for Application Programming Interface. It's a defined contract that specifies how software components communicate. An API says: "send me this, I'll return that." The web, your OS, and every library you use have APIs.

    One-line definition: An API is a waiter at a restaurant. You (the client) don't go into the kitchen (the server) to cook your food. You tell the waiter (the API) what you want, the waiter takes your order to the kitchen, and brings back the result.

    Types of APIs

    Web APIs (HTTP)
    The most common. Send HTTP requests, get JSON back. REST, GraphQL, gRPC. Used to connect frontend to backend, or services to each other.
    Library APIs
    Function calls within code. numpy.array(), pandas.read_csv(). The library exposes a defined interface. You call functions, get results.
    OS APIs (Syscalls)
    Programs talk to the operating system. open() to open a file, socket() to create a network connection. The OS exposes these through system calls.
    Hardware APIs
    Browser APIs for hardware: getUserMedia() for camera/microphone, navigator.geolocation for GPS. JavaScript accesses hardware through browser-provided APIs.
    Public APIs
    Third-party services: OpenAI API, Stripe API, Twilio API, LiveKit API. You call their HTTP endpoints, get results. Pay per use.
    Private APIs
    Internal to your organization. Your frontend calls your own backend. Microservice A calls microservice B. Not exposed to the public.

    API key concepts

    TermDefinitionExample
    EndpointA specific URL that the API exposesPOST /api/v1/chat
    RequestWhat you send to the endpointJSON body + headers
    ResponseWhat the API sends backJSON data + status code
    PayloadThe data in the request/response body{"message": "hello"}
    API keySecret token that identifies your appX-API-Key: sk-abc123
    Rate limitMax requests allowed per time window100 requests/minute
    VersioningVersion prefix to avoid breaking changes/api/v1/, /api/v2/
    PaginationSplit large results into pages?page=2&limit=20
    SDKClient library that wraps the APIimport openai; openai.chat()
    Module 8 · REST APIs

    REST APIs

    REST (Representational State Transfer) is an architectural style for designing APIs over HTTP. It defines a set of conventions for how to structure URLs, use HTTP methods, and format responses. The dominant API style on the web.

    Created by
    Roy Fielding, 2000
    Protocol
    HTTP (uses it as is)
    Data format
    JSON (usually)
    Market share
    ~80% of public APIs

    REST = nouns (resources) + verbs (HTTP methods)

    The core idea: Everything is a resource (a noun). Resources have URLs. You perform operations on them using HTTP methods (verbs). GET /users/123 = "fetch the user with id 123". Clean, predictable, standard.

    CRUD operations with REST

    # CRUD = Create, Read, Update, Delete # Resource: /api/messages # CREATE — POST to the collection POST /api/messages # create new message Body: { "text": "Hello!", "chat_id": "abc" } → 201 Created: { "id": "msg_789", "text": "Hello!" } # READ — GET individual or collection GET /api/messages # list all messages GET /api/messages/msg_789 # get specific message → 200 OK: { "id": "msg_789", "text": "Hello!" } # UPDATE — PUT (replace all) or PATCH (update some) PUT /api/messages/msg_789 # replace entire message PATCH /api/messages/msg_789 # update specific fields Body: { "text": "Updated text" } → 200 OK: { "id": "msg_789", "text": "Updated text" } # DELETE DELETE /api/messages/msg_789 # delete message → 204 No Content # success, no body # Nested resources (relationships) GET /api/chats/abc/messages # messages IN chat abc POST /api/chats/abc/messages # create message IN chat abc

    URL design conventions

    # ✅ Good REST URL design GET /api/v1/users # plural nouns GET /api/v1/users/123 # ID in path GET /api/v1/users/123/orders # nested resource GET /api/v1/orders?status=pending&limit=20 # filtering in query string GET /api/v1/orders?sort=created_at&order=desc # ❌ Bad REST URL design GET /api/getUser?id=123 # verb in URL (use HTTP method!) POST /api/deleteOrder/456 # delete via POST? No. GET /api/user # singular noun GET /API/V1/Users # uppercase (use lowercase) GET /api/v1/getUserOrders/123 # camelCase in URL (use hyphens) # ✅ URL for non-CRUD actions (exceptions are OK) POST /api/v1/orders/123/cancel # action on resource POST /api/v1/auth/login # auth actions POST /api/v1/emails/send # action that isn't CRUD

    REST response design

    # Consistent response structure (envelope pattern) # Success response: { "success": true, "data": { "id": "user_123", "email": "user@example.com", "name": "Jane Doe" }, "meta": { "timestamp": "2026-03-20T10:00:00Z" } } # Error response: { "success": false, "error": { "code": "VALIDATION_ERROR", "message": "Email is required", "field": "email" # which field failed } } # Paginated list response: { "data": [...], "pagination": { "page": 2, "limit": 20, "total": 148, "pages": 8, "next": "/api/v1/messages?page=3&limit=20" } }

    RESTful — The 6 Architectural Constraints

    "REST" is an architectural style defined by Roy Fielding's 2000 dissertation. A "RESTful API" follows all 6 constraints he defined. Most APIs called "REST" follow some but not all — and that's usually fine for practical purposes.

    REST vs RESTful: REST is the set of architectural principles. RESTful means strictly following all 6 constraints. In practice, developers use "REST API" and "RESTful API" interchangeably. The principles are a guide, not a religion.

    The 6 constraints

    1. Client-Server separation
    The UI (client) and data storage (server) are completely separate concerns. The client doesn't know how data is stored. The server doesn't know anything about the UI. This enables each to evolve independently.

    In practice: Your React frontend and FastAPI backend are separate. The frontend doesn't connect to PostgreSQL directly. The backend doesn't render HTML.
    2. Statelessness
    Every request must contain all information needed to process it. The server stores no client session state. Each request is complete and independent.

    In practice: Your JWT token is sent with every request — the server doesn't remember your previous requests. No server-side sessions. Enables horizontal scaling.
    3. Cacheability
    Responses must define themselves as cacheable or non-cacheable. If cacheable, clients can reuse responses for equivalent future requests. Improves performance and reduces server load.

    In practice: Cache-Control: max-age=3600 on GET responses. CDN caches your static assets. Never cache sensitive data.
    4. Layered system
    Client doesn't know if it's talking directly to the end server, or through intermediaries (proxies, load balancers, CDNs). Each layer only knows about the adjacent layers.

    In practice: Your client hits Cloudflare → Nginx → FastAPI. Client only knows about Cloudflare. This enables caching, load balancing, security layers.
    5. Uniform interface (the most important)
    The API follows a consistent set of rules: resources identified by URLs, manipulation through representations, self-descriptive messages, HATEOAS (links to related resources in responses).

    In practice: Consistent URL patterns (/resource/id), standard HTTP methods, JSON responses with clear structure. Predictability.
    6. Code on demand (optional)
    Servers can extend client functionality by transferring executable code. The only optional constraint.

    In practice: JavaScript served from your backend and executed in the browser. Used when serving full HTML pages with embedded scripts.
    Module 10 · REST APIs

    REST API Design Patterns

    Good API design is one of the hardest things in software engineering — you can't easily change APIs once clients depend on them. These patterns solve the most common design challenges.

    Versioning — never break existing clients

    # Strategy 1: URL versioning (most common, most explicit) /api/v1/users /api/v2/users # v2 can completely change the response shape # Strategy 2: Header versioning Accept: application/vnd.yourapp.v2+json # Strategy 3: Query parameter /api/users?version=2 # FastAPI: maintain both versions simultaneously @app.get("/api/v1/users/{user_id}") async def get_user_v1(user_id: str): return {"id": user_id, "username": ...} # old format @app.get("/api/v2/users/{user_id}") async def get_user_v2(user_id: str): return {"id": user_id, "profile": {...}} # new format

    Filtering, sorting, pagination

    # Filtering with query params GET /api/v1/messages?conversation_id=abc&status=sent GET /api/v1/users?role=admin&created_after=2024-01-01 # Sorting GET /api/v1/messages?sort=created_at&order=desc GET /api/v1/users?sort=name&order=asc # Cursor-based pagination (better for large datasets) GET /api/v1/messages?cursor=msg_500&limit=20 # Response includes next cursor: { "data": [...], "next_cursor": "msg_480" } # Page-based pagination (simpler) GET /api/v1/messages?page=3&per_page=20 # Field selection — only return fields you need GET /api/v1/users?fields=id,email,name # reduce payload size

    Error handling — be specific and helpful

    # Don't: HTTP 400: "Bad request" # useless HTTP 500: "Internal Server Error: PostgreSQL: ..." # leaks internals # Do: specific, actionable error codes HTTP 422: { "error": { "code": "VALIDATION_ERROR", "message": "Email address is already registered", "field": "email", "hint": "Use POST /api/v1/auth/forgot-password if you forgot your password" } } HTTP 429: { "error": { "code": "RATE_LIMIT_EXCEEDED", "message": "Too many requests", "retry_after_seconds": 42 # tell client when to retry } }

    Good REST design

  • Use plural nouns: /users not /user
  • Version your API from day one
  • Return consistent error shapes
  • Use proper HTTP status codes
  • Include pagination on list endpoints
  • Document with OpenAPI/Swagger

    • Avoid these patterns

  • Verbs in URLs: /getUser, /createOrder
  • Using GET for operations with side effects
  • Inconsistent naming (camelCase vs snake_case)
  • Returning 200 for errors
  • No versioning — impossible to evolve safely
  • Exposing internal implementation details in errors

    GraphQL vs REST

    GraphQL is a query language for APIs invented by Facebook in 2012. Instead of hitting many specific endpoints, you send one flexible query describing exactly the data you need. The server returns exactly that — no more, no less.

    The core difference — REST vs GraphQL request

    REST — multiple requests, fixed responses
    # To get user + their last 5 messages + each message's chat name: GET /api/users/123 # 1st request GET /api/users/123/messages?limit=5 # 2nd request GET /api/chats/abc/details # 3rd request (for chat name) # 3 HTTP round trips, potentially over-fetching each time
    GraphQL — one request, exact data
    # Single POST to /graphql: query { user(id: "123") { name email messages(last: 5) { text createdAt chat { name # only the chat name, nothing else } } } } # 1 request, exactly the data needed
    AspectRESTGraphQL
    EndpointsMany (one per resource)One (/graphql)
    Over-fetchingCommon — gets all fields even if not neededNever — request only what you need
    Under-fetchingCommon — need N+1 requestsNever — nested queries in one request
    Type systemNot built-in (use OpenAPI)Strongly typed schema built-in
    CachingEasy — HTTP caching works nativelyComplex — all via POST, no URL caching
    Learning curveLow — HTTP is universalHigher — new query language to learn
    Best forSimple CRUD, public APIsComplex data, mobile (save bandwidth)
    Used byEveryone (default)GitHub, Shopify, Twitter, Facebook
    When to pick GraphQL: Mobile apps where bandwidth matters, complex relational data with many joins, teams where frontend and backend evolve at different speeds, when clients need very different subsets of the same data.

    gRPC — High-Performance RPC

    gRPC (Google Remote Procedure Call) is a framework for service-to-service communication. Unlike REST's text-based JSON, gRPC uses binary Protocol Buffers over HTTP/2. It's 5–10x faster and supports bidirectional streaming natively.

    AspectREST / JSONgRPC / Protobuf
    Data formatJSON (text, human-readable)Protocol Buffers (binary, compact)
    Size100% baseline~10x smaller
    SpeedBaseline5–10x faster serialization
    SchemaOptional (OpenAPI)Required (.proto file)
    Code generationManual or generatedAuto-generated in any language
    StreamingLimited (SSE for server push)Client, server, and bidirectional streaming built-in
    Browser supportNativeNeeds grpc-web proxy
    Best forPublic APIs, frontend communicationMicroservice-to-microservice, ML models, IoT
    # gRPC service definition (.proto file) syntax = "proto3"; service ChatService { rpc SendMessage (MessageRequest) returns (MessageResponse); rpc StreamMessages (StreamRequest) returns (stream Message); # server streaming rpc Chat (stream Message) returns (stream Message); # bidirectional } message MessageRequest { string text = 1; string conversation_id = 2; } # Protocol Buffers compile to client/server code in Python, Go, Java, etc.
    Module 13 · Real-time

    Polling & Long Polling

    Before WebSockets existed, polling was how web apps got "real-time" updates. The client repeatedly asked "any new data?" Even today it's sometimes the right choice for simplicity.

    Regular polling

    // Frontend: ask every 5 seconds setInterval(async () => { const messages = await fetch('/api/messages?since=lastId'); updateUI(messages); }, 5000); // poll every 5 seconds # Problem: 12 requests/min even when nothing changes # Wastes bandwidth, adds server load, data can be 5s stale

    Long polling

    // Long polling: server HOLDS the request until new data arrives async function longPoll() { const response = await fetch('/api/messages/wait'); // hangs here... // ...server responds ONLY when there's a new message handleNewMessages(response); longPoll(); // immediately start the next wait } # FastAPI: hold and wait for new data @app.get("/api/messages/wait") async def wait_for_messages(last_id: str): deadline = time.time() + 30 # wait max 30 seconds while time.time() < deadline: messages = await get_new_messages(after=last_id) if messages: return messages await asyncio.sleep(0.5) return [] # timeout — client will reconnect

    When to use polling

    TechniqueLatencyServer loadUse when
    Short polling (every Ns)Up to N secondsHigh (constant requests)Update frequency is predictable, simplicity needed
    Long pollingNear real-timeMedium (connections held open)Can't use WebSocket, need better than polling
    SSEReal-timeLow (one connection, server pushes)Server → client streaming, AI responses
    WebSocketReal-timeLow (persistent connection)Bidirectional, chat, games

    SSE — Server-Sent Events

    SSE is a one-way persistent HTTP connection where the server can push any number of events to the client over time. Perfect for AI token streaming, live dashboards, progress bars, and notifications — anywhere the server needs to push data continuously.

    Direction
    Server → Client only
    Protocol
    HTTP (not new protocol)
    Auto-reconnect
    Built into browser
    Best for
    AI streaming, live feeds

    How SSE works

    Browser
    EventSource API
    ──── GET /stream ────▶
    Server
    FastAPI
    ◀─── data: token1\n\n ─── keeps sending ─── data: token2\n\n ───
    Connection stays open until server ends stream or client disconnects

    SSE message format

    # SSE wire format — very simple data: Hello, this is the first chunk\n\n ← \n\n = end of event data: And this is the second\n\n id: 42\n ← optional event ID event: message\n ← optional event type data: {"type": "token", "text": "hi"}\n\n ← JSON works too retry: 3000\n ← reconnect delay in ms data: still sending\n\n

    FastAPI SSE implementation

    from fastapi.responses import StreamingResponse import asyncio, json # AI token streaming endpoint @app.get("/api/chat/stream") async def stream_chat(message: str, user = Depends(get_current_user)): async def event_generator(): # Stream tokens from OpenAI async for chunk in openai_stream(message): token = chunk.choices[0].delta.content if token: data = json.dumps({"token": token}) yield f"data: {data}\n\n" # SSE format # Signal completion yield "data: [DONE]\n\n" return StreamingResponse( event_generator(), media_type="text/event-stream", headers={ "Cache-Control": "no-cache", "X-Accel-Buffering": "no", # disable Nginx buffering } )
    // Frontend: EventSource API const eventSource = new EventSource(`/api/chat/stream?message=${encodeURIComponent(msg)}`); eventSource.onmessage = (event) => { if (event.data === '[DONE]') { eventSource.close(); // stream ended return; } const { token } = JSON.parse(event.data); appendToken(token); // show token in UI as it arrives }; eventSource.onerror = () => eventSource.close(); // Browser auto-reconnects on error (unless you close it)

    Webhooks

    A webhook is a "reverse API call." Instead of your app asking a service "did anything happen?", the service calls YOUR endpoint when something happens. Event-driven, efficient, and the standard for integrating with external platforms.

    Polling vs Webhook analogy: Polling = checking your mailbox every 5 minutes. Webhook = the postal worker rings your doorbell when mail arrives. One is wasteful, one is efficient.

    How webhooks work

    Event happens
    payment charged
    ─▶
    Stripe
    external service
    ── POST ──▶
    Your server
    /webhook/stripe
    ─▶
    Process event
    update DB

    Webhook vs API call

    Regular API (polling)

  • YOUR server calls THEIR server
  • You initiate: "did anything happen?"
  • Repeated requests even if nothing changed
  • Near real-time requires aggressive polling
  • You control the timing

    • Webhook (event-driven)

  • THEIR server calls YOUR server
  • They notify: "this thing just happened"
  • Only fires when events actually occur
  • Instant notification
  • They control the timing

    • Webhook security — signature verification

    # How Stripe signs webhooks: # 1. Stripe creates: timestamp + "." + payload # 2. HMAC-SHA256 with your webhook secret # 3. Sends in: Stripe-Signature: t=timestamp,v1=signature # Your FastAPI endpoint: import hmac, hashlib, secrets @app.post("/webhook/stripe") async def stripe_webhook(request: Request): payload = await request.body() # raw bytes (not parsed JSON) sig_header = request.headers.get("stripe-signature") webhook_secret = os.getenv("STRIPE_WEBHOOK_SECRET") # Parse the signature header: t=...,v1=... parts = dict(kv.split("=", 1) for kv in sig_header.split(",")) timestamp = parts.get("t") v1_sig = parts.get("v1") # Recompute expected signature signed_payload = f"{timestamp}.{payload.decode()}" expected = hmac.new( webhook_secret.encode(), signed_payload.encode(), hashlib.sha256 ).hexdigest() # Constant-time comparison (prevents timing attacks) if not secrets.compare_digest(expected, v1_sig): raise HTTPException(403, "Invalid signature") # Parse and handle the event event = json.loads(payload) if event["type"] == "payment_intent.succeeded": await handle_payment_success(event["data"]["object"]) return {"status": "received"} # always return 200 quickly
    Critical webhook rules:
    1. Always verify the signature — never trust a webhook without it
    2. Return 200 immediately — do heavy processing async (queue it)
    3. Handle duplicate events — services retry on failure (make handlers idempotent)
    4. Parse raw bytes for verification — not parsed JSON (serialization may differ)

    WebRTC — Real-Time Communication

    WebRTC (Web Real-Time Communication) enables browsers and apps to communicate audio, video, and data directly peer-to-peer — without a relay server for media. It's the technology behind Google Meet, Discord, and LiveKit voice agents.

    Media path
    Peer-to-peer direct
    Encryption
    DTLS-SRTP (mandatory)
    Server needed
    Signaling + TURN
    Use case
    Voice, video, screen share

    WebRTC architecture — 3 components

    Browser A
    Peer 1
    Signaling (WebSocket)
    Your Server
    Signaling only
    TURN relay (if NAT fails)
    Browser B
    Peer 2
    ◄──────── Direct P2P media stream (audio/video) — bypasses server ────────►

    The WebRTC connection process (ICE negotiation)

    1
    SDP Offer — "Here's what I can do"
    Browser A creates an SDP (Session Description Protocol) offer: what codecs it supports (H.264, VP8), what audio formats, what resolutions. Sends to your signaling server.
    2
    SDP Answer — "Here's what I can do too"
    Your server forwards the offer to Browser B. B creates an SDP answer with its capabilities. Sends back through your server to A.
    3
    ICE candidates — "Here's how to reach me"
    Both browsers gather ICE (Interactive Connectivity Establishment) candidates — possible network paths (local IP, public IP via STUN, TURN relay). Exchange them through signaling server.
    4
    DTLS handshake — encryption key exchange
    Once a network path is found, DTLS (Datagram TLS) handshake occurs directly between peers. Encryption keys are established.
    5
    SRTP stream — encrypted media flows
    Audio and video flow directly peer-to-peer encrypted with SRTP. Your server sees none of the media — only handled the initial signaling.

    STUN vs TURN servers

    STUN server

  • Helps a peer discover its public IP
  • Used during ICE candidate gathering
  • Lightweight — just reflects your IP back
  • Free: stun.l.google.com:19302
  • Doesn't relay media — peers still direct
  • Fails if both peers are behind symmetric NAT

    • TURN server

  • Relays media when direct connection fails
  • Required for corporate NAT, strict firewalls (~15% of calls)
  • Media flows through TURN server (adds latency)
  • Costs bandwidth to operate
  • LiveKit Cloud provides TURN automatically
  • Essential for reliable production WebRTC
    • LiveKit handles all of this for you. LiveKit Cloud provides STUN, TURN, SFU (Selective Forwarding Unit for multi-party), SDP negotiation, ICE, encryption, and SDKs. You call room.connect() and it just works. Only need to understand the internals for debugging or if self-hosting.

    WebRTC Signaling Server

    The signaling server is the matchmaker for WebRTC — it helps two peers exchange the information needed to connect directly. Once connected, media flows peer-to-peer and your server is not involved.

    # WebSocket-based signaling server for WebRTC # Peers exchange SDP offers/answers and ICE candidates through here peer_rooms: dict = {} # room_id → {user_id: websocket} @app.websocket("/signal/{room_id}") async def signal(ws: WebSocket, room_id: str, token: str): user = verify_token(token) if not user: await ws.close(1008); return await ws.accept() if room_id not in peer_rooms: peer_rooms[room_id] = {} peer_rooms[room_id][user["id"]] = ws # Tell other peers a new peer joined await signal_others(room_id, user["id"], { "type": "peer_joined", "peer_id": user["id"] }) try: while True: msg = await ws.receive_json() match msg["type"]: case "offer": # Forward SDP offer to target peer target = peer_rooms[room_id].get(msg["target_id"]) if target: await target.send_json({ "type": "offer", "sdp": msg["sdp"], "from": user["id"] }) case "answer": # Forward SDP answer back to offerer target = peer_rooms[room_id].get(msg["target_id"]) if target: await target.send_json({ "type": "answer", "sdp": msg["sdp"], "from": user["id"] }) case "ice_candidate": # Forward ICE candidates to help punch through NAT target = peer_rooms[room_id].get(msg["target_id"]) if target: await target.send_json({ "type": "ice_candidate", "candidate": msg["candidate"], "from": user["id"] }) except WebSocketDisconnect: peer_rooms[room_id].pop(user["id"], None) await signal_others(room_id, user["id"], { "type": "peer_left", "peer_id": user["id"] }) async def signal_others(room_id, sender_id, msg): for uid, ws in peer_rooms.get(room_id, {}).items(): if uid != sender_id: try: await ws.send_json(msg) except: pass
