Software Architecture Patterns

Architecture is how you divide a system into parts and define the rules for how those parts communicate. Every architecture answers the same question differently: how do we split the work so the system can grow, survive failure, and be understood by humans?

One sentence definition: Software architecture is the high-level structure of a system — what the major components are, how they communicate, and which constraints govern their interactions. Everything else (folder structure, patterns, tech stack) is a consequence of this decision.

Monolith vs Microservices

The most important architectural decision you'll make. Both are valid. The wrong choice depends entirely on your team size, traffic, and stage of product. Start with the wrong one and you'll pay for it for years.

🧱 Monolithic

  • One codebase, one deployment
  • Simple local function calls between modules
  • One shared database
  • Easy to debug and trace requests end-to-end
  • Fast to build and iterate at the start
  • Entire app redeploys on every change
  • Scale entire app even if only one module is hot
  • One module's bug can crash everything
  • Technology lock-in across all modules
  • Gets harder to change as codebase grows

    • ⚙️ Microservices

  • Many codebases, independent deployments
  • Network calls (HTTP / gRPC / events) between services
  • Each service owns its own database
  • Distributed tracing required (Jaeger, Zipkin)
  • Massive upfront infrastructure investment
  • Deploy only the service that changed
  • Scale only the service under load
  • Isolated failure — one service down doesn't crash all
  • Each service can use the best language/DB for the job
  • Hard: network failures, distributed transactions, latency

    • The decision framework

    SignalUse MonolithUse Microservices
    Team size< 10 engineers> 50 engineers (multiple teams)
    Product stagePre-product-market fit, MVPProven product, scaling pains
    TrafficUniform load or low scaleDifferent modules at very different scales
    Deployment frequencyDeploy everything together is fineTeams need to deploy independently
    Failure toleranceSome downtime acceptableNo single point of failure allowed
    Tech diversity neededOne language / DB is finePayment team needs Java, ML team needs Python
    Ops maturityNo dedicated DevOps/platform teamStrong DevOps, Kubernetes experience
    The startup trap: Most startups build microservices too early, drowning in infrastructure complexity before finding product-market fit. Start monolith. When you hit real scale pain — and you'll feel it clearly — extract services one at a time. This is exactly what Shopify, Stack Overflow, and Basecamp did.

    The hybrid: Modular Monolith

    Best of both worlds for most teams
    A modular monolith has clear module boundaries inside a single deployment. Modules have strict APIs (no direct DB cross-access), enforced dependencies, and independent test suites. It deploys as one unit but is architected to be split later. When you hit scale on one module, extract it as a service without rewriting the whole app.
    # Modular monolith — one codebase, hard module boundaries src/ ├── modules/ │ ├── orders/ # owns its DB tables — other modules CANNOT query these │ │ ├── order.service.ts │ │ └── index.ts # public API — only exports to other modules │ ├── payments/ # calls orders only through orders/index.ts │ └── notifications/ └── shared/ # truly shared utilities only

    🧱 Monolithic Architecture

    The entire application is built and deployed as a single, indivisible unit. All features, all modules, all business logic lives in one codebase and runs as one process.

    Definition & Concept

    In a monolithic architecture, all components of the application — the user interface layer, business logic, data access layer, and database connection — are combined into a single program from a single platform. It's one codebase, one build, one deployment artifact (JAR, executable, Docker container).

    Mental model: A monolith is like a single apartment. Everything you need lives under one roof — bedroom, kitchen, bathroom. Easy to manage, no commute. But if you want to expand, you're constrained by the building's structure.

    How it works — the process

    Presentation layer
    UI rendering, HTTP route handling, request/response. Controllers, views, API endpoints.
    ↕ direct function call
    Business logic layer
    Services, use cases, domain rules. The application's "brain" — validates, transforms, decides.
    ↕ direct function call
    Data access layer
    Repository classes, ORM models, raw SQL. Abstracts the database from the business logic.
    ↕ SQL / ORM
    Database
    Single relational database (PostgreSQL, MySQL). All modules share one DB instance.

    Real-world examples

    Ruby on Rails apps
    GitHub started as a monolith. Basecamp is still a monolith. Rails MVC is the textbook monolith structure.
    Django applications
    Most Django startups begin as monoliths. One codebase, one manage.py, one database.
    Spring Boot Java
    Enterprise Java apps shipped as a single WAR/JAR. One build artifact deployed to application servers.

    Pros and cons

    Advantages

  • Simple to develop and deploy — one command
  • Easy to test end-to-end — everything in one place
  • No network latency between modules
  • Simple debugging — one log stream, one stack trace
  • Low infrastructure cost — one server, one DB
  • Fast local development — no docker-compose orchestra

    • Disadvantages

  • Entire app redeploys on every change
  • One bug can crash everything
  • Scaling is all-or-nothing (can't scale just the AI module)
  • Technology lock-in — whole app must use same language
  • Code becomes entangled over time ("big ball of mud")
  • Long build times as app grows
    • Famous monoliths you use daily: Shopify (Rails monolith that handles millions of stores), Stack Overflow (C# monolith on 9 servers), Basecamp, eBay (started as a Perl monolith). Don't be embarrassed to start as a monolith.

    ⚙️ Microservices Architecture

    The application is decomposed into small, independently deployable services. Each service owns a single business capability, its own database, and communicates with others over the network. The architecture of Netflix, Uber, Amazon.

    Definition & Concept

    Microservices architecture structures an application as a collection of loosely coupled, independently deployable services, each with a narrow, well-defined responsibility. Each service runs its own process, manages its own data, and communicates via lightweight protocols (REST, gRPC, or message queues).

    Mental model: Microservices is like a city. The auth service is the post office, the payment service is the bank, the notification service is the telephone exchange. Each has its own building, staff, and hours. When the bank is busy, you expand the bank — you don't expand the post office.

    The 8 core principles of microservices

    1
    Single Responsibility
    Each service does one thing well. User service handles users. Payment service handles payments. They do not overlap.
    2
    Own your database
    No service queries another service's database directly. If Order Service needs user info, it calls the User Service API. Database-per-service = hard enforcement of boundaries.
    3
    Independent deployment
    Deploy the Payment Service on a Friday without touching User Service. Each has its own CI/CD pipeline, its own Docker image, its own release cycle.
    4
    Decentralized data management
    Different services can use different databases. Payment Service uses PostgreSQL for ACID guarantees. Product Catalog uses MongoDB for flexible schema. Notification Service uses Redis.
    5
    Failure isolation
    A crashing Recommendation Service shouldn't prevent users from checking out. Services are designed to handle downstream failures gracefully (circuit breakers, fallbacks).
    6
    API contracts
    Services communicate only through defined APIs (REST, gRPC, event schemas). Internals are hidden. Changing internal DB schema doesn't break other services.
    7
    Designed for failure
    Network calls fail. Services go down. Design every inter-service call with retries, timeouts, and circuit breakers. Assume any downstream call can fail at any time.
    8
    Observable by design
    Every service emits structured logs, metrics, and traces. Distributed tracing (Jaeger, Zipkin) shows you the path of a request across 10 services. You cannot debug microservices without this.

    The hard problems with microservices

    Distributed transactions
    Placing an order requires: creating an order record AND charging a payment AND reducing inventory. Across 3 services. If payment succeeds but inventory fails — what do you do? Solution: Saga pattern — compensating transactions.
    Data consistency
    In a monolith, a DB transaction keeps data consistent. In microservices, there's no global transaction. You get eventual consistency: the system will be consistent… eventually. Requires designing for this explicitly.
    Service discovery
    Service A needs to call Service B. But B's IP changes on every deploy. Solution: service registry (Consul, Kubernetes DNS) — services register themselves and others look them up by name.
    Latency & network overhead
    What was a microsecond function call is now a network hop with serialization, DNS lookup, and TCP overhead. A request touching 10 services compounds this. Use gRPC (binary protocol) over REST where latency matters.

    Use cases — when microservices make sense

    ScenarioWhy microservices fitReal example
    Large engineering orgTeams can own services independently. No merge conflicts across teams.Amazon (one service per team)
    Extreme scale differencesVideo encoding at Netflix needs 1000x more compute than billing.Netflix, YouTube
    Polyglot requirementsML team needs Python, Core team needs Java, Frontend team needs Node.Uber's tech stack
    Zero-downtime requirementsDeploy individual services with rolling updates, no full system restart.Banking, e-commerce at peak
    Regulatory isolationPayment service must be PCI-DSS certified in isolation. Easier if it's separate.Fintech, healthcare

    Do with microservices

  • Start with a modular monolith, extract later
  • One database per service (hard boundary)
  • Use an API Gateway for all external traffic
  • Implement circuit breakers (resilience4j, Hystrix)
  • Distributed tracing from day one
  • Define service contracts with OpenAPI/Protobuf

    • Don't with microservices

  • Share a database between two services
  • Start microservices on day 1 of a startup
  • Skip observability tooling
  • Create services smaller than a sprint's worth of work
  • Synchronous calls for non-critical events

    🥞 Layered (N-Tier) Architecture

    The most widely used architectural pattern in enterprise software. Code is organized in horizontal layers where each layer serves the one above it and depends on the one below. The foundation of MVC and Clean Architecture.

    Pattern
    Horizontal layers
    Communication
    Top-down only
    Variants
    2-tier, 3-tier, N-tier
    Used in
    90% of apps

    The tiers explained

    2-tier (Client-Server)
    Client (UI) talks directly to Database. No middle layer. Old desktop apps, simple tools. Never build web apps this way — no security layer.
    3-tier (Most common)
    Presentation → Business Logic → Data. Standard for web apps. What MVC implements. What you likely build every day.
    N-tier (Enterprise)
    Adds more layers: caching tier, message queue tier, CDN tier, microservice tier. Each layer isolated and scalable independently.

    The strict rule: dependencies point down only

    Layer 1 — Presentation / UI
    Renders HTML, handles HTTP requests, returns JSON. Controllers, views, React components. Can call Layer 2. Cannot call Layer 3 or 4 directly.
    ↓ calls only the layer below
    Layer 2 — Business Logic / Application
    Services, use cases, domain rules. The "what" of the application. Validates inputs, applies rules, orchestrates data operations. Calls Layer 3.
    ↓ calls only the layer below
    Layer 3 — Data Access / Persistence
    Repositories, ORM models, raw SQL queries. Translates between business objects and database rows. Knows about the DB, not about HTTP.
    ↓ SQL / ORM queries
    Layer 4 — Database
    PostgreSQL, MongoDB, Redis. Stores and retrieves data. Knows nothing about any layer above it.

    Use cases

    Application typeHow layers map
    REST API (Express/Fastify)Routes → Controllers → Services → Repositories → PostgreSQL
    Web app (Django)Views (routes) → Views (logic) → Models → Database
    Enterprise Java (Spring)Controller → Service → Repository → Entity/DB
    Mobile backendAPI Layer → Business Layer → Cache Layer → DB Layer

    📡 Event-Driven Architecture

    Components communicate exclusively by emitting and consuming events. Producers fire events and forget. Consumers react to events they care about. No direct coupling between them. The backbone of real-time systems, agent pipelines, and modern distributed platforms.

    Coupling
    Very loose
    Consistency
    Eventual
    Scaling
    Excellent
    Debugging
    Hard

    Definition & Core concept

    In event-driven architecture, a component doesn't call another component directly. Instead it emits an event — "something happened" — and moves on. Zero, one, or many other components may react to that event. The emitter doesn't know or care about them.

    Real world analogy: A news broadcaster doesn't call each viewer individually. It broadcasts. Whoever is tuned in receives the broadcast. Event-driven architecture works exactly this way — components subscribe to what they care about.

    The 3 event patterns

    Event notification
    "Something happened." Minimal payload. Consumer fetches details separately. e.g., order.placed: { orderId: "123" } — consumer then calls Order API for full details.
    Event-carried state transfer
    "Something happened, here's everything." Full state in the event. Consumer doesn't need to call back. e.g., user.updated: { id, email, name, plan, ...all fields }
    Event sourcing
    "The event IS the source of truth." You never update records — you append events. State is computed by replaying all events. Covered in the CQRS section.

    How it flows

    // Order placed — emit event (fire and forget) class OrderService { async placeOrder(cartId) { const order = await orderRepo.create(cartId); eventBus.emit('order.placed', { orderId: order.id, userId: order.userId, total: order.total }); // OrderService has no idea who reacts to this. It just moves on. return order; } } // EmailService subscribes — independently eventBus.on('order.placed', async ({ orderId, userId }) => { const user = await userService.getById(userId); await emailService.sendConfirmation(user.email, orderId); }); // InventoryService subscribes — independently eventBus.on('order.placed', async ({ orderId }) => { await inventoryService.reserveStock(orderId); }); // Adding analytics? Just add another subscriber. Zero code changes to OrderService. eventBus.on('order.placed', ({ total }) => analytics.track('revenue', total));

    Real-time notificationsuser.mentioned, task.assigned, message.receivedRedis Pub/Sub + WebSocket

    🔀 CQRS + Event Sourcing

    Two complementary patterns. CQRS separates reads and writes into different models. Event Sourcing stores state as a sequence of immutable events rather than a current snapshot. Together they give you infinite audit trails, time travel debugging, and extreme read performance.

    CQRS stands for
    Command Query
    Responsibility Segregation
    Read model
    Optimized for queries
    Write model
    Optimized for commands
    Complexity
    Very high

    CQRS — Separate reads from writes

    Traditional CRUD: one model for both reading and writing data. CQRS says: reading and writing have fundamentally different requirements — separate them into two models.

    Command side (Writes)

  • Handles mutations: CreateOrder, CancelOrder, UpdateUser
  • Enforces business rules and invariants
  • Optimized for consistency and correctness
  • Returns success/failure, not data
  • Writes to the write store (event store)

    • Query side (Reads)

  • Handles queries: GetOrderById, ListUserOrders
  • No business rules — just data retrieval
  • Optimized for query performance (denormalized)
  • Returns exactly the shape the UI needs
  • Reads from projections (read-optimized views)

    • Event Sourcing — store events, not state

    The paradigm shift: Instead of storing "order status = cancelled", you store the entire history: OrderPlaced → PaymentCaptured → ItemShipped → OrderCancelled → RefundIssued. Current state = replay all events. You never lose history.
    // Traditional: store current state (you lose history) UPDATE orders SET status = 'cancelled', refund_amount = 50 WHERE id = 'ord-123'; // Event Sourcing: append events (history is sacred) INSERT INTO events (stream_id, type, data, timestamp) VALUES ('ord-123', 'OrderPlaced', { total: 100, items: [...] }, '2024-01-01 10:00'), ('ord-123', 'PaymentCaptured', { amount: 100 }, '2024-01-01 10:01'), ('ord-123', 'OrderCancelled', { reason: 'out of stock' }, '2024-01-02 09:15'), ('ord-123', 'RefundIssued', { amount: 100 }, '2024-01-02 09:20'); // Current state = replay: fold all events into the latest snapshot const order = events.reduce((state, event) => applyEvent(state, event), {});

    Use cases

    DomainWhy CQRS + ES fits
    Banking / FintechEvery transaction is an event. Regulators need full audit trail. Balance = replay of all debits/credits.
    Healthcare recordsMedical history must never be deleted or modified. Every update is an append.
    Collaborative editingEach keypress / edit is an event. "Undo" = replay minus last event.
    Supply chain / inventoryTrack every stock movement. Debug discrepancies by replaying history.
    E-commerce with complex ordersFull order lifecycle in events. Rebuild any past state for customer disputes.

    Publishers send messages to named channels (topics/queues). Subscribers receive messages from channels they care about. They never interact directly. The plumbing of distributed systems — Kafka, RabbitMQ, AWS SQS, Redis Pub/Sub.

    Use cases

    Background job processing
    User uploads a video → publish to video.processing queue → worker picks it up → transcodes → publishes video.ready. HTTP request returns immediately. Processing is async.
    Cross-service communication
    Order Service publishes order.placed to Kafka. Inventory, Email, Analytics, and Billing services each consume independently at their own pace. Kafka buffers spikes.
    Real-time data pipelines
    Clickstream data from millions of users → Kafka → Flink / Spark for stream processing → aggregated metrics → dashboards. LinkedIn, LinkedIn, and Twitter are all built on this.
    Microservice choreography
    Replace synchronous REST calls between services with async events. Order Service never waits for Email Service to respond. Services are decoupled in time as well as in code.

    🔗 Service-Oriented Architecture (SOA)

    The enterprise predecessor to microservices. Large services (not micro!) communicate through a centralized Enterprise Service Bus (ESB). Standard in banks, telecom companies, government systems, and large enterprises built in the 2000s–2010s.

    Service size
    Large / coarse-grained
    Protocol
    SOAP, WSDL, XML
    Hub
    ESB (centralized)
    Era
    2000–2015

    SOA vs Microservices: key differences

    AspectSOAMicroservices
    Service sizeLarge — "Customer Service" handles all customer operationsSmall — "Customer Profile", "Customer Auth", "Customer Billing" are separate
    Communication hubCentralized ESB — all services route through itDecentralized — services talk directly or via lightweight message brokers
    Data sharingServices often share a central data storeEach service has its own database
    ProtocolSOAP/XML, heavyweight WSDL contractsREST/JSON, gRPC, async events
    Deploy unitService is a large application moduleService is a small focused process
    Still used?Yes — banks, telecom, governmentYes — tech companies, startups
    SOA is not dead: The vast majority of financial institutions (banks, insurance, payments) still run SOA-based systems. If you ever work at a bank, you'll encounter SOAP endpoints and ESBs. Understanding SOA is essential for enterprise software careers.

    The ESB problem

    Why SOA fell out of favour with tech companies
    The ESB becomes a "smart pipe" — routing, transformation, orchestration logic piles up in the bus. It becomes a bottleneck, a single point of failure, and the hardest thing to change in the whole system. Microservices moved intelligence back into the services and made the communication layer ("pipe") dumb.

    Port vs Adapter

An abstract promise. interface ILLMPort { complete(messages: Message[]): Promise<string>; stream(messages: Message[]): AsyncGenerator<string>; } // ADAPTER 1 — OpenAI implements the port class OpenAIAdapter implements ILLMPort { async complete(messages) { return openai.chat.completions.create({messages}); } } // ADAPTER 2 — Anthropic.     Why this matters for AI projects specifically

    LLM providers change monthly. OpenAI releases GPT-5, Anthropic releases Claude 4, Google releases Gemini Ultra 2 — all within 3 months. If your business logic imports the OpenAI SDK directly, every model upgrade requires touching production code. With hexagonal architecture, you write one new adapter file. Your entire application: untouched.

    🕸️ Service Mesh Architecture

    An infrastructure layer for microservices. Instead of each service implementing retries, load balancing, encryption, and tracing itself, a sidecar proxy (like Envoy) handles all of it transparently. Istio, Linkerd, Consul Connect. Used at scale with Kubernetes.

    Sidecar proxy
    Envoy, Linkerd2
    Control plane
    Istio, Consul

    The sidecar pattern

    Every service pod in Kubernetes gets an Envoy proxy injected alongside it automatically. All inbound and outbound traffic flows through the proxy. The service code never knows about retries, circuit breaking, mTLS — the proxy handles it all.

    SERVICE A POD
    App Container
    Envoy Sidecar
    SERVICE B POD
    App Container
    Envoy Sidecar
    All traffic: A's Envoy → mTLS encrypted → B's Envoy → B's app

    What the mesh handles automatically

    Traffic management
    Load balancing, canary deployments, traffic splitting (10% to v2), retries, timeouts, circuit breaking — all via config, not code.
    Security (mTLS)
    Every service-to-service call is automatically mutually-authenticated and encrypted. Zero-trust networking without code changes.
    Observability
    Every request traced, timed, and logged by the proxy. Distributed traces in Jaeger. Metrics in Prometheus. No instrumentation needed in app code.
    Policy enforcement
    Service A is not allowed to call Service B — enforced at mesh level. Rate limits, authorization policies — without touching service code.
    When to use it: Only when you have 20+ microservices on Kubernetes and are experiencing real pain around security, observability, or traffic management. Adding a service mesh to 3 services is massive over-engineering. At 100 services, it becomes essential.

    Architecture 12 · Advanced

    🚀 Space-Based Architecture

    Designed to eliminate the database bottleneck at extreme scale. Processing units share an in-memory distributed data grid (the "tuple space"). Data replicates across all units. No central database for hot paths. Millisecond latency at millions of transactions per second.

    Data store
    In-memory grid
    Latency
    < 1ms
    Throughput
    Millions TPS
    Complexity
    Very high

    The core concept

    Traditional architectures hit a wall when the database becomes the bottleneck. Space-based architecture removes the DB from the hot path entirely. Processing Units (PUs) read/write to an in-memory distributed grid. An async replication engine persists to disk in the background.

    The problem it solves: A ticket sales site releases tickets for a major concert. 500,000 users hit the site simultaneously. No database can handle 500k concurrent writes/reads. Space-based keeps everything in memory, distributed across 100 PUs, each holding a replica of the data.

    Components

    Processing Units (PU)
    Identical application instances. Each holds a copy of the relevant data in memory. Scale horizontally by adding more PUs. Handle requests without DB calls.
    In-memory data grid
    Hazelcast, Apache Ignite, Redis Cluster. Partitions data across nodes, replicates for fault tolerance. Sub-millisecond reads and writes.
    Virtualized middleware
    Messaging grid routes requests to available PUs. Data grid syncs state between PUs. Processing grid manages execution.
    Async persistence
    A separate service asynchronously writes from the in-memory grid to PostgreSQL/Cassandra. Not on the hot path — DB is for durability, not performance.

    Migration Paths

    How to migrate between architectures

    You never start with the right architecture. Real systems evolve. Here's how to migrate from one architecture to another without rewriting everything from scratch.

    Monolith → Microservices (the Strangler Fig pattern)

    The Strangler Fig pattern: Named after a vine that slowly wraps around a tree. New functionality is built as a microservice. Old monolith code is replaced piece by piece. The monolith "dies" gradually — never a big-bang rewrite. Used by Netflix, Amazon, and Shopify.
    1
    Add a proxy / API gateway in front of the monolith
    All traffic goes through it. Initially it routes everything to the monolith unchanged. This is your seam for the migration.
    2
    Identify the seam: find the most independent module
    Look for a module with a clear boundary, its own data, and minimal coupling. User Auth, Notifications, and Payments are common first extractions. Never start with the core domain.
    3
    Build the new service in parallel (don't delete yet)
    Build the new microservice. It has its own database. Test it thoroughly. The monolith still handles all traffic.
    4
    Route traffic gradually (canary deploy)
    Start with 1% of traffic to new service. Watch metrics. 10% → 50% → 100%. Rollback is easy — just re-route to monolith.
    5
    Delete the module from the monolith
    100% of traffic on new service. Remove the old module. Repeat for the next module. The monolith shrinks. New services grow.

    Monolith → Modular Monolith (safest upgrade)

    # Before: a mess — modules reach into each other import { getUserById } from '../users/UserRepository'; // ❌ reaching into internals import { sendEmail } from '../email/SmtpClient'; // ❌ wrong layer import { OrderModel } from '../database/models/order'; // ❌ DB details exposed # After: modular — only import through public index.ts contracts import { getUser } from '@modules/users'; // ✅ public API only import { sendEmail } from '@modules/notifications'; // ✅ through module contract import { createOrder } from '@modules/orders'; // ✅ clean boundary

    Adding Event Sourcing to an existing app

    Don't migrate everything at once. Identify one high-value domain (orders, transactions, patient records). Apply event sourcing there first. Run the event-sourced model alongside the existing model (dual-write). Validate correctness for weeks. Then cut over. Never replace the whole DB at once.
