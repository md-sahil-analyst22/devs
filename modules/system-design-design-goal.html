Module 1 · Getting Started

What is System Design?

System design is the process of defining the architecture, components, and data flow of a large-scale software system. Before building anything, engineers align on a set of design goals — the "buzzwords" that every system must balance.

Why do design goals matter?
Every system you build is a set of trade-offs. You can't have perfect scalability, 100% availability, strong consistency, and zero faults — all at the same time for free. Understanding these goals helps you make deliberate, justified decisions rather than accidental ones.
The Restaurant Analogy
Think of a restaurant. Scalability = adding more chefs when customers grow. Availability = always being open, never turning anyone away. Consistency = every customer gets the exact same menu and prices. Fault Tolerance = the kitchen still works if one oven breaks. These same tensions exist in every distributed system.

The 5 Core Design Goals

1 · Introduction
Understanding what system design is and the problems it solves at scale.
2 · Scalability
The ability to handle growing amounts of load — horizontally or vertically.
3 · Availability
The percentage of time a system is operational and accessible to users.
4 · Consistency
Whether all nodes in a distributed system see the same data at the same time.
5 · Fault Tolerance / No SPOF
The system's ability to continue operating when components fail.

Scalability

Scalability is the system's ability to handle increasing load — more users, more data, more requests — without degrading performance. It's the most talked-about property in system design interviews.

What is Scalability?

Definition
Scalability means a system can grow to handle more work by adding resources. A scalable system performs just as well with 10 million users as it does with 10 users — it just costs more. The key question: How does performance change as load increases?
Mental model: If your system can serve 100 requests/second on 1 server, can it serve 1,000 req/s on 10 servers with no code changes? If yes — it's horizontally scalable.

Why does it matter?

Growth happens fast
Viral moments, product launches, or seasonal traffic can increase load 100× overnight. Systems that aren't designed to scale will crash exactly when you need them most.
Cost efficiency
Over-provisioning resources wastes money. A scalable architecture lets you add capacity when needed and remove it when traffic drops — pay for what you use.
User experience
A slow or down system = users leaving. Scalability is directly tied to latency, throughput, and uptime — all things users feel immediately.
Business continuity
For e-commerce, a 1-second latency increase can reduce conversions by 7%. Scalability is a revenue-protecting investment, not just a technical nice-to-have.

Vertical vs Horizontal Scaling

Scaling Strategies

How to achieve Scalability

1
Add a Load Balancer
Distribute incoming traffic across multiple servers. Strategies include Round Robin, Least Connections, and IP Hashing. Tools: Nginx, HAProxy, AWS ALB.
2
Use Caching aggressively
Cache expensive DB queries in Redis or Memcached. A cache hit is 100–1000× faster than a DB read. Apply at every layer: browser, CDN, API, database.
3
Shard your Database
Split data across multiple DB nodes by user ID or region. Each shard handles a subset of traffic. Avoid joins across shards — they're expensive and slow.
4
Use a CDN for static assets
Serve images, CSS, JS from edge nodes closest to the user. This offloads 60–80% of your bandwidth and reduces latency dramatically. Tools: Cloudflare, AWS CloudFront.
5
Decouple with Message Queues
Use Kafka or RabbitMQ to decouple producers and consumers. Spikes in traffic fill the queue instead of crashing your service. Workers process at their own pace.

Do

  • Design stateless services from day 1
  • Cache at every layer (CDN, API, DB)
  • Use read replicas for read-heavy workloads
  • Auto-scale based on CPU / request rate
  • Shard databases by a natural partition key

Don't

  • Store session state in memory on one server
  • Vertically scale as your only strategy
  • Ignore database as the bottleneck
  • Couple services tightly (REST chains)
  • Premature optimisation before profiling

Availability

Availability is the fraction of time a system is operational and able to serve requests. It's usually expressed as a percentage — "nines" — and it's one of the most important SLAs (Service Level Agreements) you'll agree with customers.

Target
99.9% – 99.999%
Formula
Uptime / Total Time
Enemy
Single Point of Failure
Pattern
Redundancy

The Nines of Availability

Availability Levels — Downtime per year
Key insight: Going from 99.9% to 99.99% cuts downtime by 10×, but the engineering cost is typically 3–5× higher. Most production systems target 3–4 nines. Five nines is reserved for critical infrastructure (banking, air traffic control).

Why Availability matters

Real cost of downtime
Amazon loses ~$220,000 per minute when AWS goes down. Even for smaller companies, a 1-hour outage can destroy customer trust that took months to build. Availability is not just technical — it is a business KPI.

How to achieve High Availability

High Availability Architecture Pattern
Redundancy
Run multiple instances of every component. No single machine should be the only one doing a job. If one dies, others take over.
Health Checks
Load balancers continuously ping servers. If a server fails a health check, it's removed from rotation automatically — no manual intervention needed.
Graceful Degradation
When a service fails, show a fallback or cached version instead of an error. Users get reduced functionality, not a broken experience.

Do

  • Run at least 2 instances in different AZs
  • Use health checks and auto-restart
  • Set up DB replication with failover
  • Use circuit breakers for dependencies
  • Monitor and alert on error rates

Don't

  • Deploy all servers in a single data center
  • Rely on manual failover processes
  • Ignore dependency availability (3rd-party APIs)
  • Skip DR (Disaster Recovery) plans
  • Confuse availability with reliability

Consistency — Strong vs Eventual

Consistency defines whether all nodes in a distributed system see the same data at the same time. It's the trickiest design goal because it forces a fundamental trade-off with availability — you usually can't have both simultaneously.

What is Consistency?

The Bank Account Problem
You have $100. You withdraw $100 from ATM A at the same moment your partner withdraws $100 from ATM B. If the system isn't strongly consistent, both succeed and you're now at -$100. Consistency prevents this — every node must agree on the current value before allowing a write.

Strong Consistency

Definition
After a write completes, every subsequent read from any node returns that value. The system behaves as if there is a single copy of the data. Also called linearisability.
Strong Consistency — All nodes agree before acknowledging the write
Cost of Strong Consistency: The write must wait for all replicas to confirm before returning success. This increases latency. If a replica is slow or unreachable, it can also reduce availability. This is the core tension described by the CAP Theorem.

Eventual Consistency

Definition
After a write, replicas will eventually converge to the same value — but there is a window of time where different nodes may return different (stale) data. The system prioritises availability over immediate consistency.
Eventual Consistency — Nodes catch up asynchronously

Strong vs Eventual — When to choose which

Scenario Consistency Model Why
Bank transfersStrongStale balance = money lost
Inventory checkoutStrongOverselling = critical issue
Social media likesEventualSlightly off count is fine
Search index updateEventualNew content appearing 1s later is OK
User profile readEventualStale profile for seconds is tolerable
Distributed lockStrongTwo processes must not hold the same lock

Do

  • Default to eventual consistency for reads
  • Use strong consistency only where money/correctness is involved
  • Document the consistency model for each service
  • Use idempotent writes to handle retries safely

Don't

  • Force strong consistency everywhere — kills performance
  • Ignore consistency and assume "it'll be fine"
  • Mix consistency models without understanding trade-offs
  • Confuse consistency with durability

Fault Tolerance & No SPOF

Fault tolerance is the system's ability to continue operating correctly even when one or more of its components fail. Eliminating Single Points of Failure (SPOF) is the architectural strategy to achieve it.

Enemy

What is a Single Point of Failure?

Definition
A SPOF is any component whose failure causes the entire system to fail. If you have one database, one server, one network switch — those are all SPOFs. The rule: if it can fail and take everything with it, it's a SPOF. Eliminate it by adding redundancy.

SPOF vs Fault-Tolerant Architecture

SPOF vs Redundant Architecture

Key Fault Tolerance Patterns

Circuit Breaker
When a downstream service starts failing, the circuit "trips" and stops sending requests to it. It periodically checks if the service has recovered. Prevents cascade failures. Pattern: Closed → Open → Half-Open.
Retry with Backoff
When a request fails, retry it — but with exponentially increasing delays (1s, 2s, 4s, 8s...) plus random jitter. Prevents thundering-herd when a service recovers. Always set a max retry limit.
Bulkhead Pattern
Isolate parts of a system so a failure in one doesn't cascade to others. Like compartments in a ship — if one floods, the others stay dry. Use thread pools or separate services per tenant.
Timeout
Always set timeouts on every network call. A stuck upstream service should not block your service indefinitely. Fail fast, return an error or fallback, keep the rest of the system running.

Circuit Breaker — State Machine

Circuit Breaker States
Real-world example: Netflix's Hystrix library pioneered the circuit breaker pattern at scale. When their recommendation service failed, instead of crashing the whole app, they showed generic top-10 lists. Fault tolerance enabled graceful degradation.

Do

  • Replicate every stateful component (DB, cache)
  • Use circuit breakers for all external calls
  • Test failures with chaos engineering (Netflix Chaos Monkey)
  • Set timeouts on every network call
  • Deploy across multiple availability zones

Don't

  • Assume dependencies are always up
  • Skip failover testing until production breaks
  • Build synchronous chains of critical services
  • Use a shared database as the only data store
  • Ignore cascading failure scenarios
Reference · Theory

CAP Theorem

The CAP Theorem, proven by Eric Brewer in 2000, states that any distributed data store can only guarantee two of three properties at the same time: Consistency, Availability, and Partition Tolerance.

The bitter truth: Network partitions always happen in distributed systems. This means you must always sacrifice either Consistency or Availability — you get to choose which matters more for your use case.

The CAP Triangle

CAP Theorem — Pick any two (but P is mandatory)
CP Systems
Consistency + Partition Tolerance
When a partition happens, the system refuses to serve stale data — it returns an error instead. Great for: financial records, distributed locks.

Examples: HBase, MongoDB (w:majority), Redis Sentinel, ZooKeeper
AP Systems
Availability + Partition Tolerance
When a partition happens, nodes keep serving requests with potentially stale data. They converge when the partition heals (eventual consistency).

Examples: Cassandra, DynamoDB, CouchDB, Riak
CA Systems
Consistency + Availability
Only possible if you never have network partitions — i.e., a single-node or LAN database. Not realistic for large distributed systems over the internet.

Examples: PostgreSQL (single node), MySQL
PACELC Extension: Even without partitions, you face a trade-off between Latency and Consistency. PACELC (by Daniel Abadi) is a more complete model: "If Partition → choose A or C. Else → choose L or C."

Interview tip: In system design interviews, always explicitly state your consistency and availability trade-off. Say: "For the payment service I'll use strong consistency at the cost of slightly higher latency. For the activity feed, I'll use eventual consistency to maximise availability." Interviewers reward this deliberate thinking.
