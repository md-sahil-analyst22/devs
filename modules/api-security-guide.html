Module 1 · Start here

Why API security matters

You built it. You deployed it. You opened ports. Now anyone on the internet can find it. This is the reality of every server connected to the internet — and ignoring security isn't an option when real users and real data are involved.

Your situation right now: You have a voice calling agent, chatbots, and web apps hosted on Azure with ports open. Every open port is a door. Some doors need to be open (your users walk through them). The goal is to install locks, cameras, and alarms — not to brick up all the doors.

What happens without security

💸
API bill explosion
Someone finds your OpenAI-connected endpoint. They script 10,000 requests. Your API costs spike to hundreds of dollars overnight.
🗄️
Data breach
Your user data, conversation logs, personal information becomes accessible to anyone who hits the right endpoint.
🔊
Service abuse
Your voice calling agent gets scripted to make thousands of free calls. Your LiveKit minutes are consumed in hours.
🚫
Service downtime
Automated bots hammer your endpoints relentlessly. Your server crashes. Real users can't access your app.

The security mindset

Security is not a feature you add at the end. It's a set of layers you build into every component. Think of it like an onion — multiple layers, each one adding protection if the outer layer fails.

Layer 1 — Network (Azure NSG / Firewall)
Block unauthorized traffic before it even reaches your server. Port rules, IP filtering, VNet isolation.
↓ if network layer passes
Layer 2 — Web server (Nginx)
Rate limiting, IP whitelisting, blocking internal endpoints, SSL termination.
↓ if nginx layer passes
Layer 3 — Application (FastAPI)
Authentication middleware, authorization checks, input validation, CORS policy.
↓ if app layer passes
Layer 4 — Data
Parameterized queries (no SQL injection), encrypted at rest, access control per user.
The golden rule of API security: Never rely on a single layer. If Nginx is misconfigured, your FastAPI auth should still reject the request. If a JWT is somehow forged, your database ACLs should still block the query. Defense in depth = multiple independent layers.

Module 2 · Know your enemy

The threat landscape

You cannot defend against what you don't understand. Here are the real attacks that happen to exposed APIs every day — with concrete examples of what they look like against YOUR system.

Common API attacks

🤖
Brute force / credential stuffing
Automated scripts try thousands of username/password combinations per second against your login endpoint. Your exposure: POST /api/login with no rate limiting.
💀
Unauthorized API access
Someone discovers your endpoint URL (from browser DevTools, GitHub, or port scanning) and calls it directly without being your frontend. Your exposure: POST /api/chat, POST /api/call/start with no auth.
🌐
Cross-Site Request Forgery (CSRF)
A malicious website tricks a logged-in user's browser into making requests to your API. The browser sends cookies automatically. Your exposure: Any cookie-based authenticated endpoint.
💉
Injection attacks
Malicious input in API parameters that executes as SQL, commands, or code. Your exposure: Any endpoint that takes user input and queries a database or runs commands.
🌊
DDoS / resource exhaustion
Flooding your API with thousands of requests per second until your server can't respond to legitimate users. Your exposure: Any public-facing endpoint, especially your voice calling agent.
🎭
Fake webhook spoofing
An attacker sends fake webhook events to your /webhook/livekit endpoint, pretending to be LiveKit. Your app processes fake call events. Your exposure: Any webhook endpoint without signature verification.
🔑
Token/key theft
API keys or JWT tokens intercepted from network traffic, browser storage, or GitHub commits. Your exposure: Any key stored in client-side JS, .env files committed to git, or unencrypted HTTP.
🕵️
IDOR (Insecure Direct Object Reference)
User A calls GET /api/conversations/123 and gets User B's conversations by just changing the ID. Your exposure: Any endpoint that returns data by ID without verifying ownership.

How attackers find your APIs

Browser DevTools
Right-click → Inspect → Network tab shows every API call your frontend makes. Endpoint URLs, headers, request bodies — all visible.
Port scanning
Tools like nmap scan your IP for open ports. Every open port is an invitation to investigate what's behind it.
GitHub / Git leaks
Developers accidentally commit .env files, API keys, or internal URLs to public repos. Bots scan GitHub 24/7 for these.
Error messages
Detailed error responses reveal internal paths, database schemas, library names. Never expose stack traces in production.
DNS enumeration
Subdomain brute-forcing reveals api.yourdomain.com, internal.yourdomain.com, staging.yourdomain.com.
API path guessing
Common paths like /admin, /api/v1, /health, /metrics are tried automatically. Don't assume obscurity = security.
Assume your endpoints will be found. Security through obscurity (hiding the URL) is not a strategy. Even if your URL is a random string, automated tools will eventually find it. Real security means the endpoint rejects unauthorized requests — not that no one knows the URL.

Implementation in FastAPI

# main.py — complete API key setup import os, secrets from fastapi import FastAPI, Header, HTTPException, Depends from dotenv import load_dotenv load_dotenv() app = FastAPI() # Load from environment — NEVER hardcode in source code API_KEY = os.getenv("API_KEY") async def verify_api_key(x_api_key: str = Header(...)): # secrets.compare_digest prevents timing attacks # (timing attack: attacker measures response time to guess key character by character) if not secrets.compare_digest(x_api_key, API_KEY): raise HTTPException(status_code=403, detail="Forbidden") # Apply to specific route @app.post("/api/chat", dependencies=[Depends(verify_api_key)]) async def chat(body: dict): return {"reply": "Hello"} # Apply to ALL routes globally app = FastAPI(dependencies=[Depends(verify_api_key)])
# .env file — store secrets here, NEVER commit this to git API_KEY=sk-a7f3b9c2d1e4f6a8b0c3d5e7f9a1b2c4d6e8f0a2b4c6d8e0f2a4b6c8d0e2f4 # Generate a strong random key in Python import secrets print(secrets.token_hex(32)) # 64-character hex string
// Frontend JavaScript — send the key in every request const response = await fetch('/api/chat', { method: 'POST', headers: { 'Content-Type': 'application/json', 'x-api-key': 'your-api-key-here' // In production: read from env variable or config }, body: JSON.stringify({ message: 'Hello' }) });

Per-service API keys (better approach)

Instead of one key for everything, give each of your services its own key. If one is compromised, rotate only that one.

# Each service has its own key SERVICE_KEYS = { "livekit-agent": os.getenv("KEY_LIVEKIT_AGENT"), "chatbot-service": os.getenv("KEY_CHATBOT"), "frontend-web": os.getenv("KEY_FRONTEND"), "webhook-handler": os.getenv("KEY_WEBHOOK"), } async def verify_service( x_api_key: str = Header(...), x_service_name: str = Header(...) ): expected = SERVICE_KEYS.get(x_service_name) if not expected or not secrets.compare_digest(x_api_key, expected): raise HTTPException(status_code=403, detail="Unknown service") return x_service_name # caller knows which service made the request

What to do and what NOT to do

Do

  • Store keys in environment variables or Azure Key Vault
  • Use secrets.compare_digest() — not ==
  • Generate keys with secrets.token_hex(32)
  • Rotate keys periodically (every 90 days)
  • Give each service its own key
  • Log which key was used (for audit)

    • Don't

  • Hardcode keys in source code
  • Commit .env files to git
  • Use short/guessable keys
  • Use the same key for everything
  • Store keys in frontend JavaScript files
  • Return key in error messages

    JWT — JSON Web Tokens

    API keys are static — once created they're valid forever until rotated. JWT tokens are dynamic — they expire automatically, carry user identity, and can store permissions. The standard for user-facing APIs.

    Best for
    User authentication
    Expiry
    Built-in (exp claim)
    Stateless
    Yes — no DB lookup
    Carries data
    Yes — user id, roles

    What a JWT looks like

    # A JWT has 3 parts, separated by dots: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 # HEADER (base64) . eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzA1MDAwMDAwfQ== # PAYLOAD . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c # SIGNATURE # Decoded payload contains: { "sub": "user_123", # subject = user id "role": "user", # custom claim "exp": 1705000000, # expires at (unix timestamp) "iat": 1704913600 # issued at }

    Create and verify tokens in FastAPI

    # pip install python-jose[cryptography] import os from jose import JWTError, jwt from datetime import datetime, timedelta from fastapi import Depends, HTTPException from fastapi.security import OAuth2PasswordBearer SECRET_KEY = os.getenv("JWT_SECRET") ALGORITHM = "HS256" # ─── Create token (on login) ─── def create_access_token(user_id: str, role: str = "user"): payload = { "sub": user_id, "role": role, "exp": datetime.utcnow() + timedelta(hours=1), # expires in 1hr "iat": datetime.utcnow() } return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM) # ─── Verify token (on every protected request) ─── oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token") async def get_current_user(token: str = Depends(oauth2_scheme)): try: payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM]) user_id = payload.get("sub") role = payload.get("role") if not user_id: raise HTTPException(status_code=401) return {"user_id": user_id, "role": role} except JWTError: raise HTTPException(status_code=401, detail="Invalid or expired token") # ─── Protect a route ─── @app.get("/api/me") async def get_profile(user = Depends(get_current_user)): return {"user_id": user["user_id"]} # ─── Role-based access ─── def require_admin(user = Depends(get_current_user)): if user["role"] != "admin": raise HTTPException(status_code=403, detail="Admin only") return user @app.delete("/api/admin/users/{id}") async def delete_user(id: str, admin = Depends(require_admin)): pass

    Access tokens vs Refresh tokens

    Access Token (short-lived)
    Expires in 15 minutes to 1 hour. Sent with every API request. If stolen, attacker has it only briefly. This is what Authorization: Bearer ... contains.
    Refresh Token (long-lived)
    Expires in 7–30 days. Stored in HttpOnly cookie (can't be read by JavaScript). Used only to get a new access token. More secure storage, longer lifetime justified.
    JWT is stateless — great for scaling, risky for revocation. Once issued, you can't "cancel" a JWT unless you maintain a blacklist. This is why short expiry times (15–60 minutes) are important. If you need instant revocation, add a token ID to a Redis blacklist and check it on every request.

    OAuth2 & Azure AD

    OAuth2 is the standard protocol for "login with Google/Microsoft/GitHub." Azure AD (now Entra ID) is Microsoft's identity platform. For internal tools — especially in an organization — this means only your team members can log in, without you managing passwords.

    OAuth2 flow — how it works

    1
    User clicks "Login with Microsoft"
    Your app redirects to Azure AD login: https://login.microsoftonline.com/tenant-id/oauth2/v2.0/authorize
    2
    User authenticates with Microsoft
    Azure AD verifies credentials (including MFA if configured). Your app never sees the password.
    3
    Azure AD redirects back with an authorization code
    A short-lived one-time code is sent to your callback URL: https://yourapp.com/auth/callback?code=xxx
    4
    Your backend exchanges code for tokens
    Server-side call to Azure AD: swap the code for an access token + refresh token. Only your backend holds the secret key needed for this exchange.
    5
    Use tokens to call your API
    Issue your own JWT to the user. Every subsequent API call carries this JWT. Your FastAPI verifies it.

    FastAPI with Azure AD — implementation

    # pip install msal fastapi import msal TENANT_ID = os.getenv("AZURE_TENANT_ID") CLIENT_ID = os.getenv("AZURE_CLIENT_ID") CLIENT_SECRET = os.getenv("AZURE_CLIENT_SECRET") REDIRECT_URI = "https://yourapp.com/auth/callback" @app.get("/auth/login") async def login(): # Build the Azure AD login URL authority = f"https://login.microsoftonline.com/{TENANT_ID}" msal_app = msal.ConfidentialClientApplication(CLIENT_ID, CLIENT_SECRET, authority) auth_url = msal_app.get_authorization_request_url( scopes=["User.Read"], redirect_uri=REDIRECT_URI ) return {"login_url": auth_url} # redirect user here @app.get("/auth/callback") async def callback(code: str): msal_app = msal.ConfidentialClientApplication(CLIENT_ID, CLIENT_SECRET, authority) result = msal_app.acquire_token_by_authorization_code( code=code, scopes=["User.Read"], redirect_uri=REDIRECT_URI ) if "error" in result: raise HTTPException(status_code=401) # result["id_token_claims"] has user info: name, email, groups user_email = result["id_token_claims"]["preferred_username"] # Issue your own JWT for subsequent API calls token = create_access_token(user_id=user_email, role="user") return {"access_token": token}
    When to use Azure AD: If you're building internal tools for your team (admin dashboards, internal chatbots, team productivity tools), Azure AD means your team members log in with their Microsoft accounts — no password management for you, and MFA is handled by your organization.
    Module 6 · Protection layers

    CORS — Cross-Origin Resource Sharing

    Your browser enforces a rule: JavaScript on evil.com cannot call your API on yourapp.com. CORS is the mechanism that controls which origins (domains) are permitted to call your API. Get it wrong in either direction and things break.

    What is an "origin"?

    # Origin = protocol + domain + port https://yourapp.com:443 # origin 1 http://yourapp.com:80 # DIFFERENT origin (different protocol) https://api.yourapp.com # DIFFERENT origin (different subdomain) https://yourapp.com:3000 # DIFFERENT origin (different port) # When your JS on yourapp.com calls api.yourapp.com — that's cross-origin # Browser blocks it UNLESS api.yourapp.com allows it in CORS headers

    FastAPI CORS configuration

    from fastapi.middleware.cors import CORSMiddleware app.add_middleware( CORSMiddleware, # ✅ PRODUCTION: Only your actual frontend domain allow_origins=[ "https://yourapp.com", "https://www.yourapp.com", "https://admin.yourapp.com", ], # ❌ NEVER in production — allows ANY website to call your API # allow_origins=["*"], allow_credentials=True, # allow cookies allow_methods=["GET", "POST", "PUT", "DELETE"], allow_headers=["*"], # or list specific headers )
    CORS is a browser security feature — it does NOT protect server-to-server calls. If an attacker writes a Python script (not a browser) to call your API, CORS won't stop them. CORS only affects browser-based requests. For real security, you still need API key auth.
    The mistake everyone makes
    Setting allow_origins=["*"] for development, then deploying to production and forgetting to change it. Now any website can call your API using a logged-in user's credentials.
    Environment-aware CORS
    Use environment variables: ALLOWED_ORIGINS=https://yourapp.com in production. ALLOWED_ORIGINS=http://localhost:3000 in development. Never wildcard in production.
    Module 7 · Protection layers

    Rate Limiting

    Rate limiting prevents any single client from overwhelming your API. Without it, one bot can send 10,000 requests per second and crash your server. With it, excessive callers are slowed down or blocked while legitimate users continue normally.

    Rate limiting in Nginx (fastest — before FastAPI)

    # nginx.conf — add to http block http { # Define rate zones limit_req_zone $binary_remote_addr zone=general:10m rate=10r/s; limit_req_zone $binary_remote_addr zone=login:10m rate=3r/m; limit_req_zone $binary_remote_addr zone=api:10m rate=30r/m; server { # Apply to all routes (general protection) location / { limit_req zone=general burst=20 nodelay; limit_req_status 429; } # Stricter on login (anti brute-force) location /api/auth/login { limit_req zone=login burst=5 nodelay; proxy_pass http://localhost:8000; } # Voice/AI endpoints (expensive operations) location /api/call { limit_req zone=api burst=10 nodelay; proxy_pass http://localhost:8001; } } }

    Rate limiting in FastAPI with slowapi

    # pip install slowapi from slowapi import Limiter, _rate_limit_exceeded_handler from slowapi.util import get_remote_address from slowapi.errors import RateLimitExceeded from fastapi import Request limiter = Limiter(key_func=get_remote_address) app.state.limiter = limiter app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler) # Apply per-route rate limits @app.post("/api/chat") @limiter.limit("20/minute") # 20 requests per minute per IP async def chat(request: Request, body: dict): return {"reply": "..."} @app.post("/api/auth/login") @limiter.limit("5/minute") # strict login limit async def login(request: Request): pass @app.post("/api/call/start") @limiter.limit("3/minute") # expensive voice call — very strict async def start_call(request: Request): pass
    Endpoint typeRecommended limitReason
    Login / auth5 per minute per IPPrevent brute force attacks
    Chat / AI responses20 per minute per userPrevent LLM cost abuse
    Voice call start3 per minute per userVery expensive — protect resources
    General GET APIs60 per minute per IPNormal usage pattern
    File upload10 per hour per userStorage cost control
    Webhook handlers100 per minute per IPMust accept bursts from Stripe/LiveKit

    Security Headers

    HTTP response headers that tell browsers how to behave with your content. They protect against XSS attacks, clickjacking, MIME sniffing, and force HTTPS. Free protection — just config.

    Essential security headers

    # nginx — add to server block server { # Force HTTPS — browser never uses HTTP again for this domain add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always; # Prevent clickjacking — your page can't be loaded in an iframe on another domain add_header X-Frame-Options "SAMEORIGIN" always; # Prevent MIME sniffing — browser uses declared content type, not guessing add_header X-Content-Type-Options "nosniff" always; # Controls what browser features your page can use add_header Permissions-Policy "microphone=(), camera=(), geolocation=()" always; # Content Security Policy — whitelist what can run on your page add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' fonts.googleapis.com" always; # Don't leak referrer info to external sites add_header Referrer-Policy "strict-origin-when-cross-origin" always; }
    # FastAPI — add headers via middleware from fastapi import Request from starlette.middleware.base import BaseHTTPMiddleware class SecurityHeadersMiddleware(BaseHTTPMiddleware): async def dispatch(self, request: Request, call_next): response = await call_next(request) response.headers["X-Content-Type-Options"] = "nosniff" response.headers["X-Frame-Options"] = "SAMEORIGIN" response.headers["X-XSS-Protection"] = "1; mode=block" # Remove version info — don't tell attackers what you're running response.headers.delete("server") response.headers.delete("x-powered-by") return response app.add_middleware(SecurityHeadersMiddleware)

    You have multiple services: voice agent, chatbot, webhooks, main API. They call each other. The goal: only YOUR services can call YOUR internal endpoints. No stranger can use your internal APIs even if they somehow discover the URL.

(constant-time comparison) if not secrets.compare_digest(x_internal_secret, INTERNAL_SECRET): raise HTTPException(status_code=403, detail="Invalid secret") return x_service_name # Internal endpoint — should ALSO be blocked by nginx @app.post("/internal/transcribe") async def transcribe( body: dict, calling_service: str = Depends(verify_internal_call) ): return {"transcript": "..."}

    Webhook Security

    Webhooks are HTTP callbacks from external platforms (LiveKit, Stripe, Twilio) to your server. The challenge: how do you know the request really came from LiveKit and not an attacker pretending to be LiveKit? Signature verification is the answer.

    How HMAC signature verification works

    LiveKit server
    sends event
    →
    Signs payload
    with your secret
    →
    Your endpoint
    receives request
    →
    Re-compute signature
    from body + secret
    →
    ✓ Match = authentic
    process event

    Generic HMAC webhook verification

    import hmac, hashlib, secrets, os from fastapi import Request, Header, HTTPException async def verify_webhook_signature( request: Request, x_signature_256: str = Header(...) ): # IMPORTANT: read the raw body bytes BEFORE parsing JSON body_bytes = await request.body() secret = os.getenv("WEBHOOK_SECRET").encode() # Re-compute the expected signature expected_sig = hmac.new( secret, body_bytes, hashlib.sha256 ).hexdigest() # Compare (constant-time to prevent timing attacks) if not secrets.compare_digest(f"sha256={expected_sig}", x_signature_256): raise HTTPException(status_code=403, detail="Invalid webhook signature") return body_bytes @app.post("/webhook/livekit") async def livekit_webhook(body: bytes = Depends(verify_webhook_signature)): event = json.loads(body) if event["event"] == "room_started": pass # handle room event if event["event"] == "participant_joined": pass # handle participant

    Platform-specific webhook verification

    LiveKit webhook
    LIVEKIT_API_SECRET is your signing secret.
    Header sent: Authorization: Bearer {token}
    Use the LiveKit Python SDK's webhook_receiver.receive() method — it handles verification automatically.
    Stripe webhook
    From Stripe Dashboard → Webhooks → Signing secret.
    Header: Stripe-Signature
    Use: stripe.WebhookSignature.verify_header(payload, sig, secret)
    Critical: always verify raw bytes, not parsed JSON. Parse the body as bytes first, verify the signature, THEN parse JSON. If you parse JSON first and re-serialize it, the signature will fail because whitespace or key ordering may differ.
    Module 11 · Service security

    WebSocket Security

    WebSockets are persistent, bidirectional connections. Unlike HTTP, you can't add auth headers after the initial handshake. Authentication must happen at connection time — typically via a token in the query parameter or during the HTTP upgrade request.

    The WebSocket authentication flow

    1
    Client gets a short-lived WS token first
    Client calls POST /api/ws-token with their existing JWT. Server returns a short-lived WebSocket-specific token (15-minute expiry).
    2
    Client connects with token in URL
    wss://yourapp.com/ws/agent?token=eyJhbGci... — token is in the query string, verified before accepting the connection.
    3
    Server validates token before accepting
    If the token is invalid or expired, server closes with code 1008 (Policy Violation). Connection is never established.

    FastAPI WebSocket implementation

    from fastapi import WebSocket, WebSocketDisconnect # Step 1: issue a short-lived WS token (HTTP endpoint) @app.post("/api/ws-token") async def get_ws_token(user = Depends(get_current_user)): ws_token = create_access_token( user_id=user["user_id"], expires_delta=timedelta(minutes=15) # short-lived ) return {"ws_token": ws_token} # Step 2: WebSocket endpoint that validates token first @app.websocket("/ws/agent") async def websocket_agent(websocket: WebSocket, token: str): # Verify token BEFORE accepting the connection try: user = verify_token(token) except: await websocket.close(code=1008) # Policy Violation return await websocket.accept() # Only accept AFTER auth passes try: while True: data = await websocket.receive_text() # Process message from authenticated user await websocket.send_text(f"Echo: {data}") except WebSocketDisconnect: pass # Client disconnected normally
    // Frontend — get token first, then connect async function connectWebSocket() { // Get short-lived WS token const { ws_token } = await fetch('/api/ws-token', { method: 'POST', headers: { 'Authorization': `Bearer ${userJwt}` } }).then(r => r.json()); // Connect with token const ws = new WebSocket(`wss://yourapp.com/ws/agent?token=${ws_token}`); ws.onopen = () => console.log('Connected'); ws.onmessage = (e) => console.log('Received:', e.data); }

    WebRTC Security

    WebRTC establishes peer-to-peer connections for real-time audio/video. The connection itself is encrypted (DTLS-SRTP mandatory). Security is controlled through the signaling layer — particularly by gatekeeping ICE/TURN credentials.

    How WebRTC security works

    Client requests
    ICE credentials
    authenticated HTTP call
    →
    Server verifies
    caller identity
    JWT / API key check
    →
    Returns short-lived
    TURN credentials
    expire in 1 hour
    →
    WebRTC connection
    established (DTLS)
    encrypted by default

    # pip install livekit from livekit import api import os LIVEKIT_API_KEY = os.getenv("LIVEKIT_API_KEY") LIVEKIT_API_SECRET = os.getenv("LIVEKIT_API_SECRET") @app.post("/api/call/token") async def get_livekit_token( room_name: str, user = Depends(get_current_user) # user must be authenticated ): # Create a room token — participant can only access this specific room token = api.AccessToken(LIVEKIT_API_KEY, LIVEKIT_API_SECRET) token.with_identity(user["user_id"]) token.with_name(user["user_id"]) token.with_grants(api.VideoGrants( room_join=True, room=room_name, can_publish=True, # can send audio/video can_subscribe=True, # can receive audio/video )) # Token expires in 1 hour — must reconnect after expiry livekit_token = token.to_jwt() return {"token": livekit_token, "room": room_name}

    Prevent IDOR — always check ownership

    # ❌ INSECURE — User A can access User B's conversations @app.get("/api/conversations/{conv_id}") async def get_conversation(conv_id: str): return await db.conversations.get(conv_id) # ❌ no ownership check # ✅ SECURE — Always verify the user owns the resource @app.get("/api/conversations/{conv_id}") async def get_conversation(conv_id: str, user = Depends(get_current_user)): conversation = await db.conversations.get(conv_id) if not conversation: raise HTTPException(status_code=404) if conversation.user_id != user["sub"]: raise HTTPException(status_code=403) # or 404 to not confirm existence return conversation
