🗺️ Topic 1 — Overview
Communication in System Design
Every distributed system is just a collection of services that talk to each other. How they talk — synchronously or asynchronously, with what protocol, in what shape — is one of the most important design decisions you'll make.

The Core Question

When Service A needs to talk to Service B, what are your options?
Every API style and messaging pattern is an answer to this question. The right answer depends on your latency requirements, payload shape, team ownership, coupling tolerance, and whether both sides need to be online at the same time.

Two Communication Styles

⚡ Synchronous
Caller waits for a response before continuing. Tight coupling. Simple to reason about. Examples: REST, GraphQL, gRPC.

Good for: queries, user-facing reads, real-time responses.
📬 Asynchronous
Caller sends a message and moves on. Loose coupling. Harder to debug. Examples: Message Queues, Event Streams.

Good for: writes, background jobs, event-driven workflows.

🌐 Topic 2 — API Paradigm
REST API
REST (Representational State Transfer) is the dominant style for building web APIs. It uses standard HTTP methods on resource-based URLs to create a uniform, stateless interface between client and server.

What is REST?

The Big Idea
REST is not a protocol — it's an architectural style with 6 constraints. Resources are nouns (/users, /orders). HTTP verbs are actions (GET, POST, PUT, DELETE). The server holds no session state between requests.
HTTP/HTTPS JSON / XML Stateless Resource-based URLs Cacheable

REST Constraints (The 6 Rules)

1. Client-Server
Separation of concerns. Client handles UI; server handles data. They evolve independently.
2. Stateless
Every request contains all info needed. No server-side session. Client sends auth token every time.
3. Cacheable
Responses must declare if they're cacheable. GET /users/1 with Cache-Control max-age=60 is cached by the browser.
4. Uniform Interface
Resources identified by URIs. Standard verbs (GET/POST/PUT/DELETE). Self-descriptive messages. HATEOAS links.
5. Layered System
Client doesn't know if it's talking to origin server or a proxy/CDN/load balancer. Enables scalability.
6. Code on Demand (optional)
Server can send executable code to client (e.g., JavaScript). Rarely used explicitly.

REST in Action — Example API

// ── USERS RESOURCE ────────────────────────────────────── GET /users → List all users POST /users → Create a new user GET /users/{id} → Get a specific user PUT /users/{id} → Replace user entirely PATCH /users/{id} → Update user partially DELETE /users/{id} → Delete user // ── NESTED RESOURCE ───────────────────────────────────── GET /users/{id}/orders → Orders for a user POST /users/{id}/orders → Create order for user // ── REQUEST / RESPONSE ────────────────────────────────── POST /users HTTP/1.1 Content-Type: application/json { "name": "Alice", "email": "alice@example.com" } HTTP/1.1 201 Created Location: /users/42 { "id": 42, "name": "Alice", "createdAt": "2025-01-01" }

Request-Response Lifecycle

REST Problems — Where it Breaks Down

Over-fetching
GET /users/42 returns all 30 fields. The mobile app only needs name and avatar. Wasted bandwidth on every request.
Under-fetching / N+1
To show a feed of 20 posts with author names: 1 call for posts + 20 calls for each author. That's the N+1 problem.
Versioning Complexity
/v1/users, /v2/users — versioning sprawls. Breaking changes force URL or header version bumps.
No Real-Time
REST is request-response. For live data you need polling, SSE, or WebSockets — outside the REST model.
💡 REST is still the default: Despite its weaknesses, REST is battle-tested, universally understood, works over HTTP caches, and has tooling everywhere. Use GraphQL or gRPC when REST's pain points are actually hurting you — not speculatively.

Do

  • Use nouns for resource URLs, not verbs
  • Return the right HTTP status codes always
  • Version your API from day one (/v1/)
  • Use pagination for list endpoints
  • Document with OpenAPI / Swagger
  • Use HTTPS always, even internally

Don't

  • Use GET /getUser or POST /deleteUser
  • Return 200 for errors with error in body
  • Put actions in URLs (use verbs in body)
  • Return unbounded lists without pagination
  • Ignore caching headers (huge perf win)
🔷 Topic 3 — API Paradigm
GraphQL
GraphQL is a query language for your API. Instead of fixed endpoints returning fixed shapes, clients ask for exactly the data they need — no more, no less — in a single request.

What is GraphQL?

The Big Idea
GraphQL was created by Facebook in 2012 to solve the mobile data problem. With REST, the server decides what data to return. With GraphQL, the client decides. One endpoint (POST /graphql), infinite flexibility.
Single Endpoint Strongly Typed Schema Client-Driven Queries Introspectable No Over/Under-fetching

REST vs GraphQL — The Core Difference

GraphQL Query Syntax

# ── Query (Read) ───────────────────────────────────────── query GetUserProfile { user(id: "42") { name email avatar posts(last: 5) { title createdAt likes } followers { count } } } # ── Mutation (Write) ────────────────────────────────────── mutation CreatePost { createPost(input: { title: "Hello World" body: "My first post" }) { id title createdAt } } # ── Subscription (Real-time) ────────────────────────────── subscription OnNewMessage { newMessage(roomId: "room-1") { text sender { name } timestamp } }

GraphQL Schema Definition

type User { id: ID! name: String! email: String! posts: [Post!]! followers: FollowerCount! } type Post { id: ID! title: String! body: String! author: User! likes: Int! createdAt: String! } type Query { user(id: ID!): User posts(limit: Int): [Post!]! } type Mutation { createPost(input: PostInput!): Post! deletePost(id: ID!): Boolean! }

GraphQL Architecture

GraphQL Pros & Cons

✅ Strengths
No over/under-fetching · Single endpoint · Self-documenting schema · Strongly typed · Great for mobile · Subscriptions for real-time · Works across multiple data sources
⚠️ Weaknesses
Complex queries can hit DB hard · HTTP caching doesn't work naturally · N+1 problem without DataLoader · Overkill for simple CRUD · Learning curve for teams
DataLoader Pattern: GraphQL's Achilles heel is the N+1 problem — each post resolver might query its author separately. DataLoader batches these into a single SELECT * FROM users WHERE id IN (...). Essential for production GraphQL.

Do

  • Use DataLoader to batch & cache DB calls
  • Set query depth and complexity limits
  • Use persisted queries in production
  • Implement field-level authorization in resolvers
  • Use schema-first design (SDL first)

Don't

  • Allow unbounded nested queries (DoS risk)
  • Skip authorization checks in resolvers
  • Use GraphQL for simple CRUD APIs
  • Ignore N+1 query performance issues
  • Expose internal DB schema directly
⚙️ Topic 4 — API Paradigm
gRPC
gRPC is a high-performance, open-source Remote Procedure Call framework by Google. It uses HTTP/2 for transport and Protocol Buffers (Protobuf) for serialization — making it 5–10× faster than REST+JSON for internal microservice communication.

What is gRPC?

The Big Idea
gRPC lets you call a function on a remote server as if it were a local function. You define a contract in a .proto file. The framework auto-generates client and server code in 10+ languages. No JSON. Binary wire format. Bidirectional streaming.
HTTP/2 Protocol Buffers Code Generation Streaming Polyglot

Defining a Service — .proto file

// user.proto ───────────────────────────────────────────── syntax = "proto3"; package user; // 1. Define your data structures message GetUserRequest { string user_id = 1; } message UserResponse { string id = 1; string name = 2; string email = 3; int32 follower_count = 4; } message UserStream { string user_id = 1; string event = 2; int64 timestamp = 3; } // 2. Define your service methods service UserService { // Unary RPC — standard request/response rpc GetUser(GetUserRequest) returns (UserResponse); // Server streaming — server sends many responses rpc StreamUserEvents(GetUserRequest) returns (stream UserStream); // Client streaming — client sends many, server replies once rpc UploadUsers(stream UserResponse) returns (UploadSummary); // Bidirectional streaming — both sides stream rpc Chat(stream Message) returns (stream Message); }

4 Types of gRPC Communication

Unary RPC
Classic request → response. Client sends one message, server replies once. Like a standard HTTP call but over HTTP/2 with Protobuf. Most common.
Server Streaming
Client sends one request, server replies with a stream of messages. Example: subscribe to live stock price feed or event log tail.
Client Streaming
Client sends a stream of messages, server replies once when done. Example: upload a large file in chunks or batch-insert rows.
Bidirectional Streaming
Both sides send independent streams over one connection. Example: real-time chat, collaborative editing, duplex IoT sensor data.

gRPC in Microservices Architecture

Why not gRPC everywhere? Browsers don't support HTTP/2 binary framing natively. You need grpc-web proxy for browser clients. For public APIs that must be consumed by any HTTP client — stick with REST. gRPC shines purely in the internal service mesh.

Do

  • Use gRPC for internal microservice calls
  • Define shared .proto files in a separate repo
  • Use deadlines/timeouts on every RPC call
  • Use interceptors for auth, logging, tracing
  • Version proto files carefully (backward compat)

Don't

  • Use gRPC as your public API (browser pain)
  • Remove fields from proto without deprecation
  • Skip error handling — use gRPC status codes
  • Ignore load balancing (L7 needed for gRPC)
  • Use gRPC for simple scripts or quick tools
📬 Topic 5 — Async Communication
Message Queues
A message queue is a form of asynchronous service-to-service communication. The sender (producer) puts a message in a queue and moves on immediately. The receiver (consumer) picks it up whenever it's ready. No waiting. No coupling.

What is a Message Queue?

The Big Idea
Think of it as a post office. You drop off a letter (message), the post office holds it (queue), and the recipient (consumer) picks it up on their schedule. Producer and consumer never need to be online simultaneously. This is the key difference from synchronous APIs.
Asynchronous Decoupled Durable At-least-once delivery Load Leveling

Core Concepts Explained

Why Use a Message Queue?

  • Decoupling — Order Service doesn't need to know Email Service exists. It just fires an event. Add new consumers without touching the producer.
  • Load Leveling — A traffic spike produces 10,000 orders/second. The queue absorbs the burst. Consumers process at their own pace. No dropped requests.
  • Reliability — If the consumer crashes, messages persist in the queue. When it restarts, it picks up where it left off. Nothing is lost.
  • Parallel Processing — Multiple consumers in a group each get different messages. Scale consumers horizontally to drain the queue faster.
  • Retry Logic — Failed messages go to a Dead Letter Queue (DLQ) for inspection and manual replay. Automatic retries with backoff.

Queue vs Pub/Sub vs Stream

📬 Queue (Point-to-Point)
One producer, one consumer group. Each message is processed by exactly one consumer. Example: SQS, RabbitMQ. Good for task workers.
📢 Pub/Sub (Fan-out)
One producer, many independent consumers all get every message. Example: SNS, Redis Pub/Sub. Good for notifications, webhooks.
🌊 Event Stream
Ordered, persistent log. Consumers read at their own position. Can replay history. Example: Kafka. Good for audit logs, analytics.

Delivery Guarantees — Critical to Know

At-most-once
Message is sent once. May be lost if consumer crashes. No retry. Lowest overhead. OK for metrics where loss is tolerable.
At-least-once
Message will be delivered, possibly more than once (retry on failure). Consumer must be idempotent. Most common guarantee.
Exactly-once
Delivered exactly once, never duplicated. Very hard and expensive to implement. Kafka supports it with transactions. Use sparingly.
⚡ Design insight: At-least-once delivery is the norm. Design your consumers to be idempotent — processing the same message twice produces the same result. Use a deduplication key (message ID) to detect and skip duplicates.

Do

  • Make consumers idempotent always
  • Set up a Dead Letter Queue (DLQ) for failures
  • Add message IDs for deduplication
  • Set message TTL to avoid stale processing
  • Monitor queue depth as a key metric
  • Use consumer groups for parallel processing

Don't

  • Use a queue for synchronous request-response
  • Put large blobs in messages (use URL + S3)
  • Ignore poison pill messages (DLQ them)
  • Skip monitoring — silent queue backup = disaster
  • Assume at-most-once delivery in business logic
