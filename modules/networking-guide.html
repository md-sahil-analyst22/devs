Module 1 · Foundations

How internet traffic works

Before Nginx, Ngrok, or Cloudflare make sense — you need to understand what happens when a user opens a browser, types a URL, and your server receives a request. This is the foundation everything else builds on.

One paragraph summary: When you type https://yourapp.com, your browser asks DNS "what is the IP for yourapp.com?", gets back an IP address, opens a TCP connection to port 443 on that IP, sends an HTTPS request, and your server processes it and sends back a response. Every tool in this guide is about controlling some part of this journey.

The complete journey of one request

1
User types URL in browser
https://yourapp.com/api/chat — the browser parses this: protocol=HTTPS, domain=yourapp.com, path=/api/chat, port=443 (implied by HTTPS).
2
DNS lookup — domain to IP
Browser asks a DNS server: "what IP address is yourapp.com?" DNS returns 20.123.45.67. Now the browser knows where to send the request.
3
TCP connection established
Browser opens a TCP connection to 20.123.45.67:443. If it's HTTPS, SSL/TLS handshake happens here — certificates are exchanged, encryption is agreed upon.
4
HTTP request arrives at your server
Your server (Nginx) receives: GET /api/chat HTTP/1.1. Nginx reads it, applies your configuration rules, and decides what to do with it.
5
Nginx routes to your application
Nginx sees the path /api/ and forwards the request to your FastAPI running on localhost:8000. This is called reverse proxying.
6
Response flows back
FastAPI processes the request, returns JSON. Nginx sends it back through the SSL connection to the browser. User sees the response.

Key concepts you'll encounter

IP Address
The numeric address of a computer on the internet. 20.123.45.67. Like a postal address — every server needs one to receive mail.
Port
A numbered door on an IP address. Port 443 = HTTPS, Port 80 = HTTP, Port 8000 = your FastAPI. Multiple apps share one IP via different ports.
DNS
Domain Name System. Translates human-readable names (yourapp.com) to IP addresses. Like a phone book for the internet.
TCP/IP
The protocol stack for internet communication. TCP ensures reliable delivery. IP routes packets to the right address.
SSL/TLS
Encryption layer over TCP. Makes HTTP into HTTPS. Certificates prove you're the real server, not an impostor.
Reverse Proxy
A middleman server (Nginx) that receives public traffic and forwards it to private backend servers. Hides your internal network.
Module 2 · Foundations

IP Addresses & DNS

Understanding IP addresses and DNS is essential for configuring Nginx, Cloudflare, and deploying applications. These are the building blocks of how servers find each other.

Types of IP addresses

Public IP — visible on internet
Your Azure VM's IP. Anyone on the internet can send traffic to it. This is what DNS records point to. Example: 20.123.45.67. Your ISP or cloud provider assigns this.
Private IP — local network only
Internal network addresses. 192.168.x.x, 10.x.x.x, 172.16-31.x.x. Your laptop's IP on WiFi. Not reachable from the internet directly. Nginx on a VM might listen on 127.0.0.1 (localhost).
localhost / 127.0.0.1
Special IP that means "this machine itself." When FastAPI runs on localhost:8000, only programs on the same server can reach it. Nginx forwards to it from the public IP.
0.0.0.0 — all interfaces
Means "listen on ALL network interfaces." When Nginx binds to 0.0.0.0:443, it accepts connections from the public internet, the local network, and localhost. The default when you want to be publicly accessible.

How DNS works — step by step

# DNS resolution chain for yourapp.com # 1. Browser checks local cache — did we look this up recently? # 2. OS checks /etc/hosts — any manual overrides? # 3. Query goes to Recursive Resolver (your ISP or 1.1.1.1) # 4. Resolver asks Root Nameserver: "who handles .com?" # 5. Resolver asks .com TLD Nameserver: "who handles yourapp.com?" # 6. Resolver asks Authoritative Nameserver (Cloudflare/Route53): "yourapp.com?" # 7. Returns: yourapp.com → 20.123.45.67 (A record) # 8. Browser caches result for TTL seconds, then connects to that IP # Useful commands nslookup yourapp.com # basic DNS lookup dig yourapp.com # detailed DNS info dig yourapp.com +short # just the IP dig yourapp.com MX # mail records host yourapp.com # simple lookup

Module 3 · Ports

What are ports?

A server has one IP address but can run many services. Ports are numbered "doors" — each service listens on a different door number. When you open port 8000 in Azure, you're unlocking that specific door for internet traffic.

Analogy: Your server's IP address is like a building's street address. Ports are like apartment numbers within that building. The mail (traffic) arrives at the building (IP) and is delivered to the specific apartment (port) it's addressed to.

Module 4 · Ports

Port Binding

Port binding is when a program "claims" a port and starts listening for connections on it. When you run uvicorn main:app --port 8000, FastAPI is binding to port 8000. Only one program can bind to a port at a time.

How binding works

# When you start FastAPI: uvicorn main:app --host 0.0.0.0 --port 8000 # The OS creates a socket and binds it: # socket.bind(('0.0.0.0', 8000)) — "I claim port 8000 on all interfaces" # socket.listen() — "start accepting connections" # --host controls WHICH interface to listen on: uvicorn main:app --host 127.0.0.1 --port 8000 # ONLY localhost — cannot reach from internet uvicorn main:app --host 0.0.0.0 --port 8000 # ALL interfaces — reachable from internet # In production: bind to 127.0.0.1, let Nginx handle public traffic # Nginx binds 0.0.0.0:443 → forwards to 127.0.0.1:8000
Bind to 127.0.0.1 (production)
FastAPI only accepts connections from the same machine. Nobody outside can directly hit your app. Nginx is the only thing that talks to FastAPI. This is the secure way.
Bind to 0.0.0.0 (risky)
FastAPI accepts connections from anywhere. Anyone who knows your IP and port 8000 can hit your app directly, bypassing Nginx security. Only do this for temporary debugging.

Binding in different frameworks

# FastAPI / Uvicorn uvicorn main:app --host 127.0.0.1 --port 8000 # Node.js app.listen(3000, '127.0.0.1') # Python raw socket server_socket.bind(('127.0.0.1', 8000)) # Nginx binding (in config) listen 443 ssl; # binds 0.0.0.0:443 (all interfaces) listen 127.0.0.1:8080; # only localhost # systemd service to auto-start on boot # /etc/systemd/system/fastapi.service [Unit] Description=FastAPI Application After=network.target [Service] User=www-data WorkingDirectory=/var/www/yourapp ExecStart=/usr/bin/uvicorn main:app --host 127.0.0.1 --port 8000 Restart=always [Install] WantedBy=multi-user.target
Port already in use error? OSError: [Errno 98] Address already in use means another process is already bound to that port. Run lsof -i :8000 to find it, then either kill it or choose a different port.
Module 5 · Ports

Port Forwarding

Port forwarding redirects incoming traffic from one port/address to another. It's the mechanism that lets a router share one public IP among many devices, lets Nginx route traffic to different apps, and lets you expose local services to the internet.

3 types of port forwarding you'll use

1. Router / NAT port forwarding (home lab)

Problem: Your home server has a private IP (192.168.1.100). The internet can only see your router's public IP. Port forwarding tells your router: "when traffic arrives on port 8000, send it to 192.168.1.100:8000."
# Router admin panel (192.168.1.1) → Port Forwarding section: External Port: 8000 Internal IP: 192.168.1.100 # your server's local IP Internal Port: 8000 Protocol: TCP # After this: publicIP:8000 → 192.168.1.100:8000

2. SSH port forwarding (tunneling)

# LOCAL forwarding — access remote service locally # "Forward my localhost:5432 to the remote server's localhost:5432" ssh -L 5432:localhost:5432 user@remoteserver.com # Now you can connect to PostgreSQL on remote server via localhost:5432 psql -h localhost -p 5432 -U myuser mydatabase # REMOTE forwarding — expose local port to remote server # "My localhost:8000 should be accessible on remote server's port 9000" ssh -R 9000:localhost:8000 user@remoteserver.com # DYNAMIC forwarding — SOCKS proxy through SSH ssh -D 1080 user@remoteserver.com # Then set browser to use SOCKS5 proxy at localhost:1080

3. Azure NSG + application-level forwarding (your setup)

# Azure NSG: controls which ports the cloud firewall allows # Inbound rule: port 443 from internet → your VM # Then Nginx inside VM: port 443 → localhost:8000 (FastAPI) # The chain for your Azure setup: Internet → Azure NSG (port 443 allowed) → VM public IP :443 → Nginx (listens on :443) → FastAPI (localhost:8000) # In Azure portal: VM → Networking → Add inbound port rule Destination port: 443 Protocol: TCP Action: Allow Priority: 100

Module 6 · Nginx

What is Nginx?

Nginx (pronounced "engine-x") is a high-performance web server and reverse proxy. It sits in front of your applications and handles everything the internet throws at it — routing, SSL termination, rate limiting, static files, WebSockets — before traffic ever reaches your code.

Created
2004 by Igor Sysoev
Market share
~34% of all websites
Model
Event-driven async
Config file
/etc/nginx/nginx.conf

Web server vs Reverse proxy — the two modes

Mode 1 — Web server

  • Serves static files directly (HTML, CSS, JS, images)
  • No backend processing needed
  • Extremely fast — reads files, sends bytes
  • Use: React/Vue build output, static sites
  • Example: root /var/www/html; try_files $uri /index.html;

    • Mode 2 — Reverse proxy

  • Forwards requests to a backend app (FastAPI, Node.js)
  • Backend processes the request, Nginx delivers the response
  • Adds SSL, rate limiting, caching in front of any app
  • Use: FastAPI, Django, Express — any HTTP server
  • Example: proxy_pass http://127.0.0.1:8000;

    • What Nginx handles so your app doesn't have to

    SSL termination
    Nginx decrypts HTTPS traffic and forwards plain HTTP to your app. Your FastAPI never needs to know about certificates.
    Static file serving
    Serves HTML, CSS, JS, images from disk at millions of requests/sec. Never goes through Python for static assets.
    Rate limiting
    Limits requests per second/minute per IP. Blocks abuse before it hits your application code.
    Load balancing
    Distributes traffic across multiple app instances. If one crashes, others continue.
    Gzip compression
    Compresses responses automatically. JSON that's 100KB becomes 15KB. Faster for users.
    Caching
    Stores responses and serves them without hitting your backend for repeat requests.

    Install Nginx on Ubuntu (Azure VM)

    # Install sudo apt update sudo apt install nginx -y # Start and enable on boot sudo systemctl start nginx sudo systemctl enable nginx # Check status sudo systemctl status nginx # Test config before applying sudo nginx -t # Reload after config changes (zero downtime) sudo systemctl reload nginx # Restart (brief downtime) sudo systemctl restart nginx # Config locations /etc/nginx/nginx.conf # main config /etc/nginx/sites-available/ # your site configs go here /etc/nginx/sites-enabled/ # symlinks to active configs /var/log/nginx/access.log # all requests /var/log/nginx/error.log # errors

    Nginx Configuration Deep Dive

    Nginx config is a hierarchy of blocks. Understanding the structure — and how server, location, and upstream blocks work — lets you build any routing logic you need.

    The config hierarchy

    http { } block
    Global HTTP settings. Rate limit zones, gzip, log formats, upstream groups. One per nginx.conf.
    ↓ contains
    server { } block
    Defines a virtual host — one per domain/subdomain. Listens on a port, matches server_name. Can have many per nginx.
    ↓ contains
    location { } block
    Matches URL paths. location /api/ { } handles all /api/* requests. Contains proxy rules, rate limits, etc.

    Anatomy of a server block

    # /etc/nginx/sites-available/yourapp server { listen 80; # what port to listen on server_name yourapp.com www.yourapp.com; # what domain to match return 301 https://$host$request_uri; # redirect HTTP → HTTPS } server { listen 443 ssl http2; # HTTPS with HTTP/2 server_name yourapp.com www.yourapp.com; # ── SSL certificates ── ssl_certificate /etc/letsencrypt/live/yourapp.com/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/yourapp.com/privkey.pem; # ── Logging ── access_log /var/log/nginx/yourapp.access.log; error_log /var/log/nginx/yourapp.error.log; # ── Gzip ── gzip on; gzip_types application/json text/css application/javascript; # ── Location blocks ── location / { proxy_pass http://127.0.0.1:8000; # FastAPI proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; } } # Enable this site sudo ln -s /etc/nginx/sites-available/yourapp /etc/nginx/sites-enabled/ sudo nginx -t && sudo systemctl reload nginx

    Location block matching — how Nginx picks the right block

    # Location matching priority (highest to lowest) location = /exact/path { } # 1. EXACT match — highest priority location ^~ /prefix/ { } # 2. PREFIX (blocks regex) location ~ /regex/ { } # 3. REGEX (case-sensitive) location ~* /regex/ { } # 4. REGEX (case-insensitive) location /prefix/ { } # 5. PREFIX match (longest wins) location / { } # 6. DEFAULT — catch-all # Practical examples location = /health { return 200 "OK"; } # exact: only /health location /api/ { proxy_pass http://127.0.0.1:8000; } # /api/anything location /webhook/ { proxy_pass http://127.0.0.1:8001; } # different service location ~* \.(jpg|png|gif|css|js)$ { # static files root /var/www/yourapp/static; expires 30d; } location / { root /var/www/yourapp; } # everything else: static

    Nginx as Reverse Proxy

    A reverse proxy sits between the internet and your backend services. It receives all public traffic and forwards it to the right internal service. This is the most important Nginx pattern for deploying FastAPI, Node.js, or any backend app.

    Forward proxy vs Reverse proxy

    Forward proxy

  • Sits in front of clients (browsers, scripts)
  • Clients configure it explicitly (browser settings)
  • Use: corporate firewalls, VPNs, bypassing geo-blocks
  • Backend servers don't know the real client

    • Reverse proxy (Nginx)

  • Sits in front of servers (FastAPI, Node.js)
  • Transparent to clients — they think they're talking to Nginx
  • Use: load balancing, SSL, routing, security
  • Clients don't know about backend servers

    • Complete reverse proxy configuration

    # Full production proxy setup for FastAPI server { listen 443 ssl http2; server_name api.yourapp.com; # ── Proxy headers — tell FastAPI who the real client is ── proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; # ── Timeouts ── proxy_connect_timeout 60s; proxy_send_timeout 60s; proxy_read_timeout 60s; # increase for AI/long ops # ── Buffer settings ── proxy_buffering off; # OFF for streaming (SSE, AI) proxy_buffer_size 4k; # ── API routes → FastAPI ── location /api/ { limit_req zone=api burst=30 nodelay; proxy_pass http://127.0.0.1:8000; } # ── WebSocket → FastAPI ── location /ws/ { proxy_pass http://127.0.0.1:8000; proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; proxy_read_timeout 3600s; # long-lived WS connections } # ── SSE (Server-Sent Events for AI streaming) ── location /api/stream/ { proxy_pass http://127.0.0.1:8000; proxy_buffering off; proxy_cache off; proxy_set_header X-Accel-Buffering no; proxy_read_timeout 300s; # long timeout for AI responses } # ── Internal endpoints — BLOCK ── location /internal/ { return 404; } }
    X-Real-IP is essential. Without proxy_set_header X-Real-IP $remote_addr, your FastAPI sees all requests coming from 127.0.0.1 (Nginx). Rate limiting per IP won't work. User IP logging won't work. Always pass real IP headers through.

    SSL / HTTPS Setup with Let's Encrypt

    HTTPS encrypts traffic between users and your server. Without it, anyone on the network can read passwords, tokens, and data in transit. Let's Encrypt gives you free SSL certificates. Certbot automates renewal.

    Setup HTTPS in 5 minutes

    1
    Point your domain to your server
    In your DNS provider (Cloudflare or domain registrar), add an A record: yourapp.com → 20.123.45.67. Wait for propagation (30 sec to a few minutes with Cloudflare).
    2
    Install Certbot
    sudo apt install certbot python3-certbot-nginx -y
    3
    Get certificate (auto-configures Nginx)
    sudo certbot --nginx -d yourapp.com -d www.yourapp.com
    4
    Certbot auto-renews — verify it works
    sudo certbot renew --dry-run # test auto-renewal
    Certificates expire every 90 days. Certbot adds a cron job to renew automatically.
    5
    Open ports 80 and 443 in Azure NSG
    Certbot needs port 80 to verify domain ownership. Port 443 for HTTPS. Both must be open in Azure NSG inbound rules.
    # What Certbot adds to your Nginx config: ssl_certificate /etc/letsencrypt/live/yourapp.com/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/yourapp.com/privkey.pem; include /etc/letsencrypt/options-ssl-nginx.conf; ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem; # Certificate locations /etc/letsencrypt/live/yourapp.com/ ├── fullchain.pem # your cert + intermediate chain ├── privkey.pem # private key — keep secret ├── cert.pem # your cert only └── chain.pem # intermediate chain only # Check certificate expiry sudo certbot certificates openssl x509 -noout -dates -in /etc/letsencrypt/live/yourapp.com/cert.pem

    Load Balancing with Nginx

    When one server instance can't handle your traffic, you run multiple instances and distribute load across them. Nginx's upstream block defines the pool of backend servers and the algorithm for distributing requests.

    # Define upstream group (pool of backend servers) upstream fastapi_cluster { # Round-robin (default) — each request goes to next server server 127.0.0.1:8000; server 127.0.0.1:8001; server 127.0.0.1:8002; } upstream fastapi_weighted { # Weighted — powerful server gets more traffic server 127.0.0.1:8000 weight=3; # 3x more traffic server 127.0.0.1:8001 weight=1; } upstream fastapi_sticky { # ip_hash — same client always goes to same server (sessions) ip_hash; server 127.0.0.1:8000; server 127.0.0.1:8001; } upstream fastapi_least_conn { # least_conn — send to server with fewest active connections least_conn; server 127.0.0.1:8000; server 127.0.0.1:8001; server 127.0.0.1:8002 backup; # only used if others are down } server { location /api/ { proxy_pass http://fastapi_cluster; } }

    Run multiple FastAPI instances with systemd

    # Start 3 FastAPI instances on different ports uvicorn main:app --host 127.0.0.1 --port 8000 --workers 1 & uvicorn main:app --host 127.0.0.1 --port 8001 --workers 1 & uvicorn main:app --host 127.0.0.1 --port 8002 --workers 1 & # OR: single command with multiple workers (Uvicorn manages) uvicorn main:app --host 127.0.0.1 --port 8000 --workers 4

    Health checks — remove failed servers

    # Nginx Plus (paid) has active health checks # Open-source Nginx uses passive health checks: upstream backend { server 127.0.0.1:8000 max_fails=3 fail_timeout=30s; server 127.0.0.1:8001 max_fails=3 fail_timeout=30s; # If a server fails 3 times in 30s → marked as down for 30s }

    WebSocket & Streaming (SSE)

    WebSockets and Server-Sent Events (SSE) are persistent connections — the server keeps pushing data. Standard HTTP proxy settings don't work for these. Nginx needs specific configuration to handle them correctly.

    WebSocket proxying

    Why special config? WebSockets start as HTTP and then upgrade to a persistent bidirectional connection via the Upgrade header. Nginx must be told to forward this upgrade, otherwise it closes the connection after the first response.
    # WebSocket proxy — the crucial headers location /ws/ { proxy_pass http://127.0.0.1:8000; proxy_http_version 1.1; # WebSocket requires HTTP/1.1 proxy_set_header Upgrade $http_upgrade; # forward the Upgrade header proxy_set_header Connection "upgrade"; # tell backend to upgrade proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_read_timeout 3600s; # keep connection for 1 hour proxy_send_timeout 3600s; }

    SSE (Server-Sent Events) for AI token streaming

    SSE is how you stream AI tokens to the browser. Your FastAPI yields tokens as they arrive from OpenAI/Anthropic, Nginx forwards each token immediately without buffering. The browser receives and displays tokens one by one.
    # SSE requires buffering OFF — or tokens wait until buffer is full location /api/stream/ { proxy_pass http://127.0.0.1:8000; proxy_buffering off; # ⚑ CRITICAL for SSE proxy_cache off; proxy_set_header X-Accel-Buffering no; proxy_read_timeout 300s; # 5 min for long AI responses proxy_set_header Host $host; proxy_set_header Connection ''; # keep-alive chunked_transfer_encoding on; # allows streaming chunks }
    # FastAPI SSE endpoint example from fastapi.responses import StreamingResponse import asyncio async def token_generator(prompt: str): async for chunk in openai_stream(prompt): yield f"data: {chunk}\n\n" # SSE format: "data: ...\n\n" yield "data: [DONE]\n\n" @app.get("/api/stream/chat") async def stream_chat(prompt: str): return StreamingResponse( token_generator(prompt), media_type="text/event-stream" )

    Ngrok — Expose Local Servers to Internet

    Ngrok creates a secure tunnel from a random public URL to your local machine. Your laptop running FastAPI on port 8000 becomes accessible as https://abc123.ngrok.io — without opening any router ports, without a domain, without a server.

    Use case
    Dev & testing
    Requires
    No server setup
    URL
    *.ngrok.io (free)
    Protocol
    HTTPS, TCP, TLS

    How Ngrok works

    Browser / API caller
    internet
    ─HTTPS─▶
    Ngrok Cloud
    abc123.ngrok.io
    ─tunnel─▶
    Ngrok agent
    your laptop
    ─local─▶

    Install and use Ngrok

    # Install on Ubuntu/Debian curl -sSL https://ngrok-agent.s3.amazonaws.com/ngrok.asc | sudo tee /etc/apt/trusted.gpg.d/ngrok.asc >/dev/null echo "deb https://ngrok-agent.s3.amazonaws.com buster main" | sudo tee /etc/apt/sources.list.d/ngrok.list sudo apt update && sudo apt install ngrok -y # Authenticate (get token from ngrok.com) ngrok config add-authtoken YOUR_TOKEN_HERE # Basic usage — expose port 8000 ngrok http 8000 # Output: # Forwarding: https://abc123.ngrok.io → localhost:8000 # You now have a public URL with HTTPS! # Expose on specific subdomain (paid plan) ngrok http --subdomain=myapp 8000 # → https://myapp.ngrok.io # Tunnel TCP port (for databases, SSH, etc.) ngrok tcp 5432 # expose PostgreSQL ngrok tcp 22 # expose SSH # With basic auth (protect your tunnel) ngrok http --basic-auth="user:password" 8000 # Ngrok config file ~/.ngrok2/ngrok.yml authtoken: YOUR_TOKEN tunnels: fastapi: proto: http addr: 8000 subdomain: myapp chatbot: proto: http addr: 8001 # Start all tunnels at once ngrok start --all

    When to use Ngrok vs not

    Good use cases

  • Testing webhooks locally (Stripe, LiveKit, Twilio)
  • Sharing local demo with a client without deploying
  • Testing mobile app against local backend
  • OAuth callback URLs during development
  • Temporarily exposing a dev server for quick feedback

    • Don't use Ngrok for

  • Production deployments — URLs change on restart
  • High traffic — free plan has connection limits
  • Long-running services — sessions expire
  • Anything that needs a stable, permanent URL
  • Services with sensitive data you can't route through ngrok.com

    • Testing LiveKit webhooks locally with Ngrok

    # Your FastAPI is running locally uvicorn main:app --port 8000 # Ngrok creates public URL ngrok http 8000 # → https://abc123.ngrok.io # In LiveKit dashboard → Webhooks → add: # https://abc123.ngrok.io/webhook/livekit # LiveKit now sends webhook events to your local FastAPI! # Ngrok web inspector at http://localhost:4040 shows all requests

    Cloudflare DNS Management

    Cloudflare's DNS is where you map your domain to your server. Understanding how to add records, the difference between proxied and DNS-only, and how subdomains work is essential for deploying any application.

    Common DNS setup for web apps

    # In Cloudflare DNS dashboard: # Root domain → your Azure VM Type: A Name: @ # @ means the root domain (yourapp.com) Content: 20.123.45.67 # your Azure VM public IP Proxy status: Proxied ☁️ # orange cloud = Cloudflare protection # www subdomain → same server Type: CNAME Name: www Content: yourapp.com Proxy status: Proxied ☁️ # API subdomain → same or different server Type: A Name: api Content: 20.123.45.67 Proxy status: Proxied ☁️ # api.yourapp.com → nginx → fastapi # Database — NEVER proxied, not exposed at all # DB should not have a public DNS record # Staging environment Type: A Name: staging Content: 20.123.45.99 # staging VM (different IP) Proxy status: DNS only ☁️ # grey cloud — bypass Cloudflare for staging

    Proxied vs DNS-only

    ☁️ Proxied (Orange cloud)

  • Traffic routes through Cloudflare servers
  • Your server's real IP is hidden
  • DDoS protection, WAF, caching active
  • Free SSL between user and Cloudflare
  • Use for: all public-facing web traffic

    • ⚫ DNS only (Grey cloud)

  • DNS resolves directly to your server IP
  • Traffic goes straight to your server
  • No Cloudflare protection or caching
  • Required for: email (MX records), SSH, non-HTTP
  • Use for: staging, internal services, mail servers
    • Cloudflare doesn't proxy everything. Email (MX records) must be DNS-only — Cloudflare doesn't handle mail. SSH also needs DNS-only since it's TCP port 22, not HTTP/HTTPS. Cloudflare proxy only works for HTTP (port 80) and HTTPS (port 443) by default.

    Cloudflare Tunnel

    Cloudflare Tunnel creates an outbound-only encrypted connection from your server to Cloudflare's network. No inbound ports needed — not even 443. Your server calls Cloudflare, Cloudflare routes traffic to it. More secure than opening any port.

    The game-changer: With Cloudflare Tunnel, you close ALL inbound ports on your server (including 443 and 80). The tunnel agent (cloudflared) runs on your server and makes an outbound connection to Cloudflare. Traffic flows through this outbound tunnel. Attackers have no open port to attack.

    Cloudflare Tunnel vs Traditional setup

    Traditional (ports open)

  • Azure NSG: ports 80 and 443 open to internet
  • Nginx listens on public IP
  • Direct path for DDoS: hit your IP directly
  • Server IP is exposed (even with Cloudflare proxy)
  • Port scanning reveals open ports

    • Cloudflare Tunnel (no ports)

  • Azure NSG: ALL inbound ports closed
  • Cloudflared agent: outbound only
  • No direct path to your server — must go through Cloudflare
  • Real IP completely hidden
  • No ports = nothing to scan

    SSL / TLS / Certificates

    SSL (now called TLS) is the encryption that makes HTTPS. It does two things: proves the server is who it claims to be (authentication) and encrypts all data in transit (confidentiality). Understanding the certificate chain helps you debug HTTPS issues.

    The TLS handshake — simplified

    1
    Client Hello
    Browser says: "I want to connect securely. Here are the encryption algorithms I support (TLS version, cipher suites)."
    2
    Server sends certificate
    Server sends its SSL certificate — contains the server's public key and is signed by a Certificate Authority (CA) like Let's Encrypt.
    3
    Browser verifies certificate
    Browser checks: Is the cert signed by a trusted CA? Is it for the right domain? Is it expired? If all pass, connection is trusted.
    4
    Key exchange
    Browser and server agree on a shared encryption key using asymmetric encryption. Now both have the same secret key without ever sending it over the wire.
    5
    Encrypted communication begins
    All subsequent messages are encrypted with the shared key (symmetric encryption — fast). The handshake happens in ~50ms.

    Certificate types

    DV (Domain Validated)
    Proves you control the domain. Free from Let's Encrypt. Good for most web apps and APIs.
    OV (Organization Validated)
    Proves your organization exists. Paid. Used by businesses where the org name in the cert matters.
    EV (Extended Validation)
    Highest validation. Shows company name in browser. Used by banks, payment processors. Most expensive.
    Wildcard cert
    One cert for all subdomains: *.yourapp.com covers api.yourapp.com, ws.yourapp.com, admin.yourapp.com etc.
    Multi-domain (SAN)
    One cert for multiple distinct domains: yourapp.com AND yourotherapp.com.
    Self-signed
    You signed it yourself. Free but browsers show "Not Secure" warning. OK for internal services, never for public.

    Cloudflare SSL modes — choose carefully

    ModeUser ↔ CloudflareCloudflare ↔ OriginUse it?
    OffHTTP onlyHTTP onlyNever
    FlexibleHTTPS ✓HTTP (unencrypted!)Never — origin is unencrypted
    FullHTTPS ✓HTTPS (self-signed OK)OK but not ideal
    Full (Strict)HTTPS ✓HTTPS (valid cert required)Use this — most secure
    Strict (HSTS)HTTPS + HSTSHTTPS (valid cert required)Best — once enabled, no rollback

    Troubleshooting Guide

    The most common problems you'll hit — and exactly how to diagnose and fix them. Work through the checklist for each issue.

    502 Bad Gateway — Nginx can't reach my app +
